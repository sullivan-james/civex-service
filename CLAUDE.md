# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Setup

Dependencies and the venv are managed by [uv](https://docs.astral.sh/uv/) — it reads `pyproject.toml`, resolves against the committed `uv.lock`, and provisions a matching Python 3.12 itself (see `.python-version`) if the system doesn't have one.

```bash
uv sync --extra server --extra workflows --extra dev  # standard dev setup (== `make install`)
uv sync --all-extras                                   # every optional extra (== `make install-all`)
uv sync                                                 # base install only, SQLite, no extras

uv lock                                                 # re-resolve after editing pyproject.toml deps
uv run civex --help                                     # run inside the synced env without activating it
```

`uv sync` creates `.venv/`. There's no separate activation step required for `uv run ...`; activate `.venv/bin/activate` directly if you want a persistent shell.

`make check`/`make secrets` also require the [gitleaks](https://github.com/gitleaks/gitleaks#installing) binary on `PATH` — it's not a `uv`/`npm` dependency. Install via `brew install gitleaks`, `go install github.com/gitleaks/gitleaks/v8@latest`, or download a release binary.

## Commands

Common tasks are wrapped in the `Makefile` — `make help`-style targets: `install`, `lint`, `format`, `format-check`, `typecheck`, `test`, `secrets`, `check` (everything CI runs), `pre-commit`, `serve`, `dev`, `clean`.

```bash
# CLI
uv run civex --help
uv run civex init                 # create a _civex/ project in the current directory
uv run civex serve                # start HTTP API (requires the server extra)
uv run civex serve --reload       # dev mode with auto-reload  (== `make serve`)

# Tests
uv run pytest tests/              # run all smoke tests            (== `make test`)
uv run pytest tests/test_smoke.py::test_init_creates_civex_dir  # single test

# Lint / format / typecheck
make check                        # ruff format --check, ruff check, mypy, pytest — what CI runs
make lint                         # ruff check --fix
make format                       # ruff format

# Frontend (cd frontend/ first)
npm run dev                       # Vite dev server (proxies /api to localhost:8000)  (== `make dev`)
npm run build                     # tsc + Vite production build (outputs to frontend/dist/)
```

The server serves the built frontend from `frontend/dist/` via the `ui` router. During development run `civex serve --reload` and `npm run dev` in parallel — Vite proxies API calls.

## Architecture

```
src/civex/
  cli/           # Typer commands — parse args → call service → format output
  domain/        # Plain dataclasses (DTOs) and exceptions; no framework dependency
  services/      # Business logic: SchemaService, DatasetService, RecordService, FileService
  repositories/
    protocols.py         # Protocol interfaces (SchemaRepository, DatasetRepository, etc.)
    local/               # SQLAlchemy implementations of those protocols
  db/
    models.py    # SQLAlchemy 2.0 ORM models (Schema, Field, Dataset, Record)
    session.py   # Engine factory; engine is cached, session is per-request
  plugins/
    base.py      # WorkflowContext (the host side of a run) + PluginTier
    runtime.py   # Drives any plugin over the wire protocol: describe/run, host calls, timeout
    launchers.py # How each tier starts: UvLauncher, DockerLauncher, InProcessLauncher (built-ins)
    workers.py   # Plugin processes/threads kept warm between runs
    host_api.py  # The one table of functions a plugin may call, by permission action
    registry.py  # Discovers built-ins and user plugins from _civex/plugins/
    builtins/    # Built-in plugins (see Built-in plugins section below)
  workflows/
    definition.py  # Pydantic models for YAML workflow files
    executor.py    # Topological sort (Kahn's) + step execution
  server/
    app.py       # FastAPI app factory
    routers/     # One router per resource: schemas, datasets, records, files, workflows, ui
  config.py      # find_project_root() walks up from cwd; load_config() reads _civex/config.toml
  context.py     # AppContext dataclass + build_local_context() factory
  console.py     # Rich Console instance used across CLI
```

### Layer rules (strict)

- `cli` → `services` via `AppContext`. Never touches repos or DB models directly.
- `services` → `repositories/protocols` (interfaces). Never imports from `cli` or `db`.
- `repositories/local` → `db/models`. The only layer that imports SQLAlchemy models.
- `plugins` → `WorkflowContext` only. Never imports SQLAlchemy or sessions.
- `domain` has no imports from the rest of civex — safe to import anywhere.

### AppContext pattern

**The service layer is the public Python API.** `civex.open(path)` (`context.open_project`: finds the project at or above `path` like the CLI does, `find_project_root(start)`) returns the same `AppContext` the CLI and server build, in-process with no server; `AppContext` is a context manager (commit on success, rollback on error, then close). There is no separate client or facade to keep in step with the CLI and API, so nothing outside a service reaches into its private attributes (`dataset_svc.lookup`/`schema_svc.lookup` resolve a name or id, `store_svc.queue()`); a caller that needs something gets a public service method. **Typed tables for notebooks:** `FileAccessService.typed_rows(query, columns=, geo=split|geojson|wkt, files=path|name, references=name|id)` and `.frame(...)` (a pandas DataFrame, imported lazily: `Int64`/`float64`/`boolean`/`datetime64[UTC]`/`category`/`string` columns, `attrs["units"]` and `attrs["types"]`) are the export's table (`_columns_for` + `table_rows`, one page of `stream_records` at a time as a `PlannedTable`, so the cost is fixed per page: `tests/services/test_frame.py`) with each cell in `domain/tables`' `PYTHON` form (`python_value`: a whole-day `date` as `datetime.date`, a partial date kept as its string, a datetime UTC-aware; `geo.to_wkt`/`point_lat_lon`); files are their path on this computer from the plan's `paths` (`_local_paths`, else the name). `AppContext.frame`/`rows(collection, schema, where=, search=, search_fields=, within=, **options)` only build the `RecordQuery`. No HTTP or CLI twin: those are the table export's json/csv. Guide: `docs/guides/python.md`.

`build_context(project)` in `context.py` wires all repos and services for one `Project` (`civex/project.py`: the `Config`, the `ConfigStore` it is kept in, the `actor` changes are recorded as, optionally a shared `engine` and `migrated=True` to skip the per-request schema check); `build_local_context(config)` is `build_context(Project.local(config))`, the project in a folder on this machine. CLI commands call `get_ctx()` from `cli/utils.py`, then call `ctx.commit()` after mutating operations, and `ctx.close()` when done. The server resolves the project once per request with `deps.current_project(request)` (the one in the cwd, unless the host set `app.state.project_resolver`) and builds the context from it; routes that need only the settings (`settings`, `db`, `ai`) take `Depends(current_project)` instead of `get_ctx`. **Settings are saved only through `ctx.config_store`** (`ConfigStore`: `load`/`save`/`flag`; `FileConfigStore` is config.toml; `parse_config`/`render_config` are the pure text forms), never by calling `save_config` from a service, so a hosted project can keep them elsewhere. Exceptions: the database-admin paths (`db_service.set_url`/`setup_docker`, `db_move_service`) and the CLI, which are the local host by definition.

### Features (what this server does)

`domain/features.py` names what a server may offer (`volumes`, `store_admin`, `local_workflows`, `plugin_editor`, `terminal`, `db_admin`, `updates`, `logs`, `ai`, `open_folder`, `desktop`, and for hosts `direct_files`, `accounts`, `hub_compute`); `LOCAL_FEATURES` is everything a project in a folder on this machine does and the default on `Project`. Three places read it and nowhere else decides: `server/app.api_routers(features)` is the one router list (a router wholly of one feature is left out of a host without it, and carries `requires(feature)`), `deps.requires(feature)` on a route inside a shared router answers 501 (`FeatureUnavailableError`, plain words from `unavailable_message`), and `GET /api/status/features` tells the frontend, whose `hooks/useFeatures` + `utils/features.offered` hide nav items (`Layout` `NavItemDef.feature`), Settings sections and the Ask AI button; until the server answers, the local set is assumed so nothing flickers. `background.run_pending_jobs` drains nothing where `local_workflows` is off, and `TransferWorker.drain` nothing where `volumes` is. `Project.local` derives the set from the settings (`project.local_features`: a project whose files are in a bucket has no `volumes` and offers `direct_files`); a host passes its own. Adding a feature: a name and sentence in `FEATURES`, the router or route gated, and `feature:` on the UI items that are part of it.

**Permissions: what the caller may do, said once.** `domain/permissions.py` is a small vocabulary of actions (`read`, `write_records`, `change_structure`, `manage_files`, `delete`, `manage_members`; `ACTIONS` has the plain words) over the project or named collections (`collection_scope`); `Permissions.can/require(action, collection_id)` (`require` raises `NotAllowedError`, 403), `can_somewhere` for a thing shared by everyone that any writer may change (a saved filter or export), `EVERYTHING` for the local user. The `Project` carries `permissions` (and `account`, `domain/accounts.Account`: who this is and where members are managed, None for whoever sits at the machine); `build_context` hands the same object to every service (`permissions=` on `RecordService`, `DatasetService`, `SchemaService`, `ViewService`, `ExportDefinitionService`, `FileService`), which ask it at their boundaries, before anything changes (`RecordService._require_each` checks every collection of a bulk delete or restore first), and to `SyncAuthorityService(policy=)`, since `Permissions.refuses(who, entry)` is a `SyncPolicy` (`action_for(entry)` maps a change to its action and collection), so a person at a browser and their device are held to one rule. `GET /api/me` (`routers/me.py`) serves the account and permissions; the frontend's `hooks/useMe` (`usePermissions().can/why`, `useAccount`) assumes everything until the server answers and the controls stay in place, switched off, with the reason as their title (the explorer's New and Delete, the record page's values (`RecordFieldGrid readOnly`), the file drop zone, Add field, Delete schema/collection, Edit details). A new write path takes `self._permissions.require(...)` first; a new control consults `usePermissions`.

**Background hosts take a context factory.** `HistoryJobs`, `TransferJobs`, `SyncJobs` and `run_pending_jobs(make_context)` open contexts through what they are given (`context.ContextFactory`; `local_context()` is the default, the cwd project), and a route that queues a drain passes `context_factory(ctx.project)` so it runs on the project the request was about. A host serving many projects constructs them per project.

### Charts and the Analytics page

**A chart is one definition, drawn by one renderer, worked out by one service call, used in three places.** `domain/charts.py` (pure): a `Chart` (`id`, optional `title`, `size` small|large) is **bars** (a `domain/summary.SavedSummary`: `group_by`, `measures`, `sort`, `show`, `chart_measure`, as `parse_group_by`/`parse_measure` write them) or a **map** (`map`: a location field, `field` or `kind.field`); `parse_chart(s)` is the one check, `Scope` the records a card counts (kind and collection by id, `within`, `search`, a filter tree). It says nothing about which records: a chart counts what it is shown beside. Bars are `RecordService.summarise`, a map `RecordService.points`; `RecordService.check_chart(schema, chart)` holds one to a kind's fields without reading a record.

- **A kind's charts** (`schemas.charts`, a JSON list; migration `e4b9c1a7d2f6`): `SchemaService.set_charts(name, charts)` (`require_somewhere(write_records)`: shared by everyone like a saved filter, not structure; checked through `check_chart`, handed over with `use_chart_check` in `context.py` since the record service sits above; one `update` entry, none when unchanged), `PUT /schemas/{s}/charts`, `civex schema charts list|add|remove|clear`. Part of the schema's snapshot (written `None` when none are set, as before kinds had charts), so it is audited and syncs with the schema (protocol 4: `FIELDS_SINCE["schema"]["charts"]`, a v3 device is not sent it). `_rewrite_charts` keeps charts in step when a field of the kind or of a kind above is renamed (rewritten) or deleted (the chart goes), each kind changed an entry like a rewritten template. A bundle carries them.
- **The Analytics page** is one synced, audited thing per project: `dashboards` (one row, `domain/dashboard.DASHBOARD_ID`, the same on every copy so two devices' first edits are one thing and the authority's create-of-existing merge settles them), `cards` a JSON list of `Card` (`id`, `kind` chart|widget, `size` small|wide, `title`, and `chart` + `records` (a `Scope`) or a `widget` key of `WIDGETS`); `parse_cards` is the one check. Until edited it is `default_cards()` and nothing is stored. `DashboardService` (`ctx.dashboard_svc`: `page`, `save`, `add`, `remove`, `resize`, `query_for(card, collection=)`) asks `read` / `require_somewhere(write_records)`, checks a new or changed chart card (`_check`: the kind, `check_chart`, the filter resolves), leaves one already on the page alone (so a card whose field or collection is gone stays, `DashboardCardDTO.problem`, until removed), writes nothing for a no-op save, and logs `dashboard` entries (Activity: "Analytics page edited", links to `/analytics`). API `GET`/`PUT /dashboard` (a chart card is drawn by the client with `POST /records/summary` or `/records/points` over its records); CLI `civex dashboard show|add|remove`. Sync: kind `dashboard` is protocol 4 (`KINDS_SINCE`; `kinds_for`/`snapshot_for`/`entry_for` are the peer router's adapter).
- **`views.summary` (the unreleased "saved analysis") is gone.** Migration `e4b9c1a7d2f6` turned every view that had one into a chart card on the page (in place where a card named it, else added at the end; ids derived from what they replace so every copy converts alike) carrying the view's kind, filter, collection, record and search, and left the view as a saved filter. A saved filter (a view) is which records: filter, sort, and the columns and `files_layout` it was saved with.
- **Counting what is inside:** the measure `inside:<kind>` (`summary.INSIDE`, `MeasurePlan.child` = schema id and depth from `schema_svc.descendants`) counts the live records of a kind beneath each record summarised: a correlated count up the parent chain summed per group (`summary_sql._inside`), one statement (`test_counting_inside_is_one_statement_however_many_records`). Grouping a parent list by a *child's* field is not offered (a record has many of them).
- **Frontend: one board.** `components/charts/ChartView` is the one renderer (bars: one `useRecordSummary` over a `RecordSelectionBody`, drawn by `SummaryChart`; in a card (`compact`) categories are a row per bar, each a `ListButton` with `aria-pressed`, while a line over time and a histogram keep their own form, smaller, so a card looks like the chart it opens as; a map: `MapView` over `RecordsMap`; `large` adds the table of numbers (`SummaryResult`) and **Download numbers**). `components/charts/ChartBoard` (cards: an **Enlarge** icon button and a ⋮ menu holding **Edit…**, **Larger** / **Smaller** (`Chart.size` small|large: a large card spans the board and draws the full chart), the host's extras, Move up/down and **Remove**, which is deliberately not a button on the card; and **Add chart**, which asks its host to open the builder) and `components/charts/NewChart` (the builder, always at full width where a chart opens large, `chart=new` in the address, or `chart=edit-<id>` on an existing chart (`initial`; it keeps its id, place and size; `utils/charts.chartPick` is the reverse of `buildChart`): the choices on the left (*Quick picks*, *One bar for each*, *Each bar shows*, *A map*, a title) and a live preview on the right, the same `ChartView` over the records the chart will count) and `OpenChart` are used by the explorer's column (`components/explorer/ChartsColumn` + `useExplorerCharts`), a kind's **Charts** tab (`components/schemas/KindCharts`, saved at once) and the Analytics page (`pages/AnalyticsPage`: `ChartView` cards with **Records** and **Open**, **For** narrowing every chart to one collection (`?for=`), **Edit page** as before; ### Data model

Record `data` is stored as a JSON/JSONB dict (no EAV), keyed by **field UUID** — `RecordService._names_to_ids()`/`_ids_to_names()` translate at the service boundary, so everything above that layer sees name-keyed data and renaming a field costs nothing in storage. Field types: `integer | float | string | boolean | date | datetime | geo | file | file_list | reference | reference_list | enum | url | tags | longtext | formula` (`VALID_DTYPES` in `schema_service.py` is the authority; a `formula` stores nothing, see **Formula fields**).

- `file` / `file_list`: record stores `FileRef` dict(s) `{sha256, filename, size}`; bytes live in `_civex/objects/<sha256[:2]>/<sha256[2:]>` (git object store layout).
- `date`: stored as an ISO string at the precision it was written (`2019`, `2019-06` or `2019-06-14`; a `precision` restriction names the least precise form a field accepts, default `day`). Logic in `domain/partial_dates.py`, mirrored by `frontend/src/utils/partialDates.ts`. Min/max compare whole periods. `datetime`: always stored as a UTC ISO string. `RecordService.add`/`update` normalise every datetime via `_normalise_datetimes()` (and the CLI via `coerce_value`), reading a value with no UTC offset as wall time in the field's `timezone` restriction, else the collection's `timezone` (`datasets.timezone`), else UTC. DST gaps/overlaps and malformed values are rejected; `update` skips values merely echoed back, so a legacy offset-less value isn't shifted when a zone is set later. The logic lives in `domain/timezones.py`; `frontend/src/utils/dates.ts` mirrors its DST rules for display and entry, and works to the second: the datetime input must have `step={1}` (the default minute step hides the seconds field), `utcToZonedLocal` includes seconds when non-zero, `zonedLocalToUTC` accepts seconds and a fraction, and `formatDateTime` shows seconds when the value has them.
- `geo`: stores a GeoJSON geometry dict (WGS84, `[lon, lat]`). Validated by `domain/geo.py` on every write, with or without restrictions; `bbox` with west > east crosses the antimeridian. CSV cells and the CLI read `"lat, lon"`, `POINT(lon lat)` or GeoJSON (`geo.parse_text`); exports write a plain point as `"lat, lon"` (`geo.to_text`). Mirrored by `frontend/src/utils/geo.ts` and `geoCoords.ts`. `parse_coordinates` also reads hemisphere letters and degrees/minutes/seconds (`56°07'12"N 3°24'36"W`); both implementations are tested against the same table of examples. A Point may carry `uncertainty_m` (a foreign member, validated) and a third coordinate (elevation, negative for depth). On the record form `GeoInput` gives guidance and an **Edit on map…** modal (`components/geo/GeoEditor.tsx`): OpenLayers in plain lat/lon with bundled coastlines (`world-atlas`) and a graticule, in a lazy chunk (`GeoMap.tsx`) so the main bundle doesn't carry it; the base (coastlines, graticule, tiles, view) is `components/geo/baseMap.createBaseMap`, shared with the explorer's results map (`RecordsMap.tsx`, clustered points, also lazy); an optional XYZ tile URL comes from `[map]` in `config.toml` (`GET/PATCH /settings/map`, `hooks/useMapSettings.ts`). The editor edits a draft (`utils/geoDraft.ts`) and changes nothing until Apply; file import (`utils/geoImport.ts`) reads GeoJSON, GPX, KML and WKT via OpenLayers' readers.
- `float` with a `unit` restriction: a field has exactly one unit and every stored value is in it. The service never converts; `domain/units.py` (mirrored by `frontend/src/utils/units.ts`) converts only at entry edges: `RecordService.coerce_value` (CLI) reads `"1024 ft"`, the record form's `UnitInput` does the same, and the CSV import asks each column's unit (`MapState.columnUnits`). Changing a field's unit is a relabel, never a conversion (the CLI asks for confirmation). Units outside the table are plain labels.
- `reference`: stores the UUID of another record as a string. The target schema is enforced via a `schema` restriction.
- `file_list`: stores a list of `FileRef` dicts.

On PostgreSQL, JSON columns use `JSONB` via `with_variant`.

**Text search matches values, never the stored JSON.** `domain/query.TextSearch` (a term and the field ids to look in) is what every search hands the repository: `RecordService.text_search(term, schema, field_names)` is the one rule for which fields (the kind's own live fields, or every schema's when none is listed, minus types whose `FieldTypeDescriptor.searchable` is false: reference, reference_list, boolean, geo; `UNSEARCHED_DTYPES`), and `record_repo.text_match` is the one predicate: a correlated EXISTS over `json_each` (SQLite) / `jsonb_each` + `jsonb_array_elements` (PostgreSQL) matching, case-insensitively with LIKE wildcards escaped, a top-level string or number, a list's string/number items, or the `filename` of a file or of each file in a list, or an id prefix of at least `ID_PREFIX_MIN` (4) hex digits (`prefix_span`, the primary key). It replaced `cast(data, String) ILIKE`, which matched field ids and file hashes (a two-letter hex search found every record) and, on PostgreSQL, a full-text `search_vector` match (words only; now used only to rank the jump-to box). The explorer, its count, `find_by_schema`/`count_by_schema_search` (reference pickers, `reachable_from`, the AI `query_records` tool), `search` (jump-to) and `iter_find` all go through it, one statement whatever the size (`test_a_search_costs_the_same_however_many_records`). `RecordQuery.search_fields` (names, needs `schema`, refused for an unknown, inherited or unsearchable field; `RecordQuery.for_kind` drops them when a query is rerun for another kind) narrows it: `search_field` on `GET /records` and every list endpoint (`query_params.record_query`), `search_fields` on move and file-access bodies, `civex record find --search/-q --search-field`, the explorer's **In all fields / In <field>** select (`qin` in the address, `useExplorer.searchFields`, read from the field-type descriptors). No index serves a substring match; a trigram index over the values (PostgreSQL `pg_trgm`) would. `tests/services/test_record_search.py`; `tests/db/test_postgres_search.py` on PostgreSQL.

Schema inheritance is resolved recursively by `SchemaService.collect_fields()` — parent fields are appended after own fields and labelled with their source schema.

### Collection scope

A collection (`datasets` table) carries a `scope` (`local` | `global`, `domain/scopes.py`), managed by `DatasetService`. **A collection holds records of every schema**: there is no per-collection schema list (the `dataset_schemas` table was dropped by migration `b3c7d1e9f5a2`; `civex collection ... --schema` and `add-schema` are gone), so a schema made after a collection can be used in it at once, and nothing about which schemas a collection takes is stored, synced or checked. The exports offered on a collection (`GET /file-access/definitions?collection=`) are those saved with a schema the collection has records of.

- `RecordService.add`/`update` check every `reference`/`reference_list` value (`_check_references`): the target must be a live record in the same collection or in a `global` one. Values equal to the stored ones are skipped on update. Schema-level reference restrictions are *not* checked against collections — schemas are global and can't know their collection.
- A `global` collection that other collections' records reference can't be made `local` or deleted (`RecordService.collection_referrers`).
- `find_by_schema(..., reachable_from=<collection>)` / `GET /records?reachable_from=` is what reference pickers search; `RecordDTO.dataset_name` and `reference_collections` (set in `_attach_reference_labels`) drive the "from collection X" marker in the UI.
- **Moving records** (`RecordService.plan_move`/`move`, the one rule behind `POST /records/move/plan|move`, `civex record move|move-all` and the explorer's **Move to…** (`MoveRecordsDialog`, SelectionBar `actions`)): re-points the chosen records (ids, or everything a `RecordQuery` lists) and everything beneath them (`RecordRepository.move`: one UPDATE per chunk of the tree, the roots' `parent_record_id` set to the target) at another collection, or inside a record there. Ids, values and history are kept and files are not touched (stored by content). Refused whole (`RecordMovePlanDTO.problems`, 422) when a record outside the moved set references one inside it that it could no longer reach (`_move_reference_problems`), a uniqueness key is taken where it lands (`_move_unique_problems`), or the kind can't sit there (`_move_kind_problems`: a top-level kind under a record, a child kind without a parent of its kind). It asks `delete` permission on the source and `write_records` on the target. **History:** one `update` entry per record whose snapshots differ in `dataset_id` (and `parent_record_id` for a root), one op per tree (`_tree_actions`), one `move` batch (`HOWS`); `audit_diff.PLACEMENT_KEYS` makes `diff_entry` report them and `AuditService._name_place` labels them "Collection"/"Inside" with names. **The database holds a child to its parent's collection** (`fk_records_parent_same_dataset`, `DEFERRABLE INITIALLY DEFERRED` since migration `c4d8e2f6a9b3`, so a tree moves one statement at a time and is checked at commit); `ProjectRules.check` asks `dataset_mismatches` after a synced action. **Over sync** a move is one action: the authority takes or refuses it whole; `RecordService.placed_with_parent` makes a child's collection its parent's when the parent moved meanwhile (the settled state is sent back); a refused change that would have moved an existing record is put back (`sync_authority._moves`); a device holds an action whole (`SyncService._waits`: an entry to a thing with an unsent change here, or one that places a record (`_places`: a create, or a changed `PLACEMENT_KEYS`) at, above or beneath one), replays held changes after each feed page in the page's savepoint (`_replay_held`), and never commits a page that leaves a child in another collection than its parent (`placement_mismatches`; a page ending mid-tree waits for the next). `tests/sync/test_move_records.py`, and `civex.testing.invariants` moves records at random.

- **Bulk edit** (`RecordService.plan_bulk_edit`/`bulk_edit`, behind `POST /records/bulk-edit/plan|bulk-edit`, `civex record set field=value ... --id|--in` and the explorer's **Edit…** (`BulkEditDialog`, SelectionBar `actions`, gated on `write_records`)): sets (or, with None, clears) `{field name: value}` on the chosen records, the same selection a move takes (`_chosen_ids`: exactly ids, or everything a `RecordQuery` lists; `RecordSelectionRequest` / `api/records.selectionBody` on the wire). `_bulk_edit` is the one walk behind plan and apply: `write_records` asked for every collection first (`RecordRepository.collections_of`), records read `BULK_EDIT_PAGE` at a time, one resolver; each record merged by `_patched` (the "change only these fields" rule `patched_data`/`patch` also use) and held to `_checked_update` (the checks `update` runs, split out of it; `_write_update` saves, logs and triggers). ### Bundles (moving data between projects)

A **bundle** replaced `civex dump`/`restore`: `domain/bundle.py` (pure: the layout and shapes, `FORMAT`, `Manifest`, `RecordLine`, `file_refs`, `sort_schemas`, `member_name_problem`) and `services/bundle_service.py` (`BundleService`, `ctx.bundle_svc`: `plan_export`, `export`, `inspect`, `import_bundle`), behind `civex bundle export|show|import` (`cli/bundle.py`; `dump`/`restore` are hidden stubs that name the replacement), `GET /bundle[/plan]`, `POST /bundle/import` (`routers/bundle.py`, tag `bundle`, progress through `report_progress`) and the Collections page's **Export bundle…** (`ExportBundleDialog`: the plan, an **Include the files** row with count and bytes) / **Import bundle…** (`api/bundle.ts`, `BundleDialogs.tsx`). A bundle is a zip: `bundle.json` (format, version, schemas parents-first in the dump's shape, collections, counts, `files.included/count/bytes/missing`), `records.jsonl` written a page at a time (`iter_find`; `{id, collection, schema, parent, data, created_at, updated_at}`, name-keyed data), `files/<sha256>` stored uncompressed (optional, `ExportOptions.include_files`; one on no reachable drive is listed in `files.missing`), `workflows/*.yaml`, `plugins/*.py`. `plan_export` and `export` are the same walk (`_walk`), so the preview can't disagree with the file. **Import** matches schemas by name (an existing one gains only missing fields; name templates and `filename_template` set after every field exists), collections by name, records by **id** (`RecordService.exists`; one here, live or deleted, is `records_existing`), and writes each record through `RecordService.add(record_id=, created_at=, updated_at=)` (→ `RecordRepository.create(id=, created_at=, updated_at=)`), so validation, references, uniqueness, history and sync all apply; a record waits (`waiting`/`blocker`) for a parent or referenced record that is later in the bundle, and one whose need never arrives, or that `add` refuses (a parent in another collection: CIVEX-168), is `skipped` with the reason (first `MAX_REPORTED` named, count exact). Files go through `FileService.store(path, collection_id)` from a temp file (placement and dedup apply) and a mismatching hash is `files_refused` and discarded; a cited file in neither the bundle nor the project is `files_missing` (the record still cites it). Workflows and plugins are written as files only if `member_name_problem` passes (no paths, dot-files or other kinds); the router then runs `discover_user_plugins`. The whole import is one `history_svc.batch("import", <file name>)`. Not carried: history, views, saved exports, settings. Tests: `tests/services/test_bundle_service.py` (a second project via `civex.testing.Projects`), `tests/cli/test_bundle.py`, `tests/server/test_bundle_router.py`.

### Releases (frozen, citable copies)

A **release** (`domain/release.py` pure: `check_name`, `check_metadata` (authors `{name, orcid?, affiliation?}`, ORCID checked and stripped of its URL; keywords), `CONTENT_FIELDS` vs `METADATA_FIELDS`, `hash_bundle`, `citation_text`/`bibtex`/`citation_cff`; `services/release_service.py`, `ctx.release_svc`; table `releases`, migration `d7a3e9c5b2f1`) is a small bundle of **records** (`BundleService.export`, records read `as_stored` so no drive is asked; `ExportOptions.query`/`record_ids` + ancestors) plus `release.json` and `CITATION.cff`. **Files are referenced, never copied**: a release is a third owner in `file_references` (`release_id`; `ck_file_references_one_owner`, `uq_file_refs_release_sha`), so GC (`copies_in_use`/`referenced_subset`), "used by" (`FileInfo.releases`, `releases_using`), pointers, `volume_breakdowns` and `surplus_by_volume` treat it like any owner with no special case. Making one is catalog-only: `release_repo.own_cited` is one INSERT…SELECT of the shas the scope's live records own, each pointing at the copy they point at (`test_owning_the_files_costs_the_same_however_many_there_are`, `test_making_a_release_asks_no_drive_where_a_file_is`). `ReleaseScope` is `{}` / `{collections}` / `{query}` / `{records}`. **Per-record hashes, one definition** (`rules.record_hash`): sha256 of canonical JSON of id, collection id, schema id, parent id and the stored values keyed by **field id** (only the live, stored fields of its kind, `stored_fields`: no formula; blanks dropped; `strip_derived`), so a rename or relabel changes no record. The bundle carries `structure.json` (`structure_of`: schemas with field ids, collections with ids) and `records.hashes` (sorted `<id> <hash> <collection id>`, `line_hashes` from the lines + structure), both written in `create` before hashing; no migration. **The content hash is over contents, never zip bytes**: `sha256:` of a versioned header (`HASH_VERSION` 2), `structure.json`, the sorted (id, record hash) pairs of the sidecar, the **sorted cited sha256s** (`HashResult.cited`; no file is read) and workflow/plugin members; `hash_bundle` recomputes it from the sidecar and reports a sidecar that doesn't match the lines; `release.json`/`CITATION.cff` are added after hashing. History position: `local_seq` (local only) and `feed_seq`; a device with unsent changes is refused ("sync first"). **What changed since is a comparison of the data, never history** (`ReleaseService.compare` → `Comparison`): the sidecar walked a page (`COMPARE_PAGE`) at a time beside the live rows as stored (`release_repo.stored_rows`, one query a page) → changed (hash differs, a move included) / removed (not live: deleted or purged) / unchanged, then the scope now in id order (`live_rows` keyset pages over the release's collection ids, the project, or the query/pick re-walked) merged with the sorted ids → added; disjoint counts per collection, `structure_changes` (schemas/fields by id: a rename is a change here, not a record change); kept in-process per (database, release) while `history_position()` is unchanged (`_COMPARED`); above `COMPARE_INLINE_MAX` (`ReleaseResponse.compare_in_background`) the UI runs it as a file job with progress (`releaseFlows.compareRelease`). `compared_records(kind, collection)` pages the ids (removed ones from `FrozenRecords`), `record_differences` is `audit_diff.diff_entry` of the frozen copy (names mapped back to the release's field ids) vs the stored record, rendered with `AuditChangeList`. **Never deleted**: `correct` changes only `METADATA_FIELDS`, `withdraw` sets `withdrawn_*` (keeps data), **`yank`** (irreversible) disowns every file and the bundle (`release_repo.disown`), sets `yanked_*` (and withdraws), leaving a tombstone that still cites; `plan_yank` counts by GC's own rule (`copies_in_use` before/after a disown inside `ctx.all_or_nothing()`, then rolled back). ### Object stores: drives or a bucket

Two protocols in `repositories/protocols.py`. **`ObjectStore`** is what every service that stores, reads or asks about a file sees (`put*`, `get`, `open`, `exists`, `size_of`, `delete`, where-is-it in volume terms: `copies`, `locate_volumes`, `copies_used`, `volume_status`, `volume_names`; GC's `iter_objects`/`reconcile_inventory`/`sweep_stale_scratch`/`gc_lock`/`verify`; and the direct-transfer trio `upload_target`/`complete_upload`/`download_url`). **`VolumeStore(ObjectStore)`** adds everything about a volume as a place (`object_path`, `path_on`, `volume_path`, transfers, locks) and only `StoreService`, the transfer engine and the folder-making parts of `FileAccessService` (which takes `volumes: VolumeStore | None` beside its store) need it. `context.make_store(config, session)` picks the store from the settings: `VolumeAwareFileObjectStore` (both protocols) for `[store.volumes]`, `S3ObjectStore` (`repositories/s3/store.py`; boto3 is a base dependency, imported only when a client is made) for `[store.s3]` (`S3Config`: `bucket`, `prefix`, `region`, `endpoint`, `profile`, `direct`; credentials never in config.toml). `AppContext.store_svc`/`transfer_svc` are properties that raise `FeatureUnavailableError(VOLUMES)` where there are no drives, and `FileService.local_path` is None there (routes then redirect or stream; `archive.build_download` streams). `Project.local` computes the features from the settings (`project.local_features`: a bucketed project loses `volumes` and gains `direct_files` unless `direct = false`), so `civex serve` on such a project hides the drive pages and answers 501 on their routes. **Which of the two** is changed only by `BucketService` (`services/bucket_service.py`, `ctx.bucket_svc`; `civex store bucket check|set|show|clear`, `/store/bucket` (`routers/bucket.py`), feature `store_admin`, which a host that decides where files go leaves out): `check` tries a bucket (list under the prefix, refusing one that already holds files, since a clean-up here would take them for unused; then write, read back, delete a probe), `use`/`stop_using` save `[store.s3]` through the config store, and `_blocked` is the one rule that a switch is allowed only while the place being left holds no files (`inventory.held`), since files are never moved between drives and a bucket (changing only the endpoint, region, profile or `direct` of the bucket in use is always allowed). `BucketStatus.left_on_drives` (files on drives while a bucket is set, e.g. a hand edit) is warned about by `civex doctor` and the app. UI: Settings → Storage is gated on `store_admin`; a bucket project sees `BucketStorage` there instead of the drive tabs, a drive project gets **Use a bucket…** on the Tasks tab (`BucketModal`, with **Check**).

**The bucket is one logical volume**, `S3_VOLUME` (`"s3"`), always online, keyed `<prefix>/<sha[:2]>/<sha[2:]>`, and the inventory is the same `stored_objects` table (`repositories/local/inventory.py` holds the writes and reads both stores share: `upsert_copies`, `forget_copy`, `copies`, `copies_used`, `unverified`, `mark_verified`, `remove_absent`, and `stored_files()`), so where a file is, how big it is and `exists` are answered from the database, never by listing the bucket (only a reconcile lists it, and `locate_volumes` asks the bucket for a bounded number of files the inventory doesn't know). `stored_objects.verified_at` (migration `b9d4e7f2a1c6`) says when a copy's bytes were checked against its hash: a drive store hashed everything it wrote (always set); a bucket object that arrived by presigned single PUT was checked by S3 (`x-amz-checksum-sha256`); one that arrived in parts, or that a reconcile found, is NULL until `ObjectStore.verify()` reads it back (run by `GCService.run`), which removes and reports one that doesn't match. **Direct files** (`features.DIRECT_FILES`, the same name as the sync capability `domain/sync.DIRECT_FILES`): `upload_target(sha, size)` is a `DirectUpload` (`domain/dtos.py`: one presigned PUT with the checksum header for files up to `SINGLE_PUT_MAX`, else a multipart `upload_id` and a presigned URL per `part_size` part), `complete_upload` checks the object is there at the announced size and records it, `download_url` presigns a GET (with `Content-Disposition` from `server/files.attachment`); the drive store answers None/raises. `GET /api/files/{sha}` answers 307 to it when the host has the feature (a HEAD is answered by civex, since the app checks before a download; `FileLink` fetches with `redirect: 'manual'` and takes an opaque redirect as yes), else serves from disk or streams. Browser uploads still go through `PUT /files/stream|batch` (hashed on the way in, then put in the bucket from a scratch file); a direct browser upload is not built yet. Tests stand a bucket in with `tests/fake_s3.py` (a boto3-shaped client with an HTTP front for its presigned URLs); `tests/services/test_s3_store.py` also checks against a real boto3 client that the target's headers are exactly what a presigned PUT signs.

### Storage volumes

`VolumeAwareFileObjectStore` (`repositories/local/file_store.py`) writes to the first usable volume in `store.volume_queue`. **The app says "drive", never "volume"** (Settings → Storage → **Drives**, **Add drive**, **Home drive**, **Empty a drive**): one word for a place files live, the same one the exports and the move dialog use; the code, the CLI and the server's own status messages keep "volume", where a volume and the physical disk it is on are told apart. A volume's whole definition lives in `config.toml` (`[store.volumes.<name>]`: `path`, `allocated_gb`, `id`, `state`); the DB holds only the blob inventory (`stored_objects`), never volume configuration.

- `volume_status(name)` is the **single** decision point for "can this volume be used?" — writes, stats, directory walks and inventory reconcile all go through it, and it returns a `VolumeStatus` (`domain/dtos.py`: `state`, `reason`, `fix`). `fix` is interface-neutral prose; the CLI adds the command and the UI a button.
- Identity: `VolumeConfig.id` + a `.civex-volume` marker in the volume root. Enforced only for volumes outside the project, and only once a volume has an `id` (assigned by `StoreService.add_volume`/`adopt_volume`, never during an upload, which must not rewrite `config.toml`). A mismatch is `wrong_drive`.
- Placement: `[store.placement.<collection-id>]` (`PlacementConfig`: `volume`, `on_unavailable` = `spill`|`fail`, `domain/placement.py`) names a collection's home volume. It is keyed by collection **id** and lives in config.toml with the volumes it names. `_write_candidates(collection_id)` is the single place that orders volumes for a new write (home first, then the queue unless `fail`); the hint is a `collection_id` argument on `put`/`put_path`/`put_stream` and `FileService`, supplied by the upload endpoints (`?collection=`), `WorkflowContext.store_file`, the import wizard and record forms (`hooks/uploadCollection.ts`). `StoreService.set_placement`/`clear_placement` manage it; `DatasetService` calls `on_purge` (wired in `context.py`) so a purged collection loses its placement.
- **Each record's file points at exactly one copy** (`file_references.volume`, migration `f7b3d9e2a6c4`; `domain/placement.py`: `Pointer`, `Scope`, `keeping`, `file_step`). `stored_objects` is keyed (`sha256`, `volume`), one row per copy (migration `c3f7a9e1d5b8`); a file may have copies on several drives, and each owner (record, live or deleted, or workflow run) points at one, so where a record's file is and what a drive holds for a collection is a fact, never a pick among copies. The pointer is local like the inventory (never in a record or a sync bundle) and is kept right in three places only: citing a file points at its newest copy (`models._sync_file_refs`; the one an upload just wrote or reused), recording a copy points the owners still waiting (NULL: not here yet, e.g. synced before downloaded) at it (`_upsert_inventory`), and removing a copy moves whatever pointed at it to the newest copy left, or NULL (`_unregister`); `rebuild()` keeps them. The migration points existing rows, per collection, at the drive holding most of its files. Locations come from the pointer (`store.copies_used(record_ids)` in `_attach_file_locations`; only an unpointed file is looked up by content via `locate_volumes`). `copies`, `_locate`, `copies_of` answer about copies; the record never says where (locations are per machine and don't sync). `_existing_copy()` is the one dedup rule for new writes: content already stored is reused, except that it is written again onto the collection's home when the home hasn't a copy (`writing_to`). A query asking whether a file is here or how big joins `inventory.stored_files()` (one row per file), never the table. `volume_breakdowns` counts a collection's files on the copies its live records point at (`shared_files`/`shared_bytes`: copies another collection's records point at too), `surplus_by_volume` gives per volume unused copies (nothing points at them: duplicates included), history-only, and `shared_*`; the volume page shows each collection's own bytes plus one **Shared by several collections** row so the rows add up. `delete(sha)` removes every reachable copy (an unplugged drive's stays, recorded), `delete(sha, volume)` one; free-up counts every copy's bytes (`SyncService._room_of`). **Moving repoints**: `transfer_engine.plan_steps` + `placement.file_step` is the one rule behind a transfer's preview (`TransferService._size_steps`), the move dialog (`FileAccessService.plan_move`/`shas_to_move`, `MovePlan.repointed`/`freed_bytes`) and the engine. A move covers some pointers (`scope_of(spec)`: a drive being emptied, a collection's live records, or `TransferSpec.record_ids`, the picked records); those point at the target; the file is copied there unless a copy is there already (then nothing is copied: de-duplication, `Step.there`); the copy it came from stays while owners the move doesn't cover point at it (`keep_source`, "copied, not moved") and any copy left with nothing pointing at it is removed, checked with `pointing_at` in the same transaction as the repoint (`_Run.flush`). Clean-up judges each copy (`FileReferenceRepository.copies_in_use`): a duplicate nothing points at is reclaimable; every copy of a file is kept when an owner has no pointer yet, a workflow run uses it, or none of the pointed-at copies is recorded. Homes only steer where new files go. There is no `include_shared` on transfers any more (old saved specs are read with `_known`).
- Picking a location: `StoreService.inspect_path()` is the single rule set for "can this folder become a volume?" (`PathInspection`: `problems` block, `warnings` don't); `add_volume` enforces it, the Add-volume form previews it (`GET /store/inspect`), so they can't disagree. `browse_directory`/`create_folder` back the in-app folder browser (`GET /store/browse`; folders only), because a browser can't give a server-side path. A relative path is resolved against the project root and "inside the project" is the store's own `_inside_project` rule.
- Network drives are mounts the OS already made (`civex/fs_locations.py` detects them from `/proc/mounts`, macOS `mount`, Windows drive type; civex doesn't mount or hold credentials). Anything that touches a volume outside the project goes through `fs_locations.guarded()`: a time-limited call with at most one call per location outstanding: a caller that arrives while an earlier call is merely busy (younger than `FS_TIMEOUT`) shares its answer or waits its turn, and only a call already past the timeout counts as stuck, so a dead mount becomes `offline` ("not responding") instead of freezing a request, and a healthy-but-busy one doesn't, and `_locate` skips volumes that aren't answering so reads elsewhere aren't stalled.
- Where a file is stored is **response-only**. `RecordService._attach_file_locations` stamps `location` (`{volume, state, available, reason, fix}`; `reason`/`fix` are the volume's own words for why it can't be opened and what to do, blank when it can) on every `file`/`file_list` value, in one inventory lookup and one status check per volume for the whole batch (`store.locate_volumes`); it runs inside `_attach_reference_labels`, which every API read passes through, and **not** in `_with_names`, which audit snapshots also use, so a location is never frozen into the log. `_strip_derived_file_keys` (`DERIVED_FILE_KEYS`) removes `location`/`resolved_filename` on `add`/`update`, because the UI echoes values back. Details come from `FileInfoService` (`GET /files/{sha256}/info`, `civex store where`): every copy with its on-disk path, size, and what uses the file. `GET /files/{sha256}` answers 503 naming the volume when the content is recorded on one that isn't reachable (404 only when it is nowhere).
- Frontend: `hooks/useFileLocationDisplay.ts` is the one rule for when to show a location (always when unavailable; the volume once there are several; always with details in advanced mode); `FileLink` / `FileLocationChip` (`components/records/FileLocation.tsx`) are used everywhere a file is rendered, and `RecordStorageSummary` summarises a record. The chip is a click/keyboard popover for everyone (plain-words where/online/what to do, from the location's `reason`/`fix`; **More details** mounts `FileInfoPanel`, already open in advanced mode), and `FileLink` checks a download with a headers-only request first so a drive unplugged since page load says which drive instead of the browser's generic failure. Adding files from the browser goes in **batches**, never a request per file: `PUT /files/batch` (`routers/files.upload_batch`) takes one streamed body, a JSON line `[{name, size}]` then the files back to back, each stored through the same `FileService.store_stream` as `PUT /files/stream` (size known, so placement works; nothing spooled); a file that can't be stored ends the batch and the answer says which (`stopped`). `api/files.uploadBatch` sends a `Blob` of the `File`s, `fileBatches` is the one sizing rule (`BATCH_FILES`, `BATCH_BYTES`; a larger file alone), and `hooks/useFileUploads.ts` is the one way the UI adds files (overall bytes/speed/ETA naming the file going in, a "Saving…" phase, cancel via `AbortSignal`, a batch sent again once after a dropped connection, and `stopped` keeping what went in and offering the rest through `UploadStopped` in `components/records/UploadProgress.tsx`), used by `RecordFieldGrid`'s `FileControl` and `DynamicField`; the import wizard batches with the same call. Locally this is **adding** ("Adding file 3 of 317", **Stop**); "sending"/"uploading" is sync's word for the server.
- **Moving files between volumes** (`domain/transfers.py`, `services/transfer_engine.py`, `transfer_service.py`, `transfer_jobs.py`, `repositories/local/transfer_repo.py`; table `storage_transfers`). Two kinds: `drain` (empty source volumes) and `consolidate` (gather collections' files: their live records' pointers; a copy other records point at stays, so it is copied). The engine's per-file order is the whole safety argument and must not be reordered: copy to a scratch file on the target while hashing (must equal the recorded sha256), optional read-back, atomic rename, `record_moves` + commit, *then* remove from the source. A crash between any two steps leaves the file on the source, the target, or both. Resuming re-discovers work from what is physically on the source (`iter_volume_objects`), so no cursor is stored; progress counts only after a batch commit, and `CopyResult.reused` + an inventory check stops a leftover original being counted twice. Transfers copy only through `VolumeStore.transfer_object`; copies touching a volume outside the project run on a watched thread (`STALL_SECONDS`) because a blocked write to a dead mount can't be interrupted. `TransferService` owns planning (`plan` is the single rule set behind the preview and `create`), freezing drain sources read-only (`StoreService.set_volume_state`, which re-reads config.toml first, remembers the previous state in `frozen`, and restores it on finish/cancel), and interrupted detection (`_reap`: a record is dead only when its `updated_at` is stale **and** `transfer_lock_held()` is false — silence alone never is, since a read-back or slow drive goes quiet while alive). Pause/cancel are saved on the row (`control`) and noticed as progress is saved, so they work across processes (web UI controlling a CLI run and vice versa); `save()` deliberately never writes `control`. **Transfers queue and run one at a time**: `create`/`begin_resume` save a transfer as `queued`, and `TransferService.next_runnable()` is the single rule for what runs next (oldest queued, or one paused only for a drive that has since answered). `TransferWorker.drain()` (`transfer_worker.py`) runs them in turn and is hosted by whichever process is at hand: the CLI (`civex store move`/`transfers resume`/`transfers run`) runs it in the foreground with a live bar, and the server's `TransferJobs` (`jobs` singleton) runs it on one thread started at startup and when something is queued, holding the running transfer's latest progress in memory (`live_progress`, which the API reports in preference to the saved copy). The store's transfer lock (O_EXCL, PID-owned) keeps it to one runner across processes: a host that finds it held (`TransferBusy`) leaves the queue to the one running it. Pausing or cancelling a queued transfer settles it at once; pausing one waiting for a drive stops the waiting. A drain's sources are frozen when it starts and put back whenever it stops for good, pauses or fails. GC and a transfer take mutually exclusive lock files, each holding its owner's PID, so a lock whose process has died is free at once (a lock with no readable PID falls back to a one-hour mtime). A copy flushing to disk (`fsync`, one call that can't report progress) gets a size-scaled stall limit (`_CopyJob.stall_limit`). SQLite connections set `busy_timeout` (`db/engine.py`); WAL is deliberately not used (sidecar files break copying/moving the DB, and it is unreliable on network/WSL drives). `save_config` is atomic (temp file + `os.replace`) because transfers rewrite config.toml while requests read it. Frontend: Settings → Storage → Tasks (`TransfersTab`, `NewTransferModal`), polling `/store/transfers`.
- **A deleted record's files are outside every placement policy, not every safety one.** What a collection's files are, for the storage report and its gather suggestions (`volume_breakdowns`), collection moves (`shas_for_collections`, `collections_using`), sync's background download (`_not_here`, `files_by_collection`) and uploads (`referenced_shas`), is what its **live** records use; a restored record's files count again. Clean-up (`referenced_subset`) still keeps them and emptying a drive (drain works from the drive's contents) still moves them, so nothing Recently Deleted can bring back is lost. A file's own details (`usage`) list every user.
- A missing volume root is **never created on demand** unless the volume is a relative path inside the project (`_ensure_volume`); and reconcile skips unreachable volumes, so an unplugged drive never loses its inventory rows.

### Files by name and folder

Files are stored by hash, but people think in records. `FileAccessService` (`services/file_access_service.py`, `ctx.file_access_svc`) turns a **selection** (`domain/file_access.FileSelection`: a `RecordQuery`, or exactly `record_ids` for ticked rows, plus optional `fields` and a `base`) into a **plan**, then optionally an export. `civex files list|export`, `POST /file-access/plan|export|zip` and the explorer's **Export** menu (`components/files/FileAccessActions`) all go through it.

- **One path rule**, `domain/file_access.py` (pure): the names of the records above a file (`RecordDTO.natural_name`, so what the UI shows), then the file's `resolved_filename`. The record that holds the file is itself a folder, so many records each holding `table.txt` can't clash. Paths start below `base` (`query.within` by default); across several collections the collection name leads. `folder_segments` appends a short id only to siblings whose names clash (case-insensitively); `file_names_in_folder` tells apart same-named different files and drops identical repeats. Don't write a second path rule for a new surface.
- **Plan before action.** `plan()` makes nothing and says what is unreachable (`FilePlan.unavailable`, grouped by drive with the volume's own `reason`/`fix`, taken from the `location` that `_attach_file_locations` already stamps). `export()` raises `FilesUnavailableError` (the API answers 409 with the plan, the CLI prints it and exits 1) unless `allow_partial`; the UI plans first and only interrupts when something is out of reach. A partial folder carries `MISSING.txt`.
- **Never searches or walks.** Sources come from `VolumeStore.path_on(sha, volume)` (pure arithmetic from the inventory's volume), not `_locate`. Records come in pages (`stream_records`), ancestors one lookup per level (`RecordService.ancestor_trails`), ticked rows in one (`get_many`), file values in one pass over the schema resolver (`file_values`); `test_a_big_selection_costs_a_fixed_number_of_queries` holds it constant. Export works a folder at a time (one directory read of what an earlier export left, one mkdir) and re-export uses the `.civex-export.json` marker (path -> sha) instead of reading the tree back; no new indexes were needed (`records.id`, `ix_records_parent`, `stored_objects.sha256`).
- **Export: a folder to open, or copies on one drive. How a folder is made is never the person's choice.** `export_managed(selection, name, mode, volume)`: `link` makes the folder in `<volume>/_exports/<name>` (`_civex/exports/<name>` for a volume inside the project) on the drive holding most of the files' bytes (`FilePlan.link_volume`, `by_volume[0]`), with a **hard link** for every file that can be linked there (`_can_link`: one throwaway link per source drive, before anything is built, so drives on one disk link) and a **copy** of every other (another disk, exFAT/FAT32, a drive's link limit), after `_check_room` for those copies; so how files are spread over drives never stops a folder (there is no `files_scattered` any more), and a re-export turns a copy into a link once the file can be linked (`how_now`). **Linked files are read-only** (`civex/file_modes.make_read_only`, on the shared inode, so the stored copy too): a link *is* the stored file and an edit would break its hash. Anything in civex that removes or replaces a stored or exported file goes through `file_modes.remove`/`replace`, because Windows refuses to delete a read-only file. `LinksNotPossibleError` (409 `links_not_possible`, name kept for the API) now means only that the drive can't be written to (`_check_writable`). `copy` writes real copies on `volume` (project if none), wherever the files are, after `_check_room`. **There are no symlinks**: they dangle when a drive is unplugged and WSL's can't be followed or deleted from Windows. `_exports` is skipped by the volume scan (it reads only 2-hex shard folders).
- **Looking after exports.** A folder is ours if it has `.civex-export.json` (path -> {sha, how: hardlinked|copied, size}; also `civex_version`, `format` (the file's own layout, 2), `mode` and `updated` in Zulu time `YYYY-MM-DDTHH:MM:SSZ`); `export` refuses a folder with other files, re-export is incremental and prunes, and `list_exports()` reads only the folders directly inside the known roots and each marker (never the files), so no walk and no registry table. `remove_export` removes exactly the marker's files (a link, never its target; a path in the marker that leaves the folder is ignored), keeps anything the user added (and so the folder), and reports freed bytes (copies only). `civex files exports list|remove`, `GET /file-access/exports`, `POST /file-access/exports/remove`, the **Made** tab of the Exports page (`ExportsList`).
- **UI flow: flat, one dialog.** `FileAccessActions` is the **Export** menu (saved exports, **Export…**, Set up exports… and Manage exports… which *navigate* to the Exports page; there is no separate table-as-CSV item: a table is part of the one dialog). The explorer groups Columns and Export with the saved-views bar. ### History (audit log) and revert

`audit_log` rows hold, per `audit_diff.stored_form` (the one rule every writer follows), the thing whole for a create (`new_data`) or a delete (`old_data`, so what was lost can be shown), and for an edit or restore only what changed (`format` 2: `delta` = `{path: {before, after}}`, `path` an attribute or `data.<field id>`, a side left out where absent; `new_data` keeps just the thing's identity, `audit_diff.IDENTITY_KEYS`, so titles and the id-in-snapshot filters still work). Entries v1.2.0 and earlier wrote whole are converted after opening, never in a migration (`HistoryCompactionService`, run by the server's `history_jobs` thread or `civex history compact [--vacuum]`; each entry must read the same as a delta or it is kept whole, `format` 3; it walks the partial index `ix_audit_log_still_whole`, migration `a4d9e2c7f310`, so batches and the count touch only what is left: a 300k-entry v1.2.0 project opens in ~1 s and converts at ~2000 entries/s). `GET /audit/storage`, `POST /audit/storage/reclaim` (SQLite VACUUM), Settings → Database **History storage**, the status bar's *Tidying history*. `tests/db/test_upgrade_from_releases.py` opens real v1.1.4 and v1.2.0 databases (`tests/fixtures/upgrades/*.db.gz`, made by that release's code with `make_fixture.py`) and checks data, conversion and (from 1.2.0) replay; add one per release. **Read an entry only through `audit_diff.entry_snapshots(old_data, new_data, delta)`**, never the columns: `make_delta`/`apply_delta` are exact (`apply_delta(old, make_delta(old, new)) == new`, 1 vs 1.0 kept), and `tests/domain/test_audit_delta.py` plus `tests/services/test_audit_delta_entries.py` hold that a delta reads back as the same changes, revert, filters and search. Entries written before this (v1.2.0) are whole snapshots (`format` 1) and read the same way. The API serves `old_data`/`new_data` as `entry_snapshots` gives them, so a reader comparing the two sides sees only what changed. `tests/services/test_audit_replay.py` replays each thing's entries from its create in write order and must reach the database. `audit_log.local_seq` is the order entries were written, numbered by the database (sequence on PostgreSQL, trigger on SQLite; migration `e8b4f2c6a917`, which a batch rebuild of `audit_log` would drop), and is what changes are sent in (`sync_repo._WRITE_ORDER`), never wall-clock time or `rowid`. The entry's *diff* is never stored. `domain/audit_diff.py` (`diff_entry`) is the one place a diff is made, and `AuditService` (`services/audit_service.py`, `ctx.history_svc`; `ctx.audit_svc` is still the raw `LocalAuditRepository`, used by sync and `status`) is the one place it is served: every audit endpoint and `civex history` read through `page`/`get`, which attach `changes` (`AuditLogDTO.changes`, response-only, never in a sync bundle) with the field's current label/dtype and in schema order. Record snapshots are **field-id-keyed**, as the record is stored (`RecordService._snapshot`, no name conversion on write), for every action, so an entry means the same after a field is renamed; `AuditService._by_field_name` turns the ids into the field's *current* name when it builds `changes`, and an id that belongs to a deleted field stays an id (a live field may have taken its name) and is labelled by `_diff` (`Change.deleted`: `deleted` = restorable, with the schema to restore it on, or `gone`). The served `old_data`/`new_data` are the stored snapshot (ids); `changes` is the readable form. Entries from before this kept names and are read as they are. A collection's snapshot written before migration `b3c7d1e9f5a2` carries `schema_ids` and `schemas`, read as written and never compared to the collection. Entries also carry `actor` (the OS user, `civex/identity.py`, unverified). **History is complete, and a test says so**: `tests/services/test_audit_replay.py` runs every kind of change and checks that the last entry about each schema, field, collection, view and record equals the database (the one thing sync will send is these entries). Anything that changes one of those must write an entry for it, including a *side effect on another thing* (`SchemaService._rewrite_templates` logs each template it rewrites in other schemas/fields; `reorder_fields` logs each field that moved). A schema/collection delete or restore writes an entry for each record it stamped or brought back (`services/cascades`, in the same action and batch, so Activity shows one event). Deliberate non-entries: purging a schema takes its fields with it, and views are removed outright (their `delete` entry is the whole story). `DERIVED_FILE_KEYS` (`domain/dtos.py`) are ignored by the diff, so an echoed-back file isn't an edit. `scope_of(kind, ref)` resolves a record/schema (its own fields)/collection to the list scope, so routers and CLI share it.

Revert is record-only: `plan_revert` is the single rule set behind the UI preview (`GET /audit/{id}/revert`), `POST /audit/{id}/revert` and `civex history revert`, and `revert` applies it **only through `RecordService.update/delete/restore`**, so validation, reference checks, triggers and a fresh audit entry all happen (a revert is itself revertible). Per field: `apply` (still as the entry left it), `conflict` (edited since; only with `force`), `same`, `skipped` (field gone, or a file whose bytes were GC'd: history-only blobs aren't GC roots). Reverting an update sends the *whole* merged data, since `RecordRepository.update` replaces `data`. Schema/field/collection entries are readable but not revertible. Frontend: rows of `AuditTrail` open `AuditEntryDialog` (full `changes` via `AuditChangeList`, then a `RevertPanel` that shows the server's plan before confirming); `utils/recordAudit.tsx`, `schemaAudit.ts` and `collectionAudit.ts` now only supply titles. **Activity** (`/activity`, `ActivityPage`, sidebar *Activity*) is one list, `ActivityFeed`; there is no separate Recently Deleted page (`/trash` redirects to Activity with **Deleted** on). The same `ActivityFeed` is a record's History tab (scoped `under` that record) and a collection's Activity tab (scoped `collection`); a schema's History stays `AuditTrail`. **Deleted** is a toggle on the feed: it adds `now = deleted` and `change = delete` to the filter (`utils/auditFilter.ts` `toggleDeleted`), so what is waiting to be restored is just history narrowed, and an item's row has **Restore** (the `RestoreDialog`) and its dialog **Delete permanently**. *A delete is not all-or-nothing.* `RecordService.restore(id, only_this=, with_parents=)`: by default a record comes back with what was deleted with it (`_restore_group`) and is refused while a deleted record is above it; `only_this` leaves its children deleted, `with_parents` brings back the deleted records above it (`_deleted_above`, each by itself, no sibling expansion) so one selection can return without the other 59. `restore_plan().parents_needed` says how many parents that is. `restore_records(ids, with_parents=True)` (`POST /records/restore-selected`) restores *exactly* the chosen records plus the parents they need, in one pass (`_restore_blockers`, fixed-point so a record whose parent is itself held back stays); the bulk-delete window (`BatchDialog`) ticks records and calls it. The set-level planners (`plan_restore_set`/`restore_set`/`restore_records`) look everything up together: per-record `restore_plan` was ~18 queries each, which made "Restore everything" on a 70-child delete a thousand-query spinner (`test_describing_and_undoing_a_bulk_delete_costs_the_same_however_big_it_is` holds it constant). A bulk delete's one line has its own **Restore** (with **Choose which…**, and **Restore everything…** in its window): `RestoreBatchDialog` calls the same restore-all with `batch=<batch id>` (`AuditService.plan_restore_all`/`restore_all(batch_id=)` → `AuditFilter.batch_id`), so a record and everything beneath it comes back parent-first as one `restore` event. With it on, **Restore all N** restores everything the filter matches: `AuditService.plan_restore_all`/`restore_all` (`GET`/`POST /audit/restore-all`) take the same filter, add the two conditions server-side, restore collections, then schemas, then records in rounds (a record under another in the set comes back with it, or once it has; one still under a deleted thing outside the set is *blocked* and reported), as one `restore` batch.

*History is filtered like records and runs, with their machinery, not its own.* `domain/audit_filters.py` declares `AUDIT_FIELDS` (`when`, `kind`, `change`, `how`, `collection`, `schema`, `under`, `now`) once, as `run_filters.py` does, and `parse_audit_filter` checks a `domain/filters.py` tree against them; `GET /audit/filter-fields` serves them, `GET /audit/events?filter=&q=&sort=` takes the tree, and the UI is the explorer's `FilterControls` over `runFilterFields` (`utils/auditFilter.ts`), with the page's own scope AND-ed in (`withScope`) and not shown as a chip. `AuditFilter` (`domain/audit_filter.py`, like `RecordQuery`) carries the fixed scopes plus `where`; `AuditService._resolve` turns what a person picks into what the repo tests (a collection or schema *name* becomes its id so a rename can't lose history, and `schema` matches the schema's own entries plus any snapshot whose `schema_id` is it, i.e. its fields, views and records of exactly that type; `under` becomes the record and everything beneath it, live or deleted) and `audit_repo._condition` maps each field to SQL (`under`/`collection` also match snapshots that *name* the id, which is how a purged child is still found). `now` (live | deleted | gone) is answered from the records table; `AuditLogDTO.now` / `AuditService._where_now` say it on each single entry, one lookup per page, so a lost record can be told from an edited, deleted or purged one.

*Bulk operations are one event.* `audit_batches` + `audit_log.batch_id` (migration `f2a6c8d1e093`; local only, not in a sync bundle). `LocalAuditRepository.batch(kind, label, ref)` creates the batch lazily at the first write inside it and joins an enclosing one, so a workflow run that deletes a tree is the run's one event. The server opens batches for record delete/restore/purge of more than one record (`_audit_batch`) and for each workflow run (`background.run_pending_jobs`, `cli.utils.run_job`); the browser import opens one with `POST /audit/batches` and sends `X-Civex-Batch` on each request (`get_ctx` joins it; an unknown id is ignored). `list_events` groups by `coalesce(batch_id, id)`; a batch reports `parts` (counts by kind and action), its entries are paged at `/audit/batches/{id}/entries`. A collection or schema delete is still one entry, since its records are stamped by the cascade, not logged. A bulk **edit** is undone whole by `AuditService.revert_batch(batch_id, force, dry_run=True)` (`GET|POST /audit/batches/{id}/revert`, `civex history undo-edit [id|--last]`, **Undo** on the batch's Activity line and in `BatchDialog`, `UndoEditDialog`): no rule of its own, it runs each entry, newest first, through `plan_revert` and the same `_apply_revert` as `revert`, in one new `edit` batch; an entry `plan_revert` blocks (record deleted since), or whose fields were all edited since without `force`, or whose old value is now refused, is `left` with its reason. Only `REVERTIBLE_BATCHES` (`edit`) are; other batches are reverted an entry at a time, and a bulk delete has Restore. Cost is a single revert's per entry (not set-level).

*Where a thing is now.* `now` is live | deleted | gone for a record, a collection or a schema (`audit_repo._now_is`, answered from those tables, and `AuditService._where_now` on each single entry with `ref`, the id or name to restore it by). **Permanently deleting a record deletes every audit entry about it and leaves one tombstone**: `RecordService.purge`/`purge_records` call `forget_records` (all its entries, then any batch left empty) and log one `purge` entry whose snapshot is `audit_diff.tombstone` (id, collection, schema, parent, created/deleted times, `"tombstone": true`, no `data`), so nothing it held survives in history and `now` is *gone*. A collection or schema purge deletes its records' entries (`forget_records_matching` on `"dataset_id"`/`"schema_id"` in the snapshot) and its own `purge` entry is the tombstone. Records purged before this are cleaned by `RetentionService.forget_purged` (`POST /retention/purged-history`, `civex retention forget-purged`, shown on Settings → Retention only while any remain), which keeps or makes one tombstone each. `civex trash list` is history filtered to deleted, in the CLI.

*Records out of sight (orphans).* A live record under a deleted record is listed by nothing above it and refused by a sync server; today's edits can't make one (a single restore under a deleted parent is refused), but history can (a record restored by itself before that rule, a cascade applied before cascades synced). `RecordService.deleted_above(id)` (the deleted records directly above a live one, topmost first), `restore_above(id)` (the one way to put one back in place: those records each by itself, so their other children stay deleted; checked, logged and synced like any restore) and `orphans(limit)` (`RecordRepository.live_under_deleted`). Surfaces: `RecordResponse.deleted_above` on a single fetch and the record page's `OrphanBanner` (**Restore …** / **Delete this …**); `GET /records/orphans`, `POST /records/{id}/restore-above`; Settings → Database **Records under a deleted record** (`OrphansCard`, shown only when there are any); `civex doctor` (counts them as an integrity issue), `civex record orphans|restore-above`. A refused record that sits under deleted records here offers the take `restore_above` (`SyncConflictDTO.sits_under`, added by `SyncService._describe`/`_sits_under`): it restores them and resends, and the server's resulting edit-vs-delete answer is not raised as a new item (it is what was asked for).

### Sync (CIVEX-305; star topology, one authority per project)

A project follows an **authority** (a normal `civex serve` with `[sync] serve = true`); devices send their `audit_log` entries and receive the authority's numbered feed. Pieces: `domain/merge.py` (pure three-way field-level merge: base = `entry.old_data`, `data` merged per field id, lifecycle/derived keys excluded), `domain/hlc.py`, `domain/sync.py` (wire types, `PROTOCOL_MIN`/`PROTOCOL_MAX`, `WIRE_FIELDS`, `SyncError.status`), `SyncAuthorityService` (who is calling comes from an `Authenticator`, `DeviceKeys` here, see **Who and what may**; `push` merges/numbers/answers, the `sync_ops` ledger answers a repeat with the stored result, DEFERRED ops (a cited file is missing) aren't stored and stop the batch), `SyncService` (client: `connect` = join/seed/empty/resumed, `sync`, lazy pull, conflicts), `SyncApplier` (applies entries by whole snapshot, so applying twice is harmless), `LocalSyncRepository`, `HttpSyncTransport` (urllib), `routers/sync_peer.py` (`/api/sync/v1/*`: hello, push, feed, snapshot/{kind}, files/missing, PUT/GET files/{sha}; 404 unless serving, then protocol and session checked; `join` and `session` take no session), CLI `civex sync ...` / `civex clone`. Tables: `sync_meta`, `sync_ops`, `sync_devices`, `sync_conflicts` (migrations `c9e1f4a7b3d2`, `d6c2a8f41b07` for a conflict's base and who wrote the value that stayed).

- **Conflict policy:** the authority's value stays; the loser is kept in `sync_conflicts` **on the device whose change did not go in** (the authority keeps no list: its answer to a push carries each clash, `OpResult.conflicts`, and `SyncService._note` is the one writer of the rows, for clashes and refusals alike); edit-vs-delete keeps the record; schema changes are serialised by the authority.
- **What the authority accepts:** `domain/sync.problem_with` is the one shape check for a change (kind, action, snapshots are objects, readable time, a valid `hlc`; a delete stamped more than an hour ahead is refused): one odd change is `rejected` by itself, never failing the push (`_settle` also turns `ValueError`/`TypeError`/`KeyError` from a snapshot into a refusal). A stamp that can't be parsed would make every later `hlc.tick` fail, so `hlc.is_valid` gates it and one far ahead is replaced by one the authority issues. A record is held to what a person's edit is by `RecordService.check_incoming` (restrictions, references, unique keys, parent), called by `SyncAuthorityService._take` before the write; writing the state stays `SyncRepository.apply_snapshot` (id-keyed and exact, no defaults, history or triggers) and a device does not re-validate what the authority settled. Not yet checked: schema, field, collection and view changes.
- **Reviewing conflicts** (`SyncService`): `conflicts()` returns `SyncConflictDTO`s described by `_describe` (record name, collection, schema, field label, the value now, `stale`, `takes`, `also_saved`; worked out on read from `RecordService.field_values`, never stored). `resolve_conflict(id, take, value, force)`: `theirs` (nothing to do), `mine`/`value` (`RecordService.patch`, so it is checked, in the history and syncs; refuses with `ConflictMovedError`, API 409 `conflict_moved`, when the value is no longer the one that stayed unless `force`), `delete`, `retry` (`_resend` logs a fresh entry from the thing as it is, on the refused entry's starting point). `_takes_for` is the only rule for what a row offers; the UI reads `takes`. `RecordService.patched_data` is the one "change only these fields" rule (plugin `patch_record` uses it). `resolve_many(take, ids=, kind=, entity_id=, force=, dry_run=)` is the one bulk rule (`POST /remote/conflicts/resolve-many`, `civex sync resolve --all`): it reads `find_open_conflicts` (no page limit, unlike `conflicts()`, which stops at 200), leaves a row that doesn't offer the take (`not_offered`) or fails its checks (`failed`) open, and for `theirs`, which is bookkeeping, is one statement and one commit; `dry_run` only counts. `reopen_conflicts` (`POST /remote/conflicts/reopen`) takes back only `theirs`, since the other takes made edits that are undone from Activity. A refused change or an edit that met a delete carries `attempted` (create/update/delete) and `changes` (`_attempt`: each field it set with before, after and the value now), response-only like the rest of `_describe`, so a screen shows the attempt where the record already is; `edited` is accepted for a clash (not in `takes`, so no button) and closes it once the person has set the field themselves. History carries the same facts: `AuditLogDTO.sync` (response-only, from `SyncService.conflicts_of_entries`, injected into `AuditService` as the `sync_conflicts` callable so history doesn't know sync; one `conflicts_of_ops` lookup per page in `_with_changes`) lists what became of each change that did not go in as made, open or settled, and a delete that met an edit lists the record as it was and as it is now (`_attempt`, `_NOW`). `GET /remote/conflicts?record=` narrows to one record. Frontend: **the record page is the one place a conflict is settled.** `components/sync/MergeView` is a Resolve tab on `RecordDetailPage` (shown while the record has open conflicts, and while rows settled this visit are still on screen): rows from `utils/syncMerge.buildMerge` (clashes together; each refused change or edit-vs-delete its own block with `describeAttempt`'s sentence and its takes), other side left, the field's own `EditableValue` (exported from `RecordFieldGrid`, so every dtype and restriction is the usual input) in the middle, this device's right, differences marked by `DiffValue` (`utils/textDiff`: word LCS, item sets for lists, whole-cell otherwise); saving the middle by hand sends `edited`; `useMergeConflicts` reads open ones plus those settled since the page opened (`status=all&record=`). `ReviewStepper` wraps every record page of a review (`utils/reviewSession`, sessionStorage: the ordered records, ticked when nothing is left) and starts when the Resolve tab opens or **Start review** is pressed. `RecordConflicts` is only the Fields-tab banner with a way in, and the grid marks clashed fields (`marked`, `layoutConflicts`). `pages/SyncReviewPage` (`/sync/review`) is the inbox only: a list with a **Resolve** link per record, `?kind=` filter, ticked-row bulk, **Keep theirs for all/these** (the filter, not the loaded ids, after a dry-run count, with **Undo**); a row with no record page (a schema's refused change, a deleted record) settles in the row. Activity: `SyncBadge` on a row and `SyncOutcome` in `AuditEntryDialog` show the same left/right. A sync failure is **not** toasted (`utils/syncToast`): the status bar (`useSyncTasks`) holds failures and values to review with their actions, and a toast is only good news that passes. `hooks/useRemote.ts`. When the settled state differs from what was sent, the authority emits a "settled" entry (actor `sync`) and flags the op entry `superseded`.
- **`audit_log.apply_state`** is `applied`, `held` (an authority change kept but not applied because this device has an unsent change to that thing) or `superseded` (never applied). `_catch_up` applies the *latest state-carrying* entry per free thing, then a trailing delete/purge; applying an older entry over a newer would roll the thing back (the randomized convergence test, `tests/sync/test_convergence.py`, exists for exactly this; `CIVEX_SYNC_SEEDS=300` runs more seeds).
- **Files straight to and from storage** (capability `direct_files`, `domain/sync.DIRECT_FILES`, offered in `Hello.capabilities` when the authority's host has the feature of that name: `context.py` passes `SyncAuthorityService(capabilities=)`). `POST /files/{sha}/upload` `{size}` answers a `DirectUpload` target (204 when the authority has the file; 501 where it isn't offered), the device PUTs the bytes to the presigned URL(s) itself (`HttpSyncTransport._upload_direct`, after `hello` said so; one PUT with the checksum header, or a part per `part_size` collecting ETags), then `POST /files/{sha}/complete` `{size, upload_id, parts}` records it; `GET /files/{sha}` answers 307 to a presigned GET, which the transport follows **without** the session token (`_open(follow=False)` + `_open_storage`: a token must never go to another host, and S3 refuses two kinds of auth). Not a protocol change: an authority without it streams as before (`PUT /files/{sha}`), and a device talking to one falls back on a 501. `tests/sync/test_direct_files.py` runs both ways over a socket with `tests/fake_s3.py`.
- **Files and data converge separately, and files are not part of a sync.** `SyncService.sync` (and the first copy, `_seed`) moves records only; files go on a loop of their own (`SyncWorker.files_tick`, on its own thread beside the sync loop in `run`, progress to `on_files`, served apart as `GET /remote`'s `files_progress`): first `send_files` (what the authority lacks, `FILES_SECONDS` a tick, stopping between files; `SyncWorker._SendRun` adds earlier passes' files, bytes and speed to each pass's progress, so the bar runs from first file to last instead of restarting each pass), then `fetch_files`. So a gigabyte of files never holds up a change, and an empty authority has the whole project in moments. A change is never held for a file: the authority takes a change citing a file it lacks (it does not defer), and the device uploads what it can read. Nothing about files owed is stored: `SyncService.send_files` works it out each time from the `file_references` catalog (`LocalSyncRepository.referenced_shas`) and the authority's `missing_files` answer, so a drive plugged back in or files added later are just found. What *is* stored is what the authority confirmed it holds (`server_files`, migration `a7c3e9f1b5d2`; `confirm_on_server` when it answers that it has a file, takes an upload, or a device downloads one from it; cleared by `forget_numbers`): every pass asks only about unconfirmed files (`referenced_shas(unconfirmed=True)`, no request when there are none), and every `FILE_CHECK_EVERY` (10 min), on **Send now** (`POST /remote/files/send`, `sync_jobs.send_now`) and on a manual sync it asks about all of them again (`everything`). `_send_files` is the one way files go up (from `send_files`; `civex sync send` in the foreground, and `civex sync now` only says how many are still to go), reporting `SyncProgress` phase `SENDING` with bytes and `bytes_total` (sizes from the inventory, one lookup; `_Counting` wraps the open file; `SyncTransport.upload_file(sha, source, size)` takes an `UploadSource`). The same table answers "not on the server yet": `location.sent` on a file value (true/false while the project follows an authority, absent otherwise; `RecordService.not_on_server`, injected from `SyncService.not_on_server`), shown by `FileLocationChip`. What the authority answered it *lacks* is kept too (`server_lacks`, migration `d2f6a9c4e8b1`; `note_server_lacks` from `_send_files`' `missing_files` answer and from a download that found nothing; removed by `confirm_on_server`, cleared by `forget_numbers`), because "unconfirmed" alone doesn't mean the server lacks it (nothing is asked right after joining): a file on no drive here that the server said it lacks is **missing** (`location.state: absent`, with `not_here_reasons`: `domain/sync.not_on_server_yet`, which names the *device* that added it, never a person), anything else not here is `remote`. `SyncService.files_waiting` (`ready`, `offline` by drive with the drive's own reason, `missing`) and `SyncStatus.files_to_send` (= ready + offline: only what a copy here can send) feed a status-bar source of their own (`hooks/tasks/useServerFilesTasks`, not the sync's): files to send with **Send now** only when some can go, and missing files as a separate task, each linking to the all-collections files list (`ALL_FILES`). The files list (`FileAccessService.listing`/`chosen`) takes `server` (`sent` | `unsent`, `domain/file_access.server_state`; a missing file is neither) and answers `server` counts; `FilesView` shows them as chips beside the places, marks a row not sent, and shows files going up live (`files_progress`, polled every second while it is set) with **Send now**. Don't reintroduce holding changes for files (a lost file is permanent and would block a record forever) or a persisted owed list. **A device fetches the files others added** (`SyncService.fetch_files`/`fetch_file`, the one rule; what is missing is worked out each time from `file_references` with no `stored_objects` row, `sync_repo.files_not_here`, never stored): in the background when `[sync] download_files` is `all` (the default; `SyncWorker._fetch_files`, `FILES_SECONDS` a tick, files the authority lacks skipped until the next file check, progress phase `files`), when opened (`GET /files/{sha}` fetches before answering, 503 if the authority can't be reached, 404 if it hasn't got the file either), and before an export (`FileAccessService.plan(fetch=True)`, used by every export/zip/download/gather path but not the preview; `fetch_missing` is injected in `context.py` so file access doesn't know sync). Downloads go through the store's `put_path` with the file's collection, so placement and dedup apply. Meanwhile its `location` is `state: remote` (`RecordService.files_from_server`). **Per collection** (`SyncService.collection_mode`, the one rule): a collection keeps its files here (`keep`) or fetches them when opened (`opened`), from `[sync.collection_files]` in config.toml (keyed by collection id), else the project's `download_files`. The background download and `files_to_fetch` cover only kept collections (`_kept_collections`); a file asked for by hash (opened, exported) comes whatever its setting. `collection_files()` is the report (here: files and bytes; only on the server: files, since a file not here has no recorded size; `sync_repo.files_by_collection`, one grouped catalog query). **Freeing space** (`free_up(collection, dry_run=True)`) removes this computer's copies only of files the server confirms it holds, asked at that moment (`missing_files`), never one a kept collection also uses (`used_by`), under the store's `gc_lock` (so not alongside a clean-up or file move), and sets the collection to `opened` first so the background download doesn't refetch them. `civex sync files [all|opened]` (table), `civex sync keep <c> [--opened|--reset]`, `civex sync free <c>`, `civex sync fetch`; `GET /remote/files`, `PATCH /remote/files/{c}`, `POST /remote/files/{c}/free-up?dry_run=`; Settings → Storage → Collections (`ComputerFiles`: `ComputerFilesDefault`, `ComputerFilesCell`, `FreeUpDialog` counting first). An authority fetches from nobody.
- **Deletes** use one stamp for both the entry timestamp and `deleted_at`, so every device stamps identically; deletes/restores don't bump `updated_at`.
- **What the authority answers is already saved, and it takes one push at a time.** The peer routes take `get_ctx` with `Depends(..., scope="function")`, so the commit runs *before* the response (with the default it runs after, and a failed commit would still have told a device "done", which then never resends; `test_peer_api`). `push` starts with `SyncRepository.lock_feed()` (a no-op write on `sync_meta`: a row lock on PostgreSQL, the write lock on SQLite) so two pushes can't merge with the same state and overwrite each other, and `_write_entries` numbers the authority's own unnumbered edits (`sequence_local_entries`) right before a pushed change, since one saved while the push merged is already inside it. The other 160 `Depends(get_ctx)` in the app still commit after answering.
- **Changes travel as deltas, and a device replays them.** A pushed edit carries `SyncEntry.delta` (identity in `new_data`); the authority rebuilds both sides on what it holds (`sync_authority._sides`: untouched values are equal on all three sides of `merge`; an edit's result is not deleted unless it says so, so edit-vs-delete keeps the thing), so an edit to another field than a concurrent one now goes in `applied`, not `merged`. The entry the authority writes after a clash, merge or refused delete (actor `sync`) stays **whole**: the device whose change lost holds values nobody else does, which a delta from the authority's state would leave. A device applies the authority's numbered, non-superseded entries for a thing **in order** (`SyncService._replay`, from `SyncRepository.numbered_entries`; `SyncApplier.apply_entry` puts a delta onto the thing as it is here): on arrival from that entry on (re-taking its own later-numbered changes, harmless), and in `_catch_up` from the first held one. That one rule replaced `has_newer_state`/`_reapply_later_delete`/pick-the-last-state; `CIVEX_SYNC_SEEDS=300` passes.
- **What a project must still be, whatever made the change (cross-kind rules).** The authority holds a change from a device to what a single machine enforces on an edit, about what it touched *after* writing it: `services/project_rules.ProjectRules` (naming and file-name templates use only fields that exist; unique keys name the schema's own live fields and no live records share one). A create is not asked (`_changed`: an empty authority is filled schemas-before-fields). `RecordService.check_incoming` also refuses a live record inside something deleted (its schema, its collection, the record above it): an edit that meets a delete keeps the record itself, never revives it into a deleted container. **One action, taken whole:** entries one action writes share `audit_log.op_id` (migration `f1c3a5e7b902`; `AuditRepository.operation()`, `SchemaService._one_action` on add/update/delete/restore field and reorder, one per tree in record deletes and restores (`_tree_actions`, restores logged parents first), schema/collection delete/restore with their records); `SyncEntry.op`; `pending_entries` and `_at_most` never split one; `SyncAuthorityService._settle_action` settles the run in one savepoint and asks the rules once at the end. An action that can't go in whole: a record-tree delete that met an edit keeps the whole tree (edit-vs-delete for each, `_keep_instead_of_delete`); anything else is answered `not_taken` for what exists here (`_put_back`: the authority's state is sent back, so the device converges instead of sitting half way; a person redoes it) and `rejected` for what doesn't. A refused single change to a schema, field, collection or view is `not_taken` too (records keep `rejected`, with Retry/Use mine). A record whose create was refused (a value its field no longer allows there) can't be edited on the authority, so while it was never taken (`SyncRepository.never_taken`) the edits made to it since go as one create of it as it is now (`SyncService._send_whole`; the others are `mark_folded`): fixing it is what sends it. A thing has at most one open refusal: refused again, the open item is renewed in place (`renew_refusal`, newer reason and change), and going in settles it as `sent` (`_note`). **Send again** (`retry`) does not settle anything: it marks the item `retrying` (still open) and asks for a sync (app: `sync_jobs.sync_now`, CLI: syncs at once), and the answer settles it. A refusal names the field it is about when it was a value (`FieldValueError.path` → the authority's `OpResult.conflicts` → `SyncConflict.field`), and the Resolve tab shows a refused record as `RefusedFix` (the reason, that field editable with what it allows; no sides), not as a diff. Following another authority clears the old one's numbers (`forget_numbers`). Retry of part of an action resends the whole action (`_resend`). **Cascades are entries:** a schema's or collection's delete or restore logs an entry per record it changed, in its action and batch (`services/cascades`); when the authority applies one from a device it writes an entry for each record it changed here that the action didn't cover (`_write_cascade`, actor `sync`); a delete applied to an already-deleted record takes the entry's stamp (`sync_repo.soft_delete`). Without these each copy worked out cascades from what it held and copies disagreed. A schema's or collection's restore brings a record back only where it could be added: not under a parent still deleted (`record_repo.parent_allows_restore`, used by both repositories and so by sync, whose `restore` delegates to them); `check_incoming` asks the parent of a record being made or brought back (not of a plain edit: a record left live under a deleted parent by deleting a parent schema stays editable, as on one machine). A record delete that meets a live record added beneath it on the server keeps the record (`_added_beneath`, edit-vs-delete). An edit that goes in without clashing takes its `updated_at` on the authority even when all its values were already there, since every copy applies the date with it. `tests/sync/test_invariants.py` (random structural and record changes on three devices; every rule above must hold on the authority and copies must agree, except what has an open review item on that device) and `test_cross_kind.py` (the cases one by one) hold all of this.

### Uniqueness policies

`schemas.unique_keys` (migration `a3d8f0b6c125`) is a JSON list of keys, each a list of the schema's **own** field ids (a child record stores only its own fields), so a rename costs nothing. `SchemaDTO.unique_keys` holds ids and `unique_key_names` the names (what the API, CLI and bundle speak). `domain/uniqueness.py` is the pure rule (which dtypes can be in a key: `UNIQUE_DTYPES`, scalars only; a blank in any field means the record isn't constrained). `SchemaService.set_unique_keys` is the one place a policy is defined: it validates, dedupes (same fields in any order = one key) and refuses while existing live records already share a key (`RecordRepository.key_duplicates`); `delete_field` drops keys using the field. Scope is **same dataset, same parent record** (top level: parent NULL), live records of exactly that schema.

`RecordService._check_unique` is the single enforcement point, called from `add` and `update` (a key whose values equal the stored ones is skipped, so an old duplicate never blocks an unrelated edit) and raises `DuplicateRecordError` (a `ValidationError`, so every caller that already skips a bad row keeps doing so; carries `existing_id`/`existing_name`/`fields`). Matching is `RecordRepository.find_key_match` (typed JSON equality; 1 == 1.0). Not enforced by the database, so two simultaneous writes on PostgreSQL could still both pass. **Every path that brings records back goes through `_restore_clashes`** (live clash *and* two deleted records sharing values in the same set): `restore`, `restore_set`, `restore_records`, `plan_restore_set` and `restore_plan` (`RestorePlanDTO.conflict`, a `RestoreConflictDTO`; `can_restore` is false, `blocked_message` says why, `held_back_message` is only the deleted-thing reason so `only_this` can still sidestep a clash). Bulk paths leave a clashing record deleted and report it in `left`/`blocked`. Workflows: `WorkflowContext.create_record/update_record` note a refused write (`duplicates`), and the executor adds `take_duplicates()` to that step's outputs (a context without it, e.g. a test double, has none). Restoring a deleted field does not put back a key dropped when it was deleted.

### Data checks

`QualityService` (`services/quality_service.py`, `ctx.quality_svc`; pure part `domain/quality.py`) says what in the records a `RecordQuery` lists needs a look, per kind and field, by asking the rules that already exist and never a copy of them: `breaks_rule` (`record_service.restriction_problem`, `_check_restrictions` without raising), `blank` (an issue only for a `required` field; every own field's empty count is reported as information, `KindReport.blanks`), `duplicate_key` (`RecordRepository.key_duplicates`, once per key), `broken_reference` (`RecordService.reference_problems`, the rule `_check_reference_targets` now raises from) and `missing_file` (`file_access.place_of` = missing, from the `location` a list stamps). One walk (`_walk`: `stream_records` at `BULK_EDIT_PAGE`, one resolver, a page's references checked together) is behind `check` (counts + `MAX_EXAMPLES` named), `records_with(query, issue, field, schema)` (exactly those records, paged: what the explorer ticks and hands to bulk edit) and `check_field(schema, field, restrictions, required)` (what rules *as they would be* make of stored values, every collection). **Changing a rule never re-checks stored values, and an update checks only the values it changes** (`record_service._changed_values`, the one "unchanged" rule behind restrictions and references on update, as `_check_unique` skips a key whose values are the stored ones; compared after derived file keys are stripped and datetimes normalised; a create checks everything), so a record left breaking a tightened rule still takes an edit to another field and its broken values can be fixed one at a time, while changing one broken value to another is refused (`tests/services/test_tightened_restrictions.py`). Sync's `check_incoming` uses the same rule against the record it holds (a record not held, or coming back from deleted, is checked in full); `update_field` doesn't refuse, the editor warns from `check_field` instead (`POST /schemas/{s}/fields/{f}/check`, `FieldForm`'s `FieldCheckWarning`, `civex schema update-field` asks). Outliers are not checked (SQLite has no percentile). Cost: a fixed number of queries per page (`test_a_check_costs_the_same_however_many_records`). API `POST /records/quality`, `POST /records/quality/records`; CLI `civex record check [--issue --field]`; UI: a fact beside the record count, **N problems**, shown only when there are any (`useRecordQuality` with the same body as `ChecksView`, so one cached query under `records` that edits refresh; asked by itself only while the list holds at most `CHECK_COUNT_UP_TO` (5000) records); it opens the issue list in the address (`show=checks`, so `FieldCheckWarning`'s link still works; **Back to records**) (`components/explorer/ChecksView`: lines open their records in place (`chk.issue`/`chk.field`), ticked with `useBulkSelection` into `BulkEditDialog`; a blank's line drills into the explorer with `blank_filter`). There is no Check data button and no table of how full each field is (`KindReport.blanks` is still reported to the API and CLI). Not in `civex doctor` (it would read every record).

### Notes on records, in threads

`domain/notes.py` is the vocabulary and its checks. **Notes** are a kind of their own, `note` (`record_notes`, migration `c2f8a4d6e1b9`: id, record_id FK `ON DELETE CASCADE`, `thread_id`, body ≤ `NOTE_MAX_LENGTH`, author = the actor, created/edited/resolved_at, resolved_by, deleted_at). **Threads are one level deep**: a note with `thread_id` NULL starts one and `NoteService.reply(note_id, body)` adds to it (a reply to a reply joins the same thread; no foreign key on `thread_id`, since sync writes notes by snapshot). `NoteService` (`ctx.note_svc`): `notes(record)` (threads oldest first, each with `NoteDTO.replies` oldest first, response-only; one query whatever the size, `LocalNoteRepository.for_record`, `test_listing_threads_costs_the_same_however_many`), `add`, `reply`, `edit` (author only), `resolve(resolved=)` (always the thread's first note, whichever note is named), `delete`/`restore` (soft), `open_notes(query)`, `collection_of` for sync. **A reply to a resolved thread opens it again**, as one action (`audit.operation()`) with the reply. Deleting a thread's first note hides its replies (nothing is stamped on them: `_live` refuses a note whose thread is deleted), so restoring it brings them back except those deleted by themselves; a reply comes back only into a live thread. Each write is a history entry of kind `note` (`IDENTITY_KEYS` keeps `record_id` and `thread_id`). A deleted record's notes are hidden with it; a purge takes them via the foreign key, and `AuditRepository._forget` deletes their entries with the record's (record, collection and schema purges alike). Permissions: `write_records` in the record's collection for everything, edit also author-only (`action_for` says `ANYWHERE` for a note; the authority asks about the record's collection in `SyncAuthorityService._check_note`, which also refuses a note on a record, or a reply to a thread, it hasn't got). **Sync**: protocol 4 (unreleased; `KINDS_SINCE["note"]`, so a v3 device gets none through the peer router's `entry_for`); `ENTITY_ORDER` ends with `note`; two replies at once are two notes (`civex.testing.notes.replies_at_once`). **What is open**: `@open_notes` (eq true/false) is a filter-tree field about the listed record itself (`_check_open_notes_leaf`, `record_repo._open_notes_condition`), counting open *threads*, and an explorer column (`validate_columns`). Reads carry `open_notes` (open threads) and `latest_note` (the latest open thread's first line, `notes.first_line`), from one windowed query per page (`RecordRepository.open_notes_of`, `_attach_open_notes`, on `get` and `query_records` only; `test_listing_open_notes_costs_the_same_however_many`). **The one place to see everything open is the Collections page's All records, filtered, listing every kind** (`utils/notes.openNotesHref`, `schema=*`; see **Every kind at once**): the sidebar's **Open notes** and the Notes tab's **All open notes** link there, its **Open notes inside** to the record's collection explorer with `schema=*&within=<id>` (`openNotesInsideHref`), and the record header's open-thread count to its own Notes tab; while the filter asks for open notes (`asksForOpenNotes`) the explorer adds the **Open notes** column and opens a record on `?tab=notes`. It is the same list for everyone. API (`routers/notes.py`, tag `notes`): `POST /records/open-notes`, `GET|POST /records/{id}/notes`, `POST /notes/{id}/replies`, `PATCH|DELETE /notes/{id}`, `POST /notes/{id}/resolve|restore`; CLI `civex record note add|reply|list|edit|resolve|delete|restore` (`list` indents replies). UI: `components/notes/NotesPanel` (threads, a Reply box each, Resolve on the thread), `hooks/useNotes`, Activity words in `activityAudit.describeNoteEntry`. There is no review status: a sign-off ("Checked", "QC: pending/passed/failed") is a choice field, set with bulk edit and filtered in the explorer. Deliberately not here (the hub's, if anyone's): mentions, notifications, assignment, per-person inboxes, unread state, reactions, per-note permissions. Not yet: notes in bundles, a note's own Restore in Activity, notes in a collection's Activity tab.

### Fields are deleted softly

`fields.deleted_at` (migration `b7f2c9a14d36`). `SchemaRepository.delete_field` marks the field instead of removing it; `SchemaDTO.fields` holds only live fields and `SchemaDTO.deleted_fields` the rest, so nothing that reads a schema sees a deleted one. Records keep the value for it in `records.data` (keyed by the field's id), and `RecordService.update` carries those values across a save (`kept` from the stored data), because saving replaces `data`: restoring must bring back the value, not an empty field. `ResolvedSchema.deleted_by_id` (a `DeletedField`: the field and the schema it was defined on, which may be an ancestor) is built in the same parent walk as the live fields (`SchemaService._collect`; a second walk breaks `test_lookup_scaling`). `_ids_to_names` leaves deleted fields' values out of a record's `data`; `_with_names` reports them as `RecordDTO.deleted_fields` (`RecordResponse.deleted_fields`), which the record page shows under **Deleted fields** with the date and a **Restore…** button (`DeletedFieldValues`). A field's name is unique among *live* fields only (partial unique index `ux_fields_schema_name_live`), so a new field can take a deleted one's name; `restore_field_plan` then refuses with `RestorePlanDTO.reason` (nothing deleted is the cause, so no `blocked_by`) and a deleted schema is a `blocked_by` like for a record. `SchemaService.restore_field`/`restore_field_plan` (`POST|GET /schemas/{schema}/fields/{id}/restore[-plan]`, `civex schema restore-field`) log a `restore` entry; Activity treats fields like schemas: `audit_repo._now_is` and `AuditService._where_now` answer live | deleted | gone for them (`now.ref` is the field id, `now.schema_name` the schema), `RestoreDialog` takes `{kind: 'field', ref, schema}`, and Restore all restores fields after schemas and before records (a field whose name was taken counts as blocked). Not yet: a deleted field is never purged (retention and `trash purge-expired` skip it) and has no "Delete permanently". A bundle carries live fields only. Template references (`{field}`) removed when a field is deleted are not put back on restore.

### Restoring from Recently Deleted

A delete stamps the thing and everything it cascades to with **one `deleted_at`** (`DatasetRepository.delete`, `SchemaRepository.delete`, `RecordRepository.delete_many`), and restore uses it: `DatasetRepository.restore`/`SchemaRepository.restore` bring back only records whose `deleted_at` equals the parent's, and `RecordService._restore_group` the descendants with the same stamp reached through others in the group, so a record deleted on its own earlier stays deleted. This is the stand-in for batch ids (see below), not a replacement: it breaks if two operations ever share a timestamp. `RecordService.restore_plan` is the single rule for "can this come back": a record is `blocked_by` (`BlockerDTO`) its collection, then its schema, then the topmost deleted record directly above it, and `restore` refuses with `RestorePlanDTO.blocked_message` (the one wording, so the API/CLI/UI agree). `DatasetService`/`SchemaService.restore_plan` give the count of records that would return. `AuditService.plan_revert` of a delete uses the same plan and carries the `blocker`. Frontend: `RestoreDialog` (`components/trash/`) is the only restore entry in the UI: it fetches the plan, says what returns and where, and when blocked offers to restore the blocker instead (a trail, with Back); `useRestore` shows the receipt (what came back, where, a **View** link) and invalidates every cache a restore touches.

### Retention (clean-ups by age)

`[retention]` (`RetentionConfig`): `purge_after_days` (how long deleted items stay restorable), `auto_purge_deleted` (whether a clean-up then deletes them), `audit_days`, `run_days` (None = forever, the default for everything). **Nothing runs by itself** (the server has no scheduler); `RetentionService` (`ctx.retention_svc`; `civex retention show|run`; `GET/PATCH /settings/retention`, `POST /retention/run`; Settings → Retention) is started by a person or a cron, always counts first (`dry_run` is the default), and takes `RetentionCutoffs` from the settings (`settings_cutoffs`) and/or explicit dates per kind (`cutoffs`: a date wins over the setting). Order: deleted collections, then schemas (their records go with them, no purge line each), then the records deleted on their own (`RecordRepository.purgeable_deleted`: never one with a child that stays, nor anything above it), then history, then runs, so the purges just made are the newest history and survive. History (`audit_repo.prune`) keeps entries about anything currently deleted (`_now_is("deleted")`, so *Deleted* in Activity still works), and each thing's creation and latest entry however old while it exists (`_prunable`; pruning once left a live record with no history at all; a thing gone for good loses even its tombstone by age; counted as `audit_kept_first_and_last`) and, with a remote, entries not in a pushed commit; it then drops batches left empty. Runs (`job_repo.delete_finished_before`) are only completed/failed/cancelled ones, removed with their step logs via `bulk_delete_jobs`. Files nothing refers to afterwards are `GCService`'s job, not this one's. Retention's history pruning is by age; permanently deleting a record removes *its* history regardless (see "Where a thing is now"), leaving a tombstone that pruning may later remove by age like any entry.

### Names vs. labels

Schemas and fields each carry a `name` and a `label` (see `domain/naming.py`, mirrored in `frontend/src/utils/naming.ts`):

- `name` — the machine key. Slug-validated (`^[a-z_][a-z0-9_]*$`) on create and rename only. Referenced as text by workflow YAML (`field:`, `schema:`, `reference` restrictions), CSV headers, name templates and API paths.
- `label` — free-text display name, nullable. `display_label(name, label)` derives one from the name when unset; `FieldDTO.display_name`/`SchemaDTO.display_name` wrap that.

Validation is write-time only: rows predating the rule keep working, and `civex schema lint` (`SchemaService.lint_names()`) reports them. Bundle import passes `allow_legacy_name=True` so an old project's names round-trip unchanged. UI forms collect the label first and auto-slug the name (`NameLabelFields`); editing never re-derives an existing name. **The app's words are Name (the `label`) and Key (the `name`)**: the key is folded under the name with a *change* link and a tooltip while it follows the name, and is a field of its own when editing. Don't surface "label" or "name" as UI words for these.

### Name templates

`domain/templating.py` is the one string builder: literal text with `{name}` / `{name:spec}` variables (`{{ }}` escape braces; a spec is `|`-chained ops: `upper lower title slug trunc(N)`, a number format `03` / `.2f`, or a date pattern `YYYY-MM-DD`). It is pure (`parse`, `validate`, `render`, `rename_field`, `remove_field`); `render`'s `on_missing` is `skip` (drop a blank value and the separator beside it — record names), `fallback` (None, so the caller keeps something else — file names) or `empty`. Built-ins `schema`, `id`, and for files `ext`, win over fields of the same name.

- A record's name is `schemas.display_template` rendered by `RecordService._natural_name` (surfaced as `RecordDTO.natural_name`); no template means the first non-blank value of a type not in `templating.UNNAMEABLE_DTYPES`. `SchemaService.add_field` starts a schema with no template (and no other own nameable field) with `{that_field}` so the rule is visible and editable (audited as a schema update; bundle import passes `auto_name=False`); schemas older than that keep the implicit rule, which the Naming tab names in its placeholder. It replaced the old `display_fields` list (the migration turns `[a, b]` into `{a} {b}`; `SchemaDTO.from_dict` still reads old dumps).
- `{ref.field}` reaches one hop through a single `reference` field whose `schema` restriction is set (`SchemaService._reference_targets` is what validation allows; file names pass none, so they can't). The engine stays pure: `render` just looks up the key `"ref.field"`, and `RecordService._label_references` fills it in from the targets it already batch-loads for reference labels (`reached_name`, so no extra query) — which means the name using it exists only on API reads, not in `_with_names` audit snapshots, and a target's own label never expands its references. `_template_holders` returns a `via` per hit (None = direct, or the reference field's name) so renames/deletes on the *target* schema's fields rewrite `{ref.f}` too.
- `SchemaService.update` validates a template against the schema's own and inherited fields. `_template_holders`/`_rewrite_templates` keep both `display_template` and every `filename_template` restriction in step when a field is renamed or deleted, resolving by field identity so a shadowed inherited field is left alone.
- `POST /schemas/{name}/preview-name` renders a template against sample values (errors come back in the body). Frontend: `components/templates/TemplateBuilder.tsx` (chips insert at the cursor, per-variable format picker by dtype from `utils/templates.ts`, server-rendered preview) is used by the schema page's Naming tab and the file field's download-name rule.

### Formula fields

A `formula` field (`FieldTypeDescriptor.computed`, `field_descriptors.COMPUTED_DTYPES`) is **worked out when read, never stored**: nothing in `records.data`, so history, sync snapshots and bundle records can't carry one and changing the expression needs no backfill (a bundle carries the field's rules; import adds formula fields last, in rounds, `BundleService._import_formulas`). Restrictions: `expression` (required), `result` (`float|integer|string|boolean|date|datetime`, filled from the expression's kind when absent), and for a float `unit`, `decimals`. `domain/formulas.py` is the language, pure and safe: `parse` (Python `ast`; only numbers, text, True/False, names and one-hop `link.field`, `+ - * / // % **`, comparisons, and/or/not, `a if c else b`, and calls to `FUNCTIONS`; no other attributes, subscripts, comprehensions, lambdas, keywords or dunders; `MAX_SOURCE`, `MAX_NODES`, `MAX_EXPONENT`, `MAX_TEXT`), `infer` (kinds), `compute` (blank in, blank out unless `coalesce`; a value that can't be worked out is `(None, why)`, never raised) and `rename`/`uses`. `SchemaService._validate_formula` (behind `add_field`/`update_field` and `check_formula`) checks names against `formula_kinds` (own and inherited fields, their formulas by result type, `link.field` to stored fields only), kinds, the result's fit and circles among the schema's own formulas (`_check_formula_cycle`); `_check_computed` refuses required/default. A rename rewrites the formulas that read the field (`_formula_holders`/`_rewrite_formulas`, logged like template rewrites); deleting a field a formula reads is refused, naming the formula. Formulas are left out of name templates (`_template_names`, `UNNAMEABLE_DTYPES`), unique keys and search. **One place works them out**: `RecordService._formula_results(schema, records, names)`, which fetches what they read from the records above and through links in one batch (`_derived_values`) and orders formulas that read formulas. API reads get them from `_attach_formulas` (inside `_attach_reference_labels`, so never in an audit snapshot) in **`derived`** (not `data`), with `formula_errors`; `_derived_values` computes own and inherited formula columns, so explorer columns, `table_rows` and `typed_rows`/`frame` have them (typed by `result`, unit in `attrs`: `FileAccessService._column_types`). Writes drop formula values (`_strip_derived_file_keys`), `coerce_value` and bulk edit refuse them, and `_locate` refuses a filter or sort on one (SQL can't see it; summaries don't offer it: no measures, no grouping). Preview: `RecordService.preview_formula` (`POST /schemas/{s}/fields/preview-formula`, `civex schema preview-formula`), with the save check's problem and a per-record error in the body. CLI: `civex schema add-field|update-field --type formula --expression/-e --result --decimals --unit`. Frontend: `FormulaControl` (expression box; `ValueInserter`/`choicesFor` shared with `TemplateBuilder`; functions from `utils/formulas.FORMULA_FUNCTIONS`; `useFormulaPreview` for the latest or a picked record, whose `problem` blocks saving), `FormulaResultControl`, `DecimalsControl`; the record page shows each formula read-only (`RecordFieldGrid computed=`) and `utils/formulas.shownAs` makes every display treat it as the type it gives. Filter pickers (`filterableFields`), sorting, bulk edit and join columns leave formulas out. Not yet: filtering, sorting or summarising by a formula (would need arithmetic compiled to SQL), `link.formula`. Tests: `tests/domain/test_formulas.py`, `tests/services/test_formula_fields.py` (with a query-count test), `tests/server/test_formula_router.py`, `tests/cli/test_schema_formula.py`.

### Field restrictions

Which restriction keys exist for a type, and how the UI should present them, is declared once in `domain/field_descriptors.py` (`FIELD_TYPES`, `FIELD_KINDS`). `schema_service.VALID_RESTRICTION_KEYS` is derived from it and `GET /schemas/field-types` serves it, so the field editor (`components/schemas/FieldForm.tsx`, rendering `RestrictionControls.tsx` through `controlRegistry.ts`) and the record form's guidance build from data. Adding a restriction means: a descriptor entry, its check in `_check_restrictions()`, and — only if no existing `control` fits — a new control in `RestrictionControls.tsx` registered in `controlRegistry.ts`. Descriptors only describe; validation stays in `_check_restrictions()` (stored values) and `SchemaService` (restriction values, `_check_control_value` + `_validate_restriction_values`). Rules (validation) are kept apart from views (how a value is displayed, e.g. a spectrogram for audio): a field's views are meant to become another section of the field inspector (`InspectorSection` in `SchemaFieldsSection.tsx`) with their own settings, not more keys in `restrictions`.

Each field carries a `restrictions: dict[str, Any]` validated at write time by `_check_restrictions()` in `record_service.py` — the single source of truth. Restriction keys by type:

| Type | Keys |
|---|---|
| `integer`, `float` | `min`, `max` |
| `float` | also `unit` (symbol; canonicalised, e.g. `degC` → `°C`) |
| `string` | `choices` (list), `max_length` |
| `longtext` | `max_length` (multi-line text box; plain string, newlines kept; not nameable in name templates) |
| `date`, `datetime` | `min`, `max` (ISO strings; compared as parsed objects, not strings; `date` bounds may be partial) |
| `date` | also `precision` (`year` / `month` / `day`) |
| `geo` | `geometry_types` (list), `bbox` (`[west, south, east, north]`) |
| `datetime` | also `timezone` (IANA name; overrides the collection's `timezone` when reading and showing this field) |
| `file`, `file_list` | `accept` (comma-separated MIME/ext), `max_size` (bytes), `filename_template` (see below) |
| `reference` | `schema` (target schema name) |
| `formula` | `expression`, `result`, and for a float result `unit`, `decimals` (see **Formula fields**) |

`filename_template` is a name template (see "Name templates" below; `{ext}` is the original file extension) resolved server-side by `resolve_filename()` in `record_service.py`, a thin wrapper over `templating.render` that adds sanitising — rejected at field-save time if it names a field not on the schema (`SchemaService._validate_filename_template()`). `RecordService._with_names()` resolves it against each record's own field values and stamps the result onto every `file`/`file_list` value in API responses as `resolved_filename`, alongside the unchanged original `filename`; a blank/missing referenced field falls back to the original filename rather than emitting a partial name. The record-UI download link (`DynamicField.tsx`) uses `resolved_filename` for its `download=` attribute. `GET /files/{sha256}` stays content-addressed and record-agnostic — it doesn't accept record/field context to resolve a template itself; it takes an explicit `?filename=` override, so scripted consumers that want the resolved name read it off the record API and pass it through.

### Workflow execution

`executor.run()` topologically sorts steps (Kahn's algorithm), resolves `step_id.output_name` input references, and calls each plugin's `run()` in order. It commits nothing: both drains (`background.run_pending_jobs`, `cli.utils.drain_jobs`) run it inside `AppContext.all_or_nothing()` (a SAVEPOINT) and commit once with the run's outcome, so a failed run keeps none of its writes (a cancelled one keeps what it got through). **What a plugin may ask of civex is one table**, `plugins/host_api.HOST_API` (name, permission action, call): the subprocess/container dispatcher answers every `rpc_call`/`call_tool` from it, a plugin's `capabilities` are permission actions (`read`, `write_records`, `manage_files`, `delete`; a bare function name still grants just that one), `granted()` works out the set at discovery, and `test_host_api` holds `docs/extending/writing-a-plugin.md`'s table to it. A new host function is an entry there plus the SDK `Ctx` method. `commit` is answered as a no-op for old plugins. **Every plugin, built-in or not, is run the same way**: `runtime.run(launcher, ...)` over the SDK wire protocol; a tier is only a `Launcher` (`launchers.py`: `UvLauncher` for `_civex/plugins/*.py`, `DockerLauncher` one container per request, `InProcessLauncher` a built-in's `serve_loop` on a thread here, not stopped by a timeout). Built-ins subclass the SDK's `Plugin` and get an SDK `Ctx`, never a `WorkflowContext`; a write the host refuses reaches them as `RpcError` (`builtins/_refusals.refused`). Custom plugins are discovered from `_civex/plugins/*.py` and must define a class named `Plugin` subclassing `civex_plugin_sdk.Plugin`. **A custom plugin declares its contract in its header** (`[tool.civex]` in the PEP 723 block, `plugins/manifest.py`: `read`/`write`/`differences`): `PluginService.save`/`save_uploaded`/`check(write=True)` (`civex plugin check [--write]`) write it from the code's `describe`; discovery and `registry.describe_file` read it without running anything; `UvLauncher(declared=)` asks the code again when its process starts (`Launcher.check`) and refuses a mismatch (`contract_mismatch`); the library's install uses `registry.describe_code` (runs it, and checks the header). **Lockfiles:** `UvLauncher.start` locks a script without one (`subprocess_runtime.lock_plugin`, `<name>.py.lock`; not in a dev checkout, whose SDK wheel is per process), and `_build_command` runs a locked script without the `--with civex-plugin-sdk==` pin. **Files go by path, in one folder per run**: `executor.run` makes `ctx.run_dir` (`runtime.new_run_dir`, in the user's cache or `CIVEX_RUNS_DIR`, never the project; a day-old leftover is removed) and removes it when the run ends; `runtime.run` names it in each `RunRequest` (protocol 3), puts large values there, and `host_api` copies files into it (`get_file`/`file_path`, read-only copies) and stores from it (`store_path`); `host_api.inside_run` refuses any path a plugin hands back outside it or its working folder (`path_refused`). `DockerLauncher` mounts it at the same path.

Workflow triggers fire via `trigger_for_record()` in `WorkflowJobService`. When a record is **created**, both `record_created` and `record_updated` are fired — but `record_updated` only includes fields with non-null values in `changed_fields`, so field-restricted triggers (`fields: [some_field]`) do not fire unless that field was actually set to a non-null value on creation.

Manual workflow runs supply inputs via `initial_outputs` in the executor (key `"__input__"`). Steps reference them as `__input__.field_name`.

**Deleting runs.** `WorkflowJobService.delete_runs(ids)` (`POST /jobs/delete` with `ids` or `filter`, `DELETE /jobs/{id}`, `civex automation delete [--pending]`, the runs table's **Delete N…**/**Delete all N…**) removes runs whatever their state: a waiting one never starts (the claim is a conditional UPDATE on a row that is gone), a running one stops before its next step (`should_stop` finds no row) and its final `mark_*` is a no-op. What it changed in records stays.

**Stopping and provenance.** `AutomationConfig.paused` (`[automation]` in config.toml, read cheaply by `read_automation_paused(civex_dir)`) is the kill switch, and `WorkflowJobService` is its one decision point: `trigger_for_record` enqueues nothing, `enqueue_manual` raises, and `claim_pending` returns None while paused, so the server's `run_pending_jobs` and the CLI's `drain_jobs` both stop at once. `stop_all()` pauses *first* (so a run can't spawn more), then cancels every pending/running job (`status = "cancelled"`); `cancel_job` does one. A running job learns it was cancelled because `executor.run(should_stop=…)` asks `job_svc.should_stop(job_id)` (a fresh status read, or paused) before every step and raises `JobCancelled` (carrying the steps done); both drains then call `mark_cancelled`, and `mark_completed`/`mark_failed` never overwrite a `cancelled` row. A step already running is not interrupted. `claim_pending` is an atomic conditional UPDATE. `WorkflowJob.trigger_detail` (`{changes: [{field, before, after, watched}], caused_by: {job_id, workflow} | null}`) says what started a run; `RecordService.update` computes `changed` from the stored values on both sides (never from the response form with its derived `resolved_filename`, which once made a workflow watching a file field re-trigger itself on every save), and `WorkflowContext.job_id`/`workflow_name` become the `_cause` passed to `record_svc.update/add` so a chained run can name its parent. `WorkflowContext.job_depth` must be passed by every drain (the CLI's once forgot, so chains never hit `MAX_JOB_DEPTH`). Frontend: `StopAutomationDialog` is the one confirmation; workflow runs and the pause show in the shared status bar (below); `RunSummary` shows what changed and the chain; `JobsTable` has a per-run cancel.

### Built-in plugins

| Plugin ID | Purpose |
|---|---|
| `civex.get_field` | Read a field from the trigger record |
| `civex.save_field` | Write a value to a field on the trigger record |
| `civex.save_fields` | Write multiple fields at once |
| `civex.load_file` | Load bytes + filename from a file field |
| `civex.load_file_list` | Load a list of file refs from a file_list field |
| `civex.extract_from_filename` | Apply a regex to a filename; optionally convert to date/datetime using token format (`YYYY MM DD HH mm SS`); non-token chars are raw regex so `[-_]` works as a separator alternative |
| `civex.create_records_from_files` | Create one record per file in a file list (no key matching — pure insert) |
| `civex.match_files_to_records` | Match files to existing child records by key extracted from filename; creates if not found |
| `civex.upsert_records` | Upsert records from a pandas DataFrame |
| `civex.rows_to_records` | Convert rows to records |
| `civex.parse_table` | Parse delimited bytes (CSV, TSV, ...) into a DataFrame; `delimiters` lets one step read several kinds |

**Writing records from a plugin.** `RecordService.update` (and so `WorkflowContext.update_record`) **replaces** a record's whole data with what it is given, so a plugin passing only the fields it knows erases the rest: `civex.upsert_records` once reduced records with 58 fields (a file, 49 computed values) to its table's 9 columns. Use `WorkflowContext.patch_record(id, fields)`: it reads the record fresh, merges only `fields`, and writes nothing when they already hold those values (no history, no triggers, not listed as touched). An absent value is left out of `fields`; it never clears anything. `upsert_records`, `save_field` and `save_fields` use it; `match_files_to_records` merges by hand.

### CLI pattern

Each CLI module (e.g. `cli/schema.py`) creates a `typer.Typer()` sub-app. Commands call `get_ctx()`, delegate to a service, print with `console` (Rich), call `ctx.commit()`, then `ctx.close()`. Error handling raises `typer.Exit(1)` after printing; `CivexError` subclasses (`NotFoundError`, `AlreadyExistsError`, `ValidationError`) are the canonical error types.

**Summaries.** `RecordService.summarise(query, SummaryRequest)` groups exactly the records a `RecordQuery` lists (it needs `schema`, the kind summarised) by up to `MAX_GROUP_BY` field values and works out measures over each group plus a total row (each record once). `domain/summary.py` (pure) holds the request (`GroupBy` field/`schema` (a kind above, resolved by `_locate` like a filter leaf; never a kind beneath)/`bucket`/`bin`, `Measure`), the one written form the CLI, API and address share (`parse_group_by`/`parse_measure`: `site.region`, `taken:month`, `depth:5`, `mean:depth`), what the repo gets (`GroupPlan`/`MeasurePlan`) and the result (`GroupValue` with `lower`/`upper` for ranges and periods so a chart can place them, `precision` for a date less precise than its period, and per row `where`: the filter tree that lists exactly that group, built by `group_value`, so drilling in is the filter's own rule; None for a list item). **Which measures and groupings a type allows is `FieldTypeDescriptor.measures`/`grouping`/`buckets`** (served by `GET /schemas/field-types` with `summary_measures`), never a second table. `repositories/local/summary_sql.py` is one statement on both dialects over `_base_query`'s WHERE: values read through their JSON type (legacy text in a number field is no number, not an error; `filled` = not absent/null/""/[]), a field of a kind above through outer joins up the parent chain, a list's items through a lateral `json_each`/`jsonb_array_elements`, groups and total one `UNION ALL` (GROUP BY by output name: PostgreSQL won't match bound parameters). Partial dates keep their own group ("2019, month not known"); a datetime groups in the field's zone, else the collection's, else UTC: PostgreSQL by `timezone()`, SQLite by a balanced CASE over `timezones.offset_changes`. No median (SQLite can't cheaply). `test_one_statement_however_many_records`; `tests/services/test_record_summary_postgres.py` reruns the service tests on PostgreSQL. Surfaces: `POST /records/summary` (`RecordSummaryRequest`, a `RecordQueryRequest` + `group_by`/`measures` strings; `?format=` writes it through `write_table` via `summary.table_of`), `civex record summarise`, and every chart (see **Charts and the Analytics page**). `components/explorer/SummaryResult` draws a result as a table and `SummaryChart` as a chart; `utils/summaryChart.buildSummaryChart` is the one rule (pure): the first grouping picks the form (`chartForm`: a date period is a line over time, a number in ranges a histogram, else bars), empty periods/ranges between are filled (0 for count/filled/distinct/sum, a gap for the rest), the second grouping is the series (`MAX_SERIES` largest, stacked only for additive measures), no value and dates less precise than the period are listed beside the chart, and every bar/point keeps its row's `where`. It draws with the analytics primitives (`BarBreakdown`, `TimeSeriesChart`, `PieBreakdown`, `chartTheme`), as the chart's `show` says (`SummaryChart as`). **Points on a map:** `RecordService.points(query, field, schema=, limit=)` (`POST /records/points`): `RecordRepository.geometries` reads only records whose value is a JSON object (up the parent chain for a kind above), oldest first, capped (`POINTS_DEFAULT_LIMIT` 10 000, `RecordPoints.total`/`truncated`); `test_mapping_costs_the_same_however_many_records`. A collection's page is its records with no tab row: Exports and Activity are in the header's menu (`?tab=` still opens them). Cancel and "done" actions use `useBack(fallback)` (a step back in history, else the fallback) instead of hard-coded list links, and a finished form replaces its own history entry. Runs filter by status, trigger and search and sort by column on the server (`GET /jobs`); every audit endpoint takes `action` and `sort` through one `AuditView` dependency.

`DynamicField` is the single component that renders an editable input for any field type, including restriction-aware behaviour (choices→select, min/max, accept/max_size on files). `JobsTable` owns its own pagination state and accepts `recordId?` + `statusFilter?` props — do not duplicate pagination in parent pages.

## Key files for common tasks

| Task | File |
|---|---|
| Add a new CLI command | `src/civex/cli/<group>.py` + register in `src/civex/main.py` |
| Add business logic | `src/civex/services/<name>_service.py` |
| Add a DB table | `src/civex/db/models.py` + `src/civex/repositories/protocols.py` + `src/civex/repositories/local/` |
| Add a built-in plugin | `src/civex/plugins/builtins/<name>.py` (auto-discovered; no registration needed) |
| Add a container-tier (Tier 2) plugin starter for a new language | `plugin-templates/<language>/` — Dockerfile + minimal shim speaking the Tier 1 wire protocol (see `plugin-templates/r/`) |
| Add an API endpoint | `src/civex/server/routers/<resource>.py` |
| New domain types | `src/civex/domain/dtos.py` or `src/civex/domain/exceptions.py` |
| Add a frontend API call | `frontend/src/api/<resource>.ts` + hook in `frontend/src/hooks/use<Resource>.ts` |

## Documentation

The docs site lives under `docs/` (MkDocs Material, see `mkdocs.yml`). Some pages are generated at build time — editing a generated page directly loses the change on the next build, so know which is which before touching a file under `docs/`:

| Path | Source of truth |
|---|---|
| `docs/reference/cli/*` | Generated from `civex.main:app` by `docs/_gen/_cli.py` |
| `docs/reference/http-api.md` + `openapi.json` | Generated from `create_app().openapi()` |
| `docs/reference/plugins/*` | Generated from the plugin registry + `docs/_prose/plugins/*.md` |
| everything else under `docs/` | Hand-written |

Keep-in-sync rules:

- New CLI command → write prose help only; no indented line art, and never `\b` escapes — it renders in the generated reference.
- New HTTP endpoint → add a docstring, and `Field(description=)` on any new request/response model — both feed the generated `http-api.md`.
- New built-in plugin → add `docs/_prose/plugins/<slug>.md` with the `<!-- civex:tables -->` marker, or CI fails.

`make docs` serves the site with live reload; `make docs-build` runs the strict build CI uses.
