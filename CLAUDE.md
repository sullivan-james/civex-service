# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Setup

Dependencies and the venv are managed by [uv](https://docs.astral.sh/uv/) — it reads `pyproject.toml`, resolves against the committed `uv.lock`, and provisions a matching Python 3.12 itself (see `.python-version`) if the system doesn't have one.

```bash
uv sync --extra server --extra workflows --extra dev  # standard dev setup (== `make install`)
uv sync --all-extras                                   # every optional extra (== `make install-all`)
uv sync                                                 # base install only, SQLite, no extras

uv lock                                                 # re-resolve after editing pyproject.toml deps
uv run civex --help                                     # run inside the synced env without activating it
```

`uv sync` creates `.venv/`. There's no separate activation step required for `uv run ...`; activate `.venv/bin/activate` directly if you want a persistent shell.

`make check`/`make secrets` also require the [gitleaks](https://github.com/gitleaks/gitleaks#installing) binary on `PATH` — it's not a `uv`/`npm` dependency. Install via `brew install gitleaks`, `go install github.com/gitleaks/gitleaks/v8@latest`, or download a release binary.

## Commands

Common tasks are wrapped in the `Makefile` — `make help`-style targets: `install`, `lint`, `format`, `format-check`, `typecheck`, `test`, `secrets`, `check` (everything CI runs), `pre-commit`, `serve`, `dev`, `clean`.

```bash
# CLI
uv run civex --help
uv run civex init                 # create a _civex/ project in the current directory
uv run civex serve                # start HTTP API (requires the server extra)
uv run civex serve --reload       # dev mode with auto-reload  (== `make serve`)

# Tests
uv run pytest tests/              # run all smoke tests            (== `make test`)
uv run pytest tests/test_smoke.py::test_init_creates_civex_dir  # single test

# Lint / format / typecheck
make check                        # ruff format --check, ruff check, mypy, pytest — what CI runs
make lint                         # ruff check --fix
make format                       # ruff format

# Frontend (cd frontend/ first)
npm run dev                       # Vite dev server (proxies /api to localhost:8000)  (== `make dev`)
npm run build                     # tsc + Vite production build (outputs to frontend/dist/)
```

The server serves the built frontend from `frontend/dist/` via the `ui` router. During development run `civex serve --reload` and `npm run dev` in parallel — Vite proxies API calls.

## Architecture

```
src/civex/
  cli/           # Typer commands — parse args → call service → format output
  domain/        # Plain dataclasses (DTOs) and exceptions; no framework dependency
  services/      # Business logic: SchemaService, DatasetService, RecordService, FileService
  repositories/
    protocols.py         # Protocol interfaces (SchemaRepository, DatasetRepository, etc.)
    local/               # SQLAlchemy implementations of those protocols
  db/
    models.py    # SQLAlchemy 2.0 ORM models (Schema, Field, Dataset, Record)
    session.py   # Engine factory; engine is cached, session is per-request
  plugins/
    base.py      # BasePlugin ABC + WorkflowContext dataclass
    registry.py  # Discovers built-ins and user plugins from _civex/plugins/
    builtins/    # Built-in plugins (see Built-in plugins section below)
  workflows/
    definition.py  # Pydantic models for YAML workflow files
    executor.py    # Topological sort (Kahn's) + step execution
  server/
    app.py       # FastAPI app factory
    routers/     # One router per resource: schemas, datasets, records, files, workflows, ui
  config.py      # find_project_root() walks up from cwd; load_config() reads _civex/config.toml
  context.py     # AppContext dataclass + build_local_context() factory
  console.py     # Rich Console instance used across CLI
```

### Layer rules (strict)

- `cli` → `services` via `AppContext`. Never touches repos or DB models directly.
- `services` → `repositories/protocols` (interfaces). Never imports from `cli` or `db`.
- `repositories/local` → `db/models`. The only layer that imports SQLAlchemy models.
- `plugins` → `WorkflowContext` only. Never imports SQLAlchemy or sessions.
- `domain` has no imports from the rest of civex — safe to import anywhere.

### AppContext pattern

`build_local_context(config)` in `context.py` wires all repos and services. CLI commands call `get_ctx()` from `cli/utils.py`, then call `ctx.commit()` after mutating operations, and `ctx.close()` when done. The server calls `build_local_context()` once per request.

### Data model

Record `data` is stored as a JSON/JSONB dict (no EAV), keyed by **field UUID** — `RecordService._names_to_ids()`/`_ids_to_names()` translate at the service boundary, so everything above that layer sees name-keyed data and renaming a field costs nothing in storage. Field types: `integer | float | string | boolean | date | datetime | geo | file | file_list | reference | reference_list | enum | url | tags | longtext` (`VALID_DTYPES` in `schema_service.py` is the authority).

- `file` / `file_list`: record stores `FileRef` dict(s) `{sha256, filename, size}`; bytes live in `_civex/objects/<sha256[:2]>/<sha256[2:]>` (git object store layout).
- `date`: stored as an ISO string at the precision it was written (`2019`, `2019-06` or `2019-06-14`; a `precision` restriction names the least precise form a field accepts, default `day`). Logic in `domain/partial_dates.py`, mirrored by `frontend/src/utils/partialDates.ts`. Min/max compare whole periods. `datetime`: always stored as a UTC ISO string. `RecordService.add`/`update` normalise every datetime via `_normalise_datetimes()` (and the CLI via `coerce_value`), reading a value with no UTC offset as wall time in the field's `timezone` restriction, else the collection's `timezone` (`datasets.timezone`), else UTC. DST gaps/overlaps and malformed values are rejected; `update` skips values merely echoed back, so a legacy offset-less value isn't shifted when a zone is set later. The logic lives in `domain/timezones.py`; `frontend/src/utils/dates.ts` mirrors its DST rules for display and entry, and works to the second: the datetime input must have `step={1}` (the default minute step hides the seconds field), `utcToZonedLocal` includes seconds when non-zero, `zonedLocalToUTC` accepts seconds and a fraction, and `formatDateTime` shows seconds when the value has them.
- `geo`: stores a GeoJSON geometry dict (WGS84, `[lon, lat]`). Validated by `domain/geo.py` on every write, with or without restrictions; `bbox` with west > east crosses the antimeridian. CSV cells and the CLI read `"lat, lon"`, `POINT(lon lat)` or GeoJSON (`geo.parse_text`); exports write a plain point as `"lat, lon"` (`geo.to_text`). Mirrored by `frontend/src/utils/geo.ts` and `geoCoords.ts`. `parse_coordinates` also reads hemisphere letters and degrees/minutes/seconds (`56°07'12"N 3°24'36"W`); both implementations are tested against the same table of examples. A Point may carry `uncertainty_m` (a foreign member, validated) and a third coordinate (elevation, negative for depth). On the record form `GeoInput` gives guidance and an **Edit on map…** modal (`components/geo/GeoEditor.tsx`): OpenLayers in plain lat/lon with bundled coastlines (`world-atlas`) and a graticule, in a lazy chunk (`GeoMap.tsx`) so the main bundle doesn't carry it; an optional XYZ tile URL comes from `[map]` in `config.toml` (`GET/PATCH /settings/map`, `hooks/useMapSettings.ts`). The editor edits a draft (`utils/geoDraft.ts`) and changes nothing until Apply; file import (`utils/geoImport.ts`) reads GeoJSON, GPX, KML and WKT via OpenLayers' readers.
- `float` with a `unit` restriction: a field has exactly one unit and every stored value is in it. The service never converts; `domain/units.py` (mirrored by `frontend/src/utils/units.ts`) converts only at entry edges: `RecordService.coerce_value` (CLI) reads `"1024 ft"`, the record form's `UnitInput` does the same, and the CSV import asks each column's unit (`MapState.columnUnits`). Changing a field's unit is a relabel, never a conversion (the CLI asks for confirmation). Units outside the table are plain labels.
- `reference`: stores the UUID of another record as a string. The target schema is enforced via a `schema` restriction.
- `file_list`: stores a list of `FileRef` dicts.

On PostgreSQL, JSON columns use `JSONB` via `with_variant`.

Schema inheritance is resolved recursively by `SchemaService.collect_fields()` — parent fields are appended after own fields and labelled with their source schema.

### Collection scope and schema lists

A collection (`datasets` table) carries a `scope` (`local` | `global`, `domain/scopes.py`) and a schema list (`dataset_schemas`, surfaced as `DatasetDTO.schemas` — names). Both are managed by `DatasetService`:

- `RecordService.add` rejects a record whose schema isn't in its collection's list (`_check_schema_allowed`); an empty list allows nothing. A child schema's ancestors must be listed too, and a schema with live records can't be removed (`DatasetService._check_schema_list`/`update`).
- `RecordService.add`/`update` check every `reference`/`reference_list` value (`_check_references`): the target must be a live record in the same collection or in a `global` one. Values equal to the stored ones are skipped on update. Schema-level reference restrictions are *not* checked against collections — schemas are global and can't know their collection.
- A `global` collection that other collections' records reference can't be made `local` or deleted (`RecordService.collection_referrers`).
- `find_by_schema(..., reachable_from=<collection>)` / `GET /records?reachable_from=` is what reference pickers search; `RecordDTO.dataset_name` and `reference_collections` (set in `_attach_reference_labels`) drive the "from collection X" marker in the UI.
- Tests: the schema-list check is disabled by an autouse fixture in `tests/conftest.py`; request `strict_schema_lists` to exercise it.

### Storage volumes

`VolumeAwareFileObjectStore` (`repositories/local/file_store.py`) writes to the first usable volume in `store.volume_queue`. A volume's whole definition lives in `config.toml` (`[store.volumes.<name>]`: `path`, `allocated_gb`, `id`, `state`); the DB holds only the blob inventory (`stored_objects`), never volume configuration.

- `volume_status(name)` is the **single** decision point for "can this volume be used?" — writes, stats, directory walks and inventory reconcile all go through it, and it returns a `VolumeStatus` (`domain/dtos.py`: `state`, `reason`, `fix`). `fix` is interface-neutral prose; the CLI adds the command and the UI a button.
- Identity: `VolumeConfig.id` + a `.civex-volume` marker in the volume root. Enforced only for volumes outside the project, and only once a volume has an `id` (assigned by `StoreService.add_volume`/`adopt_volume`, never during an upload, which must not rewrite `config.toml`). A mismatch is `wrong_drive`.
- Placement: `[store.placement.<collection-id>]` (`PlacementConfig`: `volume`, `on_unavailable` = `spill`|`fail`, `domain/placement.py`) names a collection's home volume. It is keyed by collection **id** and lives in config.toml with the volumes it names. `_write_candidates(collection_id)` is the single place that orders volumes for a new write (home first, then the queue unless `fail`); the hint is a `collection_id` argument on `put`/`put_path`/`put_stream` and `FileService`, supplied by the upload endpoints (`?collection=`), `WorkflowContext.store_file`, the import wizard and record forms (`hooks/uploadCollection.ts`). `StoreService.set_placement`/`clear_placement` manage it; `DatasetService` calls `on_purge` (wired in `context.py`) so a purged collection loses its placement.
- **A home keeps a copy of every file its collection uses** (`domain/placement.py`, the one copies rule). `stored_objects` is keyed (`sha256`, `volume`), one row per copy (migration `c3f7a9e1d5b8`), and is the only answer to where a file is on this computer: `copies(shas)`, `locate_volumes` (a copy that can be read now first), `_locate` (reads: tries the recorded volumes only; walks the volumes once only for content the inventory doesn't know, and records what it finds), `copies_of`. The record never says where (locations are per machine and don't sync). `_existing_copy()` is the one dedup rule: content already stored is reused, except that it is written again onto the collection's home when the home hasn't a copy (`writing_to`); no other drive ever gets a second copy. A query asking whether a file is here or how big joins `inventory.stored_files()` (one row per file), never the table. `volume_breakdowns(homes=)` counts each of a collection's files once, on its home if a copy is there. `delete(sha)` removes every reachable copy (an unplugged drive's stays, recorded), `delete(sha, volume)` one; free-up counts every copy's bytes (`SyncService._room_of`). Moving: `transfer_engine.plan_steps` + `placement.file_step` is the one rule behind a transfer's preview (`TransferService._size_steps`), the move dialog (`FileAccessService.plan_move`/`shas_to_move`) and the engine: a file is **copied** (`keep_source`, the original stays and stays recorded) when its drive is the home of a collection that uses it (gathering a collection, its own home doesn't count), else moved; `TransferPlan.copied`. There is no `include_shared` on transfers any more (old saved specs are read with `_known`). Not yet: clean-up doesn't remove copies left on a drive that stopped being a home.
- Picking a location: `StoreService.inspect_path()` is the single rule set for "can this folder become a volume?" (`PathInspection`: `problems` block, `warnings` don't); `add_volume` enforces it, the Add-volume form previews it (`GET /store/inspect`), so they can't disagree. `browse_directory`/`create_folder` back the in-app folder browser (`GET /store/browse`; folders only), because a browser can't give a server-side path. A relative path is resolved against the project root and "inside the project" is the store's own `_inside_project` rule.
- Network drives are mounts the OS already made (`civex/fs_locations.py` detects them from `/proc/mounts`, macOS `mount`, Windows drive type; civex doesn't mount or hold credentials). Anything that touches a volume outside the project goes through `fs_locations.guarded()`: a time-limited call with at most one call per location outstanding: a caller that arrives while an earlier call is merely busy (younger than `FS_TIMEOUT`) shares its answer or waits its turn, and only a call already past the timeout counts as stuck, so a dead mount becomes `offline` ("not responding") instead of freezing a request, and a healthy-but-busy one doesn't, and `_locate` skips volumes that aren't answering so reads elsewhere aren't stalled.
- Where a file is stored is **response-only**. `RecordService._attach_file_locations` stamps `location` (`{volume, state, available, reason, fix}`; `reason`/`fix` are the volume's own words for why it can't be opened and what to do, blank when it can) on every `file`/`file_list` value, in one inventory lookup and one status check per volume for the whole batch (`store.locate_volumes`); it runs inside `_attach_reference_labels`, which every API read passes through, and **not** in `_with_names`, which audit snapshots also use, so a location is never frozen into the log. `_strip_derived_file_keys` (`DERIVED_FILE_KEYS`) removes `location`/`resolved_filename` on `add`/`update`, because the UI echoes values back. Details come from `FileInfoService` (`GET /files/{sha256}/info`, `civex store where`): every copy with its on-disk path, size, and what uses the file. `GET /files/{sha256}` answers 503 naming the volume when the content is recorded on one that isn't reachable (404 only when it is nowhere).
- Frontend: `hooks/useFileLocationDisplay.ts` is the one rule for when to show a location (always when unavailable; the volume once there are several; always with details in advanced mode); `FileLink` / `FileLocationChip` (`components/records/FileLocation.tsx`) are used everywhere a file is rendered, and `RecordStorageSummary` summarises a record. The chip is a click/keyboard popover for everyone (plain-words where/online/what to do, from the location's `reason`/`fix`; **More details** mounts `FileInfoPanel`, already open in advanced mode), and `FileLink` checks a download with a headers-only request first so a drive unplugged since page load says which drive instead of the browser's generic failure. Uploads share `hooks/useFileUploads.ts` (live bytes/speed/ETA, a "Saving…" phase once every byte is sent, cancel via `AbortSignal` that keeps finished files) and `components/records/UploadProgress.tsx`, used by both `RecordFieldGrid`'s `FileControl` and `DynamicField`.
- **Moving files between volumes** (`domain/transfers.py`, `services/transfer_engine.py`, `transfer_service.py`, `transfer_jobs.py`, `repositories/local/transfer_repo.py`; table `storage_transfers`). Two kinds: `drain` (empty source volumes) and `consolidate` (gather collections' files; files also used by a collection kept elsewhere stay unless `include_shared`). The engine's per-file order is the whole safety argument and must not be reordered: copy to a scratch file on the target while hashing (must equal the recorded sha256), optional read-back, atomic rename, `record_moves` + commit, *then* remove from the source. A crash between any two steps leaves the file on the source, the target, or both. Resuming re-discovers work from what is physically on the source (`iter_volume_objects`), so no cursor is stored; progress counts only after a batch commit, and `CopyResult.reused` + an inventory check stops a leftover original being counted twice. Transfers copy only through `FileObjectStore.transfer_object`; copies touching a volume outside the project run on a watched thread (`STALL_SECONDS`) because a blocked write to a dead mount can't be interrupted. `TransferService` owns planning (`plan` is the single rule set behind the preview and `create`), freezing drain sources read-only (`StoreService.set_volume_state`, which re-reads config.toml first, remembers the previous state in `frozen`, and restores it on finish/cancel), and interrupted detection (`_reap`: a record is dead only when its `updated_at` is stale **and** `transfer_lock_held()` is false — silence alone never is, since a read-back or slow drive goes quiet while alive). Pause/cancel are saved on the row (`control`) and noticed as progress is saved, so they work across processes (web UI controlling a CLI run and vice versa); `save()` deliberately never writes `control`. **Transfers queue and run one at a time**: `create`/`begin_resume` save a transfer as `queued`, and `TransferService.next_runnable()` is the single rule for what runs next (oldest queued, or one paused only for a drive that has since answered). `TransferWorker.drain()` (`transfer_worker.py`) runs them in turn and is hosted by whichever process is at hand: the CLI (`civex store move`/`transfers resume`/`transfers run`) runs it in the foreground with a live bar, and the server's `TransferJobs` (`jobs` singleton) runs it on one thread started at startup and when something is queued, holding the running transfer's latest progress in memory (`live_progress`, which the API reports in preference to the saved copy). The store's transfer lock (O_EXCL, PID-owned) keeps it to one runner across processes: a host that finds it held (`TransferBusy`) leaves the queue to the one running it. Pausing or cancelling a queued transfer settles it at once; pausing one waiting for a drive stops the waiting. A drain's sources are frozen when it starts and put back whenever it stops for good, pauses or fails. GC and a transfer take mutually exclusive lock files, each holding its owner's PID, so a lock whose process has died is free at once (a lock with no readable PID falls back to a one-hour mtime). A copy flushing to disk (`fsync`, one call that can't report progress) gets a size-scaled stall limit (`_CopyJob.stall_limit`). SQLite connections set `busy_timeout` (`db/engine.py`); WAL is deliberately not used (sidecar files break copying/moving the DB, and it is unreliable on network/WSL drives). `save_config` is atomic (temp file + `os.replace`) because transfers rewrite config.toml while requests read it. Frontend: Settings → Storage → Tasks (`TransfersTab`, `NewTransferModal`), polling `/store/transfers`.
- **A deleted record's files are outside every placement policy, not every safety one.** What a collection's files are, for the storage report and its gather suggestions (`volume_breakdowns`), collection moves (`shas_for_collections`, `collections_using`), sync's background download (`_not_here`, `files_by_collection`) and uploads (`referenced_shas`), is what its **live** records use; a restored record's files count again. Clean-up (`referenced_subset`) still keeps them and emptying a drive (drain works from the drive's contents) still moves them, so nothing Recently Deleted can bring back is lost. A file's own details (`usage`) list every user.
- A missing volume root is **never created on demand** unless the volume is a relative path inside the project (`_ensure_volume`); and reconcile skips unreachable volumes, so an unplugged drive never loses its inventory rows.

### Files by name and folder

Files are stored by hash, but people think in records. `FileAccessService` (`services/file_access_service.py`, `ctx.file_access_svc`) turns a **selection** (`domain/file_access.FileSelection`: a `RecordQuery`, or exactly `record_ids` for ticked rows, plus optional `fields` and a `base`) into a **plan**, then optionally an export. `civex files list|export`, `POST /file-access/plan|export|zip` and the explorer's **Open files in folder** / **Download zip** (`components/files/FileAccessActions`) all go through it.

- **One path rule**, `domain/file_access.py` (pure): the names of the records above a file (`RecordDTO.natural_name`, so what the UI shows), then the file's `resolved_filename`. The record that holds the file is itself a folder, so many records each holding `table.txt` can't clash. Paths start below `base` (`query.within` by default); across several collections the collection name leads. `folder_segments` appends a short id only to siblings whose names clash (case-insensitively); `file_names_in_folder` tells apart same-named different files and drops identical repeats. Don't write a second path rule for a new surface.
- **Plan before action.** `plan()` makes nothing and says what is unreachable (`FilePlan.unavailable`, grouped by drive with the volume's own `reason`/`fix`, taken from the `location` that `_attach_file_locations` already stamps). `export()` raises `FilesUnavailableError` (the API answers 409 with the plan, the CLI prints it and exits 1) unless `allow_partial`; the UI plans first and only interrupts when something is out of reach. A partial folder carries `MISSING.txt`.
- **Never searches or walks.** Sources come from `FileObjectStore.path_on(sha, volume)` (pure arithmetic from the inventory's volume), not `_locate`. Records come in pages (`stream_records`), ancestors one lookup per level (`RecordService.ancestor_trails`), ticked rows in one (`get_many`), file values in one pass over the schema resolver (`file_values`); `test_a_big_selection_costs_a_fixed_number_of_queries` holds it constant. Export works a folder at a time (one directory read of what an earlier export left, one mkdir) and re-export uses the `.civex-export.json` marker (path -> sha) instead of reading the tree back; no new indexes were needed (`records.id`, `ix_records_parent`, `stored_objects.sha256`).
- **Export: links on the files' drive, or copies on one drive.** `export_managed(selection, name, mode, volume)`: `link` makes **hard links** in `<volume>/_exports/<name>` (`_civex/exports/<name>` for a volume inside the project) on the one drive that holds the files, so there is no copy and Windows/WSL see ordinary files; it **refuses** (`FilesScatteredError`, API 409 `files_scattered`; `FilePlan.scattered`/`by_volume`/`link_volume`) when the reachable files are on more than one drive, and `LinksNotPossibleError` (409 `links_not_possible`, found by `_probe_link` before anything is built) when the drive can't link (exFAT/FAT32, read-only, other filesystem). `copy` writes real copies on `volume` (project if none), wherever the files are, after `_check_room`. **There are no symlinks**: they dangle when a drive is unplugged and WSL's can't be followed or deleted from Windows. `_exports` is skipped by the volume scan (it reads only 2-hex shard folders).
- **Looking after exports.** A folder is ours if it has `.civex-export.json` (path -> {sha, how: hardlinked|copied, size}; also `civex_version`, `format` (the file's own layout, 2), `mode` and `updated` in Zulu time `YYYY-MM-DDTHH:MM:SSZ`); `export` refuses a folder with other files, re-export is incremental and prunes, and `list_exports()` reads only the folders directly inside the known roots and each marker (never the files), so no walk and no registry table. `remove_export` removes exactly the marker's files (a link, never its target; a path in the marker that leaves the folder is ignored), keeps anything the user added (and so the folder), and reports freed bytes (copies only). `civex files exports list|remove`, `GET /file-access/exports`, `POST /file-access/exports/remove`, the **Made** tab of the Exports page (`ExportsList`).
- **UI flow: flat, one dialog.** `FileAccessActions` is the **Export** menu (saved exports, **Export…**, Set up exports… and Manage exports… which *navigate* to the Exports page; there is no separate table-as-CSV item: a table is part of the one dialog). Saved and one-off exports open `ExportDialog`, which is the schema builder (`ExportBuilder` in `components/exports/ExportDefinitionBuilder.tsx`, shared `ExportSteps`/`MethodStep`) in *run* mode: What · Layout · Finish, finishing with the method (link / copy + drive / zip) rather than a name; a saved export opens filled in at Finish. `useExportHost` owns the dialogs; `ExportButton` opens them from a plain button. The explorer groups Columns and Export with the saved-views bar. Every action is one request through `components/files/fileFlows.ts` (`openAsFolder`, `chooseCopy`, `downloadZip`, `copyToDrive`, `moveThenOpen`), run as a **file job** (`hooks/fileJobs.ts`, a module-level store, so it outlives the component). There is no separate "checking" request: the export call itself answers, and a 409 with a known `code` (`files_unavailable`, `files_scattered`, `links_not_possible`, via `problemFrom`/`tryExport`; `ApiError.body` carries the plan) opens the **one** dialog (`FilesDialog`): what is held and where, what can't be reached (**Check again** in place), and the way forward (link / move then link / copy; `DrivePicker` + `useDriveChoice` are the one drive-and-free-space rule). `moveThenOpen` queues the existing `files` transfer, follows it (`waitForMove`, progress in the bar) and then links and opens, so it is one action for the person. `useFileJobTasks` shows a job in the status bar only after `FILE_JOB_SHOW_AFTER_MS` (1 s; `useBusyFor` is shared with automation). `reportExport` is the one place that says what an export did.
- **Where the menu is.** The explorer (the listed schema has file fields; ticked rows or the current query; the active view's layout), a **record page header** (`selection {within: record.id}`, no schema: every file under the record, via `schemaTreeHasFiles`), and each saved export on the Exports page. **Exports are saved with a schema.** `export_definitions` (migration `d9f3b1c7e4a2`; `ExportDefinitionDTO`, `LocalExportDefinitionRepository`, `ExportDefinitionService`, `ctx.export_def_svc`): schema, optional holder kind (None = any kind beneath), file fields (empty = all), a filter tree (the views/queries format, validated through `RecordService.resolve`) and a layout. It says nothing about a collection or record: those are where it is *run*. `_check` validates the whole definition (holder must be the schema or beneath it and able to hold files; fields must be file fields it has; a filter needs a holder; layout in `LAYOUTS`) on create and every update. `available_on(schema)` = definitions saved with that schema or one above whose files are at or beneath it (an Encounter's export runs on Encounter, Recording and Selection records); `for_collection` = those saved with the collection's schemas. `selection(definition, collection, within)` is the `FileSelection`; with no holder it sets `FileSelection.schemas` so "any kind beneath" stays in the schema's own tree (`_select_records` honours it). API: `/schemas/{s}/exports` CRUD, `GET /file-access/definitions?schema=|collection=`, and `export: "schema/name"` (+ `collection`/`within`) on any file-access request. CLI: `civex schema exports list|show|add|set|remove`, `civex files list|export|gather --export schema/name`. UI: **the Exports page** (`/exports`, `pages/ExportsPage`, sidebar *Exports*; tabs **Saved** and **Made** in the address, `?schema=` narrows the list and `?collection=` is where **Run…** runs). `components/exports/SavedExports` is the **one** place exports are defined, changed, deleted and run, and it lives on the page only: **a schema has no Exports tab** (an old `/schemas/<id>?tab=exports` link redirects to `/exports?schema=<name>`). ### History (audit log) and revert

`audit_log` rows hold, per `audit_diff.stored_form` (the one rule every writer follows), the thing whole for a create (`new_data`) or a delete (`old_data`, so what was lost can be shown), and for an edit or restore only what changed (`format` 2: `delta` = `{path: {before, after}}`, `path` an attribute or `data.<field id>`, a side left out where absent; `new_data` keeps just the thing's identity, `audit_diff.IDENTITY_KEYS`, so titles and the id-in-snapshot filters still work). Entries v1.2.0 and earlier wrote whole are converted after opening, never in a migration (`HistoryCompactionService`, run by the server's `history_jobs` thread or `civex history compact [--vacuum]`; each entry must read the same as a delta or it is kept whole, `format` 3; it walks the partial index `ix_audit_log_still_whole`, migration `a4d9e2c7f310`, so batches and the count touch only what is left: a 300k-entry v1.2.0 project opens in ~1 s and converts at ~2000 entries/s). `GET /audit/storage`, `POST /audit/storage/reclaim` (SQLite VACUUM), Settings → Database **History storage**, the status bar's *Tidying history*. `tests/db/test_upgrade_from_releases.py` opens real v1.1.4 and v1.2.0 databases (`tests/fixtures/upgrades/*.db.gz`, made by that release's code with `make_fixture.py`) and checks data, conversion and (from 1.2.0) replay; add one per release. **Read an entry only through `audit_diff.entry_snapshots(old_data, new_data, delta)`**, never the columns: `make_delta`/`apply_delta` are exact (`apply_delta(old, make_delta(old, new)) == new`, 1 vs 1.0 kept), and `tests/domain/test_audit_delta.py` plus `tests/services/test_audit_delta_entries.py` hold that a delta reads back as the same changes, revert, filters and search. Entries written before this (v1.2.0) are whole snapshots (`format` 1) and read the same way. The API serves `old_data`/`new_data` as `entry_snapshots` gives them, so a reader comparing the two sides sees only what changed. `tests/services/test_audit_replay.py` replays each thing's entries from its create in write order and must reach the database. `audit_log.local_seq` is the order entries were written, numbered by the database (sequence on PostgreSQL, trigger on SQLite; migration `e8b4f2c6a917`, which a batch rebuild of `audit_log` would drop), and is what changes are sent in (`sync_repo._WRITE_ORDER`), never wall-clock time or `rowid`. The entry's *diff* is never stored. `domain/audit_diff.py` (`diff_entry`) is the one place a diff is made, and `AuditService` (`services/audit_service.py`, `ctx.history_svc`; `ctx.audit_svc` is still the raw `LocalAuditRepository`, used by sync and `status`) is the one place it is served: every audit endpoint and `civex history` read through `page`/`get`, which attach `changes` (`AuditLogDTO.changes`, response-only, never in a sync bundle) with the field's current label/dtype and in schema order. Record snapshots are **field-id-keyed**, as the record is stored (`RecordService._snapshot`, no name conversion on write), for every action, so an entry means the same after a field is renamed; `AuditService._by_field_name` turns the ids into the field's *current* name when it builds `changes`, and an id that belongs to a deleted field stays an id (a live field may have taken its name) and is labelled by `_diff` (`Change.deleted`: `deleted` = restorable, with the schema to restore it on, or `gone`). The served `old_data`/`new_data` are the stored snapshot (ids); `changes` is the readable form. Entries from before this kept names and are read as they are. A collection's snapshot carries `schema_ids` beside `schemas` for the same reason. Entries also carry `actor` (the OS user, `civex/identity.py`, unverified). **History is complete, and a test says so**: `tests/services/test_audit_replay.py` runs every kind of change and checks that the last entry about each schema, field, collection, view and record equals the database (the one thing sync will send is these entries). Anything that changes one of those must write an entry for it, including a *side effect on another thing* (`SchemaService._rewrite_templates` logs each template it rewrites in other schemas/fields; `reorder_fields` logs each field that moved). A schema/collection delete or restore writes an entry for each record it stamped or brought back (`services/cascades`, in the same action and batch, so Activity shows one event). Deliberate non-entries: purging a schema takes its fields with it, a collection's `schemas` names are derived from `schema_ids`, and views are removed outright (their `delete` entry is the whole story). `DERIVED_FILE_KEYS` (`domain/dtos.py`) are ignored by the diff, so an echoed-back file isn't an edit. `scope_of(kind, ref)` resolves a record/schema (its own fields)/collection to the list scope, so routers and CLI share it.

Revert is record-only: `plan_revert` is the single rule set behind the UI preview (`GET /audit/{id}/revert`), `POST /audit/{id}/revert` and `civex history revert`, and `revert` applies it **only through `RecordService.update/delete/restore`**, so validation, reference checks, triggers and a fresh audit entry all happen (a revert is itself revertible). Per field: `apply` (still as the entry left it), `conflict` (edited since; only with `force`), `same`, `skipped` (field gone, or a file whose bytes were GC'd: history-only blobs aren't GC roots). Reverting an update sends the *whole* merged data, since `RecordRepository.update` replaces `data`. Schema/field/collection entries are readable but not revertible. Frontend: rows of `AuditTrail` open `AuditEntryDialog` (full `changes` via `AuditChangeList`, then a `RevertPanel` that shows the server's plan before confirming); `utils/recordAudit.tsx`, `schemaAudit.ts` and `collectionAudit.ts` now only supply titles. **Activity** (`/activity`, `ActivityPage`, sidebar *Activity*) is one list, `ActivityFeed`; there is no separate Recently Deleted page (`/trash` redirects to Activity with **Deleted** on). The same `ActivityFeed` is a record's History tab (scoped `under` that record) and a collection's Activity tab (scoped `collection`); a schema's History stays `AuditTrail`. **Deleted** is a toggle on the feed: it adds `now = deleted` and `change = delete` to the filter (`utils/auditFilter.ts` `toggleDeleted`), so what is waiting to be restored is just history narrowed, and an item's row has **Restore** (the `RestoreDialog`) and its dialog **Delete permanently**. *A delete is not all-or-nothing.* `RecordService.restore(id, only_this=, with_parents=)`: by default a record comes back with what was deleted with it (`_restore_group`) and is refused while a deleted record is above it; `only_this` leaves its children deleted, `with_parents` brings back the deleted records above it (`_deleted_above`, each by itself, no sibling expansion) so one selection can return without the other 59. `restore_plan().parents_needed` says how many parents that is. `restore_records(ids, with_parents=True)` (`POST /records/restore-selected`) restores *exactly* the chosen records plus the parents they need, in one pass (`_restore_blockers`, fixed-point so a record whose parent is itself held back stays); the bulk-delete window (`BatchDialog`) ticks records and calls it. The set-level planners (`plan_restore_set`/`restore_set`/`restore_records`) look everything up together: per-record `restore_plan` was ~18 queries each, which made "Restore everything" on a 70-child delete a thousand-query spinner (`test_describing_and_undoing_a_bulk_delete_costs_the_same_however_big_it_is` holds it constant). A bulk delete's one line has its own **Restore** (with **Choose which…**, and **Restore everything…** in its window): `RestoreBatchDialog` calls the same restore-all with `batch=<batch id>` (`AuditService.plan_restore_all`/`restore_all(batch_id=)` → `AuditFilter.batch_id`), so a record and everything beneath it comes back parent-first as one `restore` event. With it on, **Restore all N** restores everything the filter matches: `AuditService.plan_restore_all`/`restore_all` (`GET`/`POST /audit/restore-all`) take the same filter, add the two conditions server-side, restore collections, then schemas, then records in rounds (a record under another in the set comes back with it, or once it has; one still under a deleted thing outside the set is *blocked* and reported), as one `restore` batch.

*History is filtered like records and runs, with their machinery, not its own.* `domain/audit_filters.py` declares `AUDIT_FIELDS` (`when`, `kind`, `change`, `how`, `collection`, `schema`, `under`, `now`) once, as `run_filters.py` does, and `parse_audit_filter` checks a `domain/filters.py` tree against them; `GET /audit/filter-fields` serves them, `GET /audit/events?filter=&q=&sort=` takes the tree, and the UI is the explorer's `FilterControls` over `runFilterFields` (`utils/auditFilter.ts`), with the page's own scope AND-ed in (`withScope`) and not shown as a chip. `AuditFilter` (`domain/audit_filter.py`, like `RecordQuery`) carries the fixed scopes plus `where`; `AuditService._resolve` turns what a person picks into what the repo tests (a collection or schema *name* becomes its id so a rename can't lose history, and `schema` matches the schema's own entries plus any snapshot whose `schema_id` is it, i.e. its fields, views and records of exactly that type; `under` becomes the record and everything beneath it, live or deleted) and `audit_repo._condition` maps each field to SQL (`under`/`collection` also match snapshots that *name* the id, which is how a purged child is still found). `now` (live | deleted | gone) is answered from the records table; `AuditLogDTO.now` / `AuditService._where_now` say it on each single entry, one lookup per page, so a lost record can be told from an edited, deleted or purged one.

*Bulk operations are one event.* `audit_batches` + `audit_log.batch_id` (migration `f2a6c8d1e093`; local only, not in a sync bundle). `LocalAuditRepository.batch(kind, label, ref)` creates the batch lazily at the first write inside it and joins an enclosing one, so a workflow run that deletes a tree is the run's one event. The server opens batches for record delete/restore/purge of more than one record (`_audit_batch`) and for each workflow run (`background.run_pending_jobs`, `cli.utils.run_job`); the browser import opens one with `POST /audit/batches` and sends `X-Civex-Batch` on each request (`get_ctx` joins it; an unknown id is ignored). `list_events` groups by `coalesce(batch_id, id)`; a batch reports `parts` (counts by kind and action), its entries are paged at `/audit/batches/{id}/entries`. A collection or schema delete is still one entry, since its records are stamped by the cascade, not logged. Batches can't be reverted yet (only single record changes can).

*Where a thing is now.* `now` is live | deleted | gone for a record, a collection or a schema (`audit_repo._now_is`, answered from those tables, and `AuditService._where_now` on each single entry with `ref`, the id or name to restore it by). **Permanently deleting a record deletes every audit entry about it and leaves one tombstone**: `RecordService.purge`/`purge_records` call `forget_records` (all its entries, then any batch left empty) and log one `purge` entry whose snapshot is `audit_diff.tombstone` (id, collection, schema, parent, created/deleted times, `"tombstone": true`, no `data`), so nothing it held survives in history and `now` is *gone*. A collection or schema purge deletes its records' entries (`forget_records_matching` on `"dataset_id"`/`"schema_id"` in the snapshot) and its own `purge` entry is the tombstone. Records purged before this are cleaned by `RetentionService.forget_purged` (`POST /retention/purged-history`, `civex retention forget-purged`, shown on Settings → Retention only while any remain), which keeps or makes one tombstone each. `civex trash list` is history filtered to deleted, in the CLI.

*Records out of sight (orphans).* A live record under a deleted record is listed by nothing above it and refused by a sync server; today's edits can't make one (a single restore under a deleted parent is refused), but history can (a record restored by itself before that rule, a cascade applied before cascades synced). `RecordService.deleted_above(id)` (the deleted records directly above a live one, topmost first), `restore_above(id)` (the one way to put one back in place: those records each by itself, so their other children stay deleted; checked, logged and synced like any restore) and `orphans(limit)` (`RecordRepository.live_under_deleted`). Surfaces: `RecordResponse.deleted_above` on a single fetch and the record page's `OrphanBanner` (**Restore …** / **Delete this …**); `GET /records/orphans`, `POST /records/{id}/restore-above`; Settings → Database **Records under a deleted record** (`OrphansCard`, shown only when there are any); `civex doctor` (counts them as an integrity issue), `civex record orphans|restore-above`. A refused record that sits under deleted records here offers the take `restore_above` (`SyncConflictDTO.sits_under`, added by `SyncService._describe`/`_sits_under`): it restores them and resends, and the server's resulting edit-vs-delete answer is not raised as a new item (it is what was asked for).

### Sync (CIVEX-305; star topology, one authority per project)

A project follows an **authority** (a normal `civex serve` with `[sync] serve = true`); devices send their `audit_log` entries and receive the authority's numbered feed. Pieces: `domain/merge.py` (pure three-way field-level merge: base = `entry.old_data`, `data` merged per field id, lifecycle/derived keys excluded), `domain/hlc.py`, `domain/sync.py` (wire types, `PROTOCOL_MIN`/`PROTOCOL_MAX`, `WIRE_FIELDS`, `SyncError.status`), `SyncAuthorityService` (who is calling comes from an `Authenticator`, `DeviceKeys` here, see **Who and what may**; `push` merges/numbers/answers, the `sync_ops` ledger answers a repeat with the stored result, DEFERRED ops (a cited file is missing) aren't stored and stop the batch), `SyncService` (client: `connect` = join/seed/empty/resumed, `sync`, lazy pull, conflicts), `SyncApplier` (applies entries by whole snapshot, so applying twice is harmless), `LocalSyncRepository`, `HttpSyncTransport` (urllib), `routers/sync_peer.py` (`/api/sync/v1/*`: hello, push, feed, snapshot/{kind}, files/missing, PUT/GET files/{sha}; 404 unless serving, then protocol and session checked; `join` and `session` take no session), CLI `civex sync ...` / `civex clone`. Tables: `sync_meta`, `sync_ops`, `sync_devices`, `sync_conflicts` (migrations `c9e1f4a7b3d2`, `d6c2a8f41b07` for a conflict's base and who wrote the value that stayed).

- **Conflict policy:** the authority's value stays; the loser is kept in `sync_conflicts` **on the device whose change did not go in** (the authority keeps no list: its answer to a push carries each clash, `OpResult.conflicts`, and `SyncService._note` is the one writer of the rows, for clashes and refusals alike); edit-vs-delete keeps the record; schema changes are serialised by the authority.
- **What the authority accepts:** `domain/sync.problem_with` is the one shape check for a change (kind, action, snapshots are objects, readable time, a valid `hlc`; a delete stamped more than an hour ahead is refused): one odd change is `rejected` by itself, never failing the push (`_settle` also turns `ValueError`/`TypeError`/`KeyError` from a snapshot into a refusal). A stamp that can't be parsed would make every later `hlc.tick` fail, so `hlc.is_valid` gates it and one far ahead is replaced by one the authority issues. A record is held to what a person's edit is by `RecordService.check_incoming` (restrictions, references, unique keys, schema allowed in the collection, parent), called by `SyncAuthorityService._take` before the write; writing the state stays `SyncRepository.apply_snapshot` (id-keyed and exact, no defaults, history or triggers) and a device does not re-validate what the authority settled. Not yet checked: schema, field, collection and view changes.
- **Reviewing conflicts** (`SyncService`): `conflicts()` returns `SyncConflictDTO`s described by `_describe` (record name, collection, schema, field label, the value now, `stale`, `takes`, `also_saved`; worked out on read from `RecordService.field_values`, never stored). `resolve_conflict(id, take, value, force)`: `theirs` (nothing to do), `mine`/`value` (`RecordService.patch`, so it is checked, in the history and syncs; refuses with `ConflictMovedError`, API 409 `conflict_moved`, when the value is no longer the one that stayed unless `force`), `delete`, `retry` (`_resend` logs a fresh entry from the thing as it is, on the refused entry's starting point). `_takes_for` is the only rule for what a row offers; the UI reads `takes`. `RecordService.patched_data` is the one "change only these fields" rule (plugin `patch_record` uses it). `resolve_many(take, ids=, kind=, entity_id=, force=, dry_run=)` is the one bulk rule (`POST /remote/conflicts/resolve-many`, `civex sync resolve --all`): it reads `find_open_conflicts` (no page limit, unlike `conflicts()`, which stops at 200), leaves a row that doesn't offer the take (`not_offered`) or fails its checks (`failed`) open, and for `theirs`, which is bookkeeping, is one statement and one commit; `dry_run` only counts. `reopen_conflicts` (`POST /remote/conflicts/reopen`) takes back only `theirs`, since the other takes made edits that are undone from Activity. A refused change or an edit that met a delete carries `attempted` (create/update/delete) and `changes` (`_attempt`: each field it set with before, after and the value now), response-only like the rest of `_describe`, so a screen shows the attempt where the record already is; `edited` is accepted for a clash (not in `takes`, so no button) and closes it once the person has set the field themselves. History carries the same facts: `AuditLogDTO.sync` (response-only, from `SyncService.conflicts_of_entries`, injected into `AuditService` as the `sync_conflicts` callable so history doesn't know sync; one `conflicts_of_ops` lookup per page in `_with_changes`) lists what became of each change that did not go in as made, open or settled, and a delete that met an edit lists the record as it was and as it is now (`_attempt`, `_NOW`). `GET /remote/conflicts?record=` narrows to one record. Frontend: **the record page is the one place a conflict is settled.** `components/sync/MergeView` is a Resolve tab on `RecordDetailPage` (shown while the record has open conflicts, and while rows settled this visit are still on screen): rows from `utils/syncMerge.buildMerge` (clashes together; each refused change or edit-vs-delete its own block with `describeAttempt`'s sentence and its takes), other side left, the field's own `EditableValue` (exported from `RecordFieldGrid`, so every dtype and restriction is the usual input) in the middle, this device's right, differences marked by `DiffValue` (`utils/textDiff`: word LCS, item sets for lists, whole-cell otherwise); saving the middle by hand sends `edited`; `useMergeConflicts` reads open ones plus those settled since the page opened (`status=all&record=`). `ReviewStepper` wraps every record page of a review (`utils/reviewSession`, sessionStorage: the ordered records, ticked when nothing is left) and starts when the Resolve tab opens or **Start review** is pressed. `RecordConflicts` is only the Fields-tab banner with a way in, and the grid marks clashed fields (`marked`, `layoutConflicts`). `pages/SyncReviewPage` (`/sync/review`) is the inbox only: a list with a **Resolve** link per record, `?kind=` filter, ticked-row bulk, **Keep theirs for all/these** (the filter, not the loaded ids, after a dry-run count, with **Undo**); a row with no record page (a schema's refused change, a deleted record) settles in the row. Activity: `SyncBadge` on a row and `SyncOutcome` in `AuditEntryDialog` show the same left/right. A sync failure is **not** toasted (`utils/syncToast`): the status bar (`useSyncTasks`) holds failures and values to review with their actions, and a toast is only good news that passes. `hooks/useRemote.ts`. When the settled state differs from what was sent, the authority emits a "settled" entry (actor `sync`) and flags the op entry `superseded`.
- **`audit_log.apply_state`** is `applied`, `held` (an authority change kept but not applied because this device has an unsent change to that thing) or `superseded` (never applied). `_catch_up` applies the *latest state-carrying* entry per free thing, then a trailing delete/purge; applying an older entry over a newer would roll the thing back (the randomized convergence test, `tests/sync/test_convergence.py`, exists for exactly this; `CIVEX_SYNC_SEEDS=300` runs more seeds).
- **Files and data converge separately.** A change is never held for a file: the authority takes a change citing a file it lacks (it does not defer), and the device uploads what it can read. Nothing about files owed is stored: `SyncService._send_missing_files` works it out each time from the `file_references` catalog (`LocalSyncRepository.referenced_shas`) and the authority's `missing_files` answer, so a drive plugged back in or files added later are just found. It costs a request per 1000 referenced files, so the background worker does it every `FILE_CHECK_EVERY` (10 min, in memory) and a manual sync always does. Don't reintroduce holding changes for files (a lost file is permanent and would block a record forever) or a persisted owed list. **A device fetches the files others added** (`SyncService.fetch_files`/`fetch_file`, the one rule; what is missing is worked out each time from `file_references` with no `stored_objects` row, `sync_repo.files_not_here`, never stored): in the background when `[sync] download_files` is `all` (the default; `SyncWorker._fetch_files`, `FILES_SECONDS` a tick, files the authority lacks skipped until the next file check, progress phase `files`), when opened (`GET /files/{sha}` fetches before answering, 503 if the authority can't be reached, 404 if it hasn't got the file either), and before an export (`FileAccessService.plan(fetch=True)`, used by every export/zip/download/gather path but not the preview; `fetch_missing` is injected in `context.py` so file access doesn't know sync). Downloads go through the store's `put_path` with the file's collection, so placement and dedup apply. Meanwhile its `location` is `state: remote` (`RecordService.files_from_server`). **Per collection** (`SyncService.collection_mode`, the one rule): a collection keeps its files here (`keep`) or fetches them when opened (`opened`), from `[sync.collection_files]` in config.toml (keyed by collection id), else the project's `download_files`. The background download and `files_to_fetch` cover only kept collections (`_kept_collections`); a file asked for by hash (opened, exported) comes whatever its setting. `collection_files()` is the report (here: files and bytes; only on the server: files, since a file not here has no recorded size; `sync_repo.files_by_collection`, one grouped catalog query). **Freeing space** (`free_up(collection, dry_run=True)`) removes this computer's copies only of files the server confirms it holds, asked at that moment (`missing_files`), never one a kept collection also uses (`used_by`), under the store's `gc_lock` (so not alongside a clean-up or file move), and sets the collection to `opened` first so the background download doesn't refetch them. `civex sync files [all|opened]` (table), `civex sync keep <c> [--opened|--reset]`, `civex sync free <c>`, `civex sync fetch`; `GET /remote/files`, `PATCH /remote/files/{c}`, `POST /remote/files/{c}/free-up?dry_run=`; Settings → Storage → Collections (`ComputerFiles`: `ComputerFilesDefault`, `ComputerFilesCell`, `FreeUpDialog` counting first). An authority fetches from nobody.
- **Deletes** use one stamp for both the entry timestamp and `deleted_at`, so every device stamps identically; deletes/restores don't bump `updated_at`.
- **What the authority answers is already saved, and it takes one push at a time.** The peer routes take `get_ctx` with `Depends(..., scope="function")`, so the commit runs *before* the response (with the default it runs after, and a failed commit would still have told a device "done", which then never resends; `test_peer_api`). `push` starts with `SyncRepository.lock_feed()` (a no-op write on `sync_meta`: a row lock on PostgreSQL, the write lock on SQLite) so two pushes can't merge with the same state and overwrite each other, and `_write_entries` numbers the authority's own unnumbered edits (`sequence_local_entries`) right before a pushed change, since one saved while the push merged is already inside it. The other 160 `Depends(get_ctx)` in the app still commit after answering.
- **Changes travel as deltas, and a device replays them.** A pushed edit carries `SyncEntry.delta` (identity in `new_data`); the authority rebuilds both sides on what it holds (`sync_authority._sides`: untouched values are equal on all three sides of `merge`; an edit's result is not deleted unless it says so, so edit-vs-delete keeps the thing), so an edit to another field than a concurrent one now goes in `applied`, not `merged`. The entry the authority writes after a clash, merge or refused delete (actor `sync`) stays **whole**: the device whose change lost holds values nobody else does, which a delta from the authority's state would leave. A device applies the authority's numbered, non-superseded entries for a thing **in order** (`SyncService._replay`, from `SyncRepository.numbered_entries`; `SyncApplier.apply_entry` puts a delta onto the thing as it is here): on arrival from that entry on (re-taking its own later-numbered changes, harmless), and in `_catch_up` from the first held one. That one rule replaced `has_newer_state`/`_reapply_later_delete`/pick-the-last-state; `CIVEX_SYNC_SEEDS=300` passes.
- **What a project must still be, whatever made the change (cross-kind rules).** The authority holds a change from a device to what a single machine enforces on an edit, about what it touched *after* writing it: `services/project_rules.ProjectRules` (naming and file-name templates use only fields that exist; unique keys name the schema's own live fields and no live records share one; a collection lists the schema of every live record in it, and every listed schema's ancestors). A create is not asked (`_changed`: an empty authority is filled schemas-before-fields). `RecordService.check_incoming` also refuses a live record inside something deleted (its schema, its collection, the record above it): an edit that meets a delete keeps the record itself, never revives it into a deleted container. **One action, taken whole:** entries one action writes share `audit_log.op_id` (migration `f1c3a5e7b902`; `AuditRepository.operation()`, `SchemaService._one_action` on add/update/delete/restore field and reorder, one per tree in record deletes and restores (`_tree_actions`, restores logged parents first), schema/collection delete/restore with their records); `SyncEntry.op`; `pending_entries` and `_at_most` never split one; `SyncAuthorityService._settle_action` settles the run in one savepoint and asks the rules once at the end. An action that can't go in whole: a record-tree delete that met an edit keeps the whole tree (edit-vs-delete for each, `_keep_instead_of_delete`); anything else is answered `not_taken` for what exists here (`_put_back`: the authority's state is sent back, so the device converges instead of sitting half way; a person redoes it) and `rejected` for what doesn't. A refused single change to a schema, field, collection or view is `not_taken` too (records keep `rejected`, with Retry/Use mine). A record whose create was refused (a value its field no longer allows there) can't be edited on the authority, so while it was never taken (`SyncRepository.never_taken`) the edits made to it since go as one create of it as it is now (`SyncService._send_whole`; the others are `mark_folded`): fixing it is what sends it. A thing has at most one open refusal: refused again, the open item is renewed in place (`renew_refusal`, newer reason and change), and going in settles it as `sent` (`_note`). **Send again** (`retry`) does not settle anything: it marks the item `retrying` (still open) and asks for a sync (app: `sync_jobs.sync_now`, CLI: syncs at once), and the answer settles it. A refusal names the field it is about when it was a value (`FieldValueError.path` → the authority's `OpResult.conflicts` → `SyncConflict.field`), and the Resolve tab shows a refused record as `RefusedFix` (the reason, that field editable with what it allows; no sides), not as a diff. Following another authority clears the old one's numbers (`forget_numbers`). Retry of part of an action resends the whole action (`_resend`). **Cascades are entries:** a schema's or collection's delete or restore logs an entry per record it changed, in its action and batch (`services/cascades`); when the authority applies one from a device it writes an entry for each record it changed here that the action didn't cover (`_write_cascade`, actor `sync`); a delete applied to an already-deleted record takes the entry's stamp (`sync_repo.soft_delete`). Without these each copy worked out cascades from what it held and copies disagreed. A schema's or collection's restore brings a record back only where it could be added: not under a parent still deleted, and only if its collection still lists its schema (`record_repo.parent_allows_restore`, used by both repositories and so by sync, whose `restore` delegates to them); `check_incoming` asks the schema list and the parent of a record being made or brought back (not of a plain edit: a record left live under a deleted parent by deleting a parent schema stays editable, as on one machine). A record delete that meets a live record added beneath it on the server keeps the record (`_added_beneath`, edit-vs-delete). An edit that goes in without clashing takes its `updated_at` on the authority even when all its values were already there, since every copy applies the date with it. Not yet: restoring a *single* record locally doesn't check its collection's schema list (a device's such restore is refused by the authority). `tests/sync/test_invariants.py` (random structural and record changes on three devices; every rule above must hold on the authority and copies must agree, except what has an open review item on that device) and `test_cross_kind.py` (the cases one by one) hold all of this.
- **Joining and seeding while in use.** Snapshot pages follow on from a thing (`after` = `domain/sync.snapshot_cursor`: `created_at|id`, keyset in `snapshots_page`), never an offset, so something purged between pages can't shift a page past an unchanged thing. `_join` writes a record (or schema) only once the one it sits under is there (`_sits_under`, `_join_one`: children wait by parent id; a clock-skewed child can be older than its parent), marks pre-join entries synced *first*, and leaves later local edits pending. While it copies, the cursor is `JOINING` (-1): `sync` refuses ("connect again") and `connect` copies again (`_plan_connect`), so a feed is never applied to half a copy. A join does **not** download history: it sets `sync_meta.history_from` to the number it copied at, and `fetch_history(progress, pages)` (resumable, from `history_fetched_upto`) fetches it afterwards, a few pages per `SyncWorker` tick (`HISTORY_PAGES`) or with a bar in `civex clone`/`civex sync connect` (Ctrl+C leaves it to the worker).
- **Copying shows progress.** `connect(progress=)` and `fetch_history` report `SyncProgress` (`phase` copying/filling/history, `done`, `total`, `kind`; totals from `Hello.counts`). The CLI draws it with Rich (`cli/sync._connect_showing_progress`). In the server `POST /remote/connect` only checks (`check_connect`: address, invite (joins), protocol, who holds data; 202) and `sync_jobs.start_connect` copies on a thread; `GET /remote` serves `progress`, `connecting`, `connect_error` (in memory). A connect with no invite uses this computer's joined key (the UI's **Try again**). Frontend: `utils/syncProgress.describeSyncProgress` is the one wording, `components/ui/ProgressBar` the one bar (the status bar uses it too), shown by `useSyncTasks` and Settings → Sync (`Copying`). `_seed` covers only the entries pending when its *first* attempt began: `begin_seed` moves them to `sync_state = 'seeding'` (kept across an interrupted seed, because the ledger answers a resent seed op from its first sending) and `finish_seed` makes them `synced`; anything edited meanwhile is sent afterwards as an ordinary change.
- **Local guard:** on a serving project remote hosts reach only `/api/sync/v1/`; everything else keeps the host check even with `--allow-remote` (`security._serving_sync`). That check reads the `Host` header, which a reverse proxy may rewrite, so an authority on a network runs `civex serve --sync-only` (`app.create_sync_app`: the peer router and `/health`, no lifespan jobs, no OpenAPI) behind the proxy, and the app on loopback. A device connects only over `https://` (`http://` only to a loopback host: `sync_service._check_address`, also checked on the stored remote; `domain/hosts.is_loopback` is the one loopback rule).
- **Versions.** A device sends `X-Civex-Protocol: <min>-<max>` (`protocol_header`); `sync_peer.peer` picks the newest both speak (`agree`) or answers 426 with `{message, protocol_min, protocol_max, server_version}`, which the transport turns into "update civex on the server / this computer" (`protocol_mismatch`, the one wording). `Hello` carries the agreed version, the range, `server_version` and `CAPABILITIES` (optional features: adding one is not a protocol change). `FeedPage.from_dict` stops a sync, without moving the cursor, on a kind or action this civex doesn't know. **What travels is `WIRE_FIELDS`**: `sync_repo._dicts` and `_entries` (`SyncEntry.on_the_wire`; a purge's tombstone travels whole) emit only those, `problem_with` refuses a change carrying anything else, and `tests/sync/test_wire_shapes.py` holds them to the columns (`_NOT_WRITTEN` = local-only) and to `tests/sync/wire_shapes.json` for `PROTOCOL_MAX`: changing them means raising `PROTOCOL_MAX`, recording the new shape, and serving the previous version what it can read (an adapter in the peer router, not in the core).
- **Who and what may (the hub seam).** `Principal` (`name`, `token_id`, `device_id`, `person`) is what the authority knows of a caller; every settle path takes it. An `Authenticator` (`authenticate(token) -> Principal`) and a `SyncPolicy` (`refuses(who, entry)`, asked in `_problem` beside `problem_with`, so a refusal is answered like a broken rule) are constructor arguments of `SyncAuthorityService`; `context.py` passes `DeviceKeys` and no policy. The author stamped on an entry is `_author`: `person` (proved) wins over the label a device claims, then the device's name.
- **Devices join by invite and sign in with a key** (`services/device_keys.DeviceKeys`, `ctx.device_keys`; `civex/keys.py` is the one Ed25519 module, the `cryptography` dependency; migration `a8c4e2f6b1d9`). The admin invites a device by name (`invite`: `civex_inv_…`, works once, `INVITE_HOURS` by default, only its hash kept in `sync_invites`; one pending invite and one live device per name). The device makes a key pair (`user_state.device_key_for`, beside its device id, moved with it by `move_device`) and joins (`POST /api/sync/v1/join`: invite + device id + public key → `Joined`, carrying the authority's public key, which the device keeps by address: `user_state.save_authority`). It signs in (`POST /session`) by signing `session_request(authority key, device id, unix time)` (within `CLOCK_SKEW_SECONDS`); the authority answers a `SessionGrant`: a token for `SESSION_SECONDS` (device row + expiry + an HMAC keyed by the authority's key, so no table) and its signature over `session_answer`, which the transport checks, so a different server at that address gets nothing. Every other call sends that token (`Authorization: Bearer`); `HttpSyncTransport` signs in when it has no session or it is about to expire and once more on a 401. `authenticate` reads the device row each time, so revoking is immediate. The authority's own private key is `sync_meta.authority_key`, made at the first invite (`has_key` keeps reads from making one). Only `join` and `session` take no token; their failures are counted per caller in memory (`sync_peer._attempts`, 429 past 10 a minute), and `_serving` is a dependency so a server not serving answers 404 whatever the body. `check_connect` joins when given an invite (so the app's background connect needs none); without one the device must have joined that address. `sync_devices` has unique indexes on name and device id among live rows, so a revoked device's name and id can be used again; the same machine joining again replaces itself. Invites start with `INVITE_PREFIX` (a gitleaks rule in `.gitleaks.toml`). CLI `civex sync device invite|list|cancel|revoke`, `civex sync connect|clone --invite`; API `/remote/authority` (with `fingerprint`, `devices`, `invites`), `/remote/authority/invites[/{name}/cancel]`, `/remote/authority/devices/{name}/revoke`; UI `SyncServing` and the connect form's **Invite** field.
- **Recorded author:** `[identity] name` in the project's config.toml (`IdentityConfig`; `civex sync user`, `GET/PATCH /settings/identity`, Settings → Sync), else the OS user (`identity.local_actor(config.identity.name)`); both set it through `identity.choose_name`. **A synced change keeps both facts**: `audit_log.actor` is who made it as the device gave it (a label, kept by the authority after `sync_authority._claimed_author` trims it and refuses `sync`, the authority's own mark), and `audit_log.device` is the device that sent it, stamped by the authority (migration `b5e1d8f2a647`; on the wire as `SyncEntry.device`; the sending device learns it from the feed in `mark_seq`). A device's key proves a device, not a person. Conflicts carry the same pair (`theirs_actor`, `theirs_device`). The UI says it one way, `utils/syncConflicts.byWhom` ("l2 via backup"); Activity shows the device under the name. Entries from before keep the device's name as author and no device.
- **The CLI and the app do the same things through the same calls.** Connecting (`SyncService.connect`/`check_connect`, joining with an invite when given one), serving (`SyncService.set_serving`; `civex sync authority enable|disable`, `PATCH /remote/authority`), devices (`DeviceKeys.invite|pending_invites|cancel_invite|list_devices|revoke_device`; `civex sync device ...`, `/remote/authority/...`, Settings → Sync **Other devices following this project**, `SyncServing`), settling (`resolve_conflict` with `theirs|mine|value|delete|retry`, `resolve_many`, `reopen_conflicts`; `civex sync resolve [--value|--all --kind]`, `civex sync reopen`, `civex sync conflicts [--record]`). A new sync action gets a service method first, then both a command and an endpoint; neither writes config or rules of its own. It is a label only; a synced change is attributed by the authority.
- **Device identity:** the device id and private key (per project) and each joined authority's public key (per address) live in `~/.civex/sync.toml` (`user_state.py`, `CIVEX_USER_STATE` override, mode 0600), never in the project folder.
- **Background sync (CIVEX-308):** `SyncWorker` (`services/sync_worker.py`) is the one rule for *when* to sync (a request, unsent changes 3 s after the last attempt, the `[sync] interval_seconds`; failures back off 5 s doubling to 15 min, a refusal that waiting can't fix waits 15 min; pausing stops the schedule but a request still runs). It is hosted by the server (`services/sync_jobs.py`, started in the lifespan) and by `civex sync watch`; `SyncService.sync` holds the PID-owned lock so two hosts never run at once. `/api/remote/*` (`routers/remote.py`) is the people-facing API (status, connect, disconnect, sync, pause/interval, conflicts, resolve). Frontend: Settings → Sync (`SyncSection`), `hooks/useRemote.ts`, and the status-bar source `hooks/tasks/useSyncTasks.ts` (quiet unless syncing, failing or conflicts are waiting).
- Both-non-empty first sync is refused (merging two projects is not supported).
- **Workflows and plugins are shared, not synced: the library** (`domain/library.py`, `services/library_service.py`, `ctx.library_svc`; table `library_items`, **one row per version**, + `sync_devices.may_publish`; migrations `b2d6f8a3c517`, `e6a2c8f4d1b7` (versions, pins, contracts)). A person *publishes* and a person elsewhere *installs*. **Nothing is written into `_civex/workflows`/`_civex/plugins` by sync or by publishing**, because describing a plugin runs it. The authority keeps text only and `LibraryService.accept` checks it without running it: `name_problem` (no path escape), `content_problem` (256 KB, a plugin parses and defines `Plugin`), the sha256, `provides_problem` (no `civex.` id), `_contract_problem` (a plugin's declared `contract`, a `describe` answer as JSON, must parse, fit 64 KB and be for the id it provides), `parse_workflow` (YAML aliases refused: alias bombs); a publish is taken whole or not at all. **Versions:** new text is the next version (`LocalLibraryRepository.add`; text that is already a version is that version), every version is kept, `latest()` returns each item's newest with its `history`. A plugin keeps its `provides` id in every version (a new id = a new plugin name). A workflow version **pins** `{plugin id: version}` (the versions published with it, else the library's newest), and installing it installs those (`_plan`). **Breakage:** `plan_install` judges, without running anything, what the changed plugins would break here from their declared contracts (`new_breaks`: only errors the change causes, via `validate_workflow_contracts`; the workflow being installed must check out whole) → `InstallPlan.breaks`, which blocks unless `force`; `install` then describes each new plugin from `_civex/.staging/` (`registry.describe_file`, cache by hash; staging is outside `plugins/` so nothing loads it; removed after), refuses one that loads as another id, and checks again. A new plugin version that would break a shared workflow pinned to an older one is a publish **warning** (`_pinned_elsewhere`; `PublishResult.warnings`). Here-status is worked out from text alone (`local_version` by sha against `history`: absent / same / older / different = changed here); only *changed here* needs `replace`. `withdraw` takes one version or all; a plugin version a shared workflow pins stays unless `force`. Who: `who=None` is this computer (may always publish); a device needs `may_publish` (`DeviceKeys.allow_publish`, `civex sync device allow-publish|deny-publish`, `POST /remote/authority/devices/{n}/publish`) and `[sync] library` (`off`|`workflows` default|`all`; `SyncService.set_library`, `civex sync authority library`, `PATCH /remote/authority {library}`); refusals are `NotAllowedError` (403; the transport keeps 403 apart from 401, and reads a 204's empty body). `browse/show/publish/plan_install/install/unpublish` work the same on this project's own library (serving: `_Own`) or the authority's (`_Theirs` over `SyncTransport.library*`; peer routes `/sync/v1/library`, `?version=`, capability `library`). CLI `civex sync library list|show|publish|install|remove` (`-v` version, `--force`); API `/remote/library…` (`GET /remote/library` is `[]` while not sharing). **UI: no separate place.** The Workflows page is `WorkflowsPanel` (search, **Show…** by sharing state, sort, paging in the address; rows are this project's workflows merged with the library's, `utils/workflowSharing.workflowRows`/`sharingState`/`sharingLabel` the one rule; row menus publish/update/install), each row opens **`pages/WorkflowPage`** (`/workflows/:stem`, also for one only in the library; tabs Overview = `WorkflowSummary`, Sharing = `WorkflowSharing`: versions with install/roll back/remove, pinned plugins and how they stand here). `LibraryInstallDialog` reads the plan, shows plugin code, needs "I trust it" for code and "Install anyway" for breaks; `PublishDialog` shows the warnings. The authority's controls are in `SyncServing`. Tests: `tests/sync/test_library.py`, `test_library_api.py`, `test_http_roundtrip.py::test_the_library_over_a_socket`.

*Who made a change.* Every entry written through `LocalAuditRepository` (constructed with `actor=local_actor()` in `context.py`, `civex/identity.py`) stores the **OS user** running civex in `actor`; it is informational and unverified, and older entries are NULL. `AuditLogDTO.actor` / `AuditLogResponse.actor` serve it; the entry dialog shows "by <name>" and `ActivityFeed` leads each row with **Who** (`AuditEventDTO.actor`: the entry's, or for a batch any of its entries', since one person makes a batch), then what happened, then when. `device_id` is not set yet. For synced changes the authority stamps `device` from the signed-in device and keeps `actor` as a label (see **Recorded author**); with real user accounts, a signed-in user becomes the verified author. Entries not yet acknowledged show NULL, meaning "the local user". `device_id` is a random UUID4 generated once, when a machine first connects to an authority, and kept in per-user state **outside the project folder** (keyed by `project_id`) so copying a project doesn't copy an identity; the authority keeps each device's id with its public key. `(hlc, device_id)` is the deterministic tie-break.

### Uniqueness policies

`schemas.unique_keys` (migration `a3d8f0b6c125`) is a JSON list of keys, each a list of the schema's **own** field ids (a child record stores only its own fields), so a rename costs nothing. `SchemaDTO.unique_keys` holds ids and `unique_key_names` the names (what the API, CLI and dump speak). `domain/uniqueness.py` is the pure rule (which dtypes can be in a key: `UNIQUE_DTYPES`, scalars only; a blank in any field means the record isn't constrained). `SchemaService.set_unique_keys` is the one place a policy is defined: it validates, dedupes (same fields in any order = one key) and refuses while existing live records already share a key (`RecordRepository.key_duplicates`); `delete_field` drops keys using the field. Scope is **same dataset, same parent record** (top level: parent NULL), live records of exactly that schema.

`RecordService._check_unique` is the single enforcement point, called from `add` and `update` (a key whose values equal the stored ones is skipped, so an old duplicate never blocks an unrelated edit) and raises `DuplicateRecordError` (a `ValidationError`, so every caller that already skips a bad row keeps doing so; carries `existing_id`/`existing_name`/`fields`). Matching is `RecordRepository.find_key_match` (typed JSON equality; 1 == 1.0). Not enforced by the database, so two simultaneous writes on PostgreSQL could still both pass. **Every path that brings records back goes through `_restore_clashes`** (live clash *and* two deleted records sharing values in the same set): `restore`, `restore_set`, `restore_records`, `plan_restore_set` and `restore_plan` (`RestorePlanDTO.conflict`, a `RestoreConflictDTO`; `can_restore` is false, `blocked_message` says why, `held_back_message` is only the deleted-thing reason so `only_this` can still sidestep a clash). Bulk paths leave a clashing record deleted and report it in `left`/`blocked`. Workflows: `WorkflowContext.create_record/update_record` note a refused write (`duplicates`), and the executor adds `take_duplicates()` to that step's outputs (a context without it, e.g. a test double, has none). Restoring a deleted field does not put back a key dropped when it was deleted.

### Fields are deleted softly

`fields.deleted_at` (migration `b7f2c9a14d36`). `SchemaRepository.delete_field` marks the field instead of removing it; `SchemaDTO.fields` holds only live fields and `SchemaDTO.deleted_fields` the rest, so nothing that reads a schema sees a deleted one. Records keep the value for it in `records.data` (keyed by the field's id), and `RecordService.update` carries those values across a save (`kept` from the stored data), because saving replaces `data`: restoring must bring back the value, not an empty field. `ResolvedSchema.deleted_by_id` (a `DeletedField`: the field and the schema it was defined on, which may be an ancestor) is built in the same parent walk as the live fields (`SchemaService._collect`; a second walk breaks `test_lookup_scaling`). `_ids_to_names` leaves deleted fields' values out of a record's `data`; `_with_names` reports them as `RecordDTO.deleted_fields` (`RecordResponse.deleted_fields`), which the record page shows under **Deleted fields** with the date and a **Restore…** button (`DeletedFieldValues`). A field's name is unique among *live* fields only (partial unique index `ux_fields_schema_name_live`), so a new field can take a deleted one's name; `restore_field_plan` then refuses with `RestorePlanDTO.reason` (nothing deleted is the cause, so no `blocked_by`) and a deleted schema is a `blocked_by` like for a record. `SchemaService.restore_field`/`restore_field_plan` (`POST|GET /schemas/{schema}/fields/{id}/restore[-plan]`, `civex schema restore-field`) log a `restore` entry; Activity treats fields like schemas: `audit_repo._now_is` and `AuditService._where_now` answer live | deleted | gone for them (`now.ref` is the field id, `now.schema_name` the schema), `RestoreDialog` takes `{kind: 'field', ref, schema}`, and Restore all restores fields after schemas and before records (a field whose name was taken counts as blocked). Not yet: a deleted field is never purged (retention and `trash purge-expired` skip it) and has no "Delete permanently". Dump/restore carries live fields only. Template references (`{field}`) removed when a field is deleted are not put back on restore.

### Restoring from Recently Deleted

A delete stamps the thing and everything it cascades to with **one `deleted_at`** (`DatasetRepository.delete`, `SchemaRepository.delete`, `RecordRepository.delete_many`), and restore uses it: `DatasetRepository.restore`/`SchemaRepository.restore` bring back only records whose `deleted_at` equals the parent's, and `RecordService._restore_group` the descendants with the same stamp reached through others in the group, so a record deleted on its own earlier stays deleted. This is the stand-in for batch ids (see below), not a replacement: it breaks if two operations ever share a timestamp. `RecordService.restore_plan` is the single rule for "can this come back": a record is `blocked_by` (`BlockerDTO`) its collection, then its schema, then the topmost deleted record directly above it, and `restore` refuses with `RestorePlanDTO.blocked_message` (the one wording, so the API/CLI/UI agree). `DatasetService`/`SchemaService.restore_plan` give the count of records that would return. `AuditService.plan_revert` of a delete uses the same plan and carries the `blocker`. Frontend: `RestoreDialog` (`components/trash/`) is the only restore entry in the UI: it fetches the plan, says what returns and where, and when blocked offers to restore the blocker instead (a trail, with Back); `useRestore` shows the receipt (what came back, where, a **View** link) and invalidates every cache a restore touches.

### Retention (clean-ups by age)

`[retention]` (`RetentionConfig`): `purge_after_days` (how long deleted items stay restorable), `auto_purge_deleted` (whether a clean-up then deletes them), `audit_days`, `run_days` (None = forever, the default for everything). **Nothing runs by itself** (the server has no scheduler); `RetentionService` (`ctx.retention_svc`; `civex retention show|run`; `GET/PATCH /settings/retention`, `POST /retention/run`; Settings → Retention) is started by a person or a cron, always counts first (`dry_run` is the default), and takes `RetentionCutoffs` from the settings (`settings_cutoffs`) and/or explicit dates per kind (`cutoffs`: a date wins over the setting). Order: deleted collections, then schemas (their records go with them, no purge line each), then the records deleted on their own (`RecordRepository.purgeable_deleted`: never one with a child that stays, nor anything above it), then history, then runs, so the purges just made are the newest history and survive. History (`audit_repo.prune`) keeps entries about anything currently deleted (`_now_is("deleted")`, so *Deleted* in Activity still works), and each thing's creation and latest entry however old while it exists (`_prunable`; pruning once left a live record with no history at all; a thing gone for good loses even its tombstone by age; counted as `audit_kept_first_and_last`) and, with a remote, entries not in a pushed commit; it then drops batches left empty. Runs (`job_repo.delete_finished_before`) are only completed/failed/cancelled ones, removed with their step logs via `bulk_delete_jobs`. Files nothing refers to afterwards are `GCService`'s job, not this one's. Retention's history pruning is by age; permanently deleting a record removes *its* history regardless (see "Where a thing is now"), leaving a tombstone that pruning may later remove by age like any entry.

### Names vs. labels

Schemas and fields each carry a `name` and a `label` (see `domain/naming.py`, mirrored in `frontend/src/utils/naming.ts`):

- `name` — the machine key. Slug-validated (`^[a-z_][a-z0-9_]*$`) on create and rename only. Referenced as text by workflow YAML (`field:`, `schema:`, `reference` restrictions), CSV headers, name templates and API paths.
- `label` — free-text display name, nullable. `display_label(name, label)` derives one from the name when unset; `FieldDTO.display_name`/`SchemaDTO.display_name` wrap that.

Validation is write-time only: rows predating the rule keep working, and `civex schema lint` (`SchemaService.lint_names()`) reports them. Restore/import paths pass `allow_legacy_name=True` so an old dump round-trips unchanged. UI forms collect the label first and auto-slug the name (`NameLabelFields`); editing never re-derives an existing name.

### Name templates

`domain/templating.py` is the one string builder: literal text with `{name}` / `{name:spec}` variables (`{{ }}` escape braces; a spec is `|`-chained ops: `upper lower title slug trunc(N)`, a number format `03` / `.2f`, or a date pattern `YYYY-MM-DD`). It is pure (`parse`, `validate`, `render`, `rename_field`, `remove_field`); `render`'s `on_missing` is `skip` (drop a blank value and the separator beside it — record names), `fallback` (None, so the caller keeps something else — file names) or `empty`. Built-ins `schema`, `id`, and for files `ext`, win over fields of the same name.

- A record's name is `schemas.display_template` rendered by `RecordService._natural_name` (surfaced as `RecordDTO.natural_name`); no template means the first non-blank value of a type not in `templating.UNNAMEABLE_DTYPES`. `SchemaService.add_field` starts a schema with no template (and no other own nameable field) with `{that_field}` so the rule is visible and editable (audited as a schema update; dump restore passes `auto_name=False`); schemas older than that keep the implicit rule, which the Naming tab names in its placeholder. It replaced the old `display_fields` list (the migration turns `[a, b]` into `{a} {b}`; `SchemaDTO.from_dict` still reads old dumps).
- `{ref.field}` reaches one hop through a single `reference` field whose `schema` restriction is set (`SchemaService._reference_targets` is what validation allows; file names pass none, so they can't). The engine stays pure: `render` just looks up the key `"ref.field"`, and `RecordService._label_references` fills it in from the targets it already batch-loads for reference labels (`reached_name`, so no extra query) — which means the name using it exists only on API reads, not in `_with_names` audit snapshots, and a target's own label never expands its references. `_template_holders` returns a `via` per hit (None = direct, or the reference field's name) so renames/deletes on the *target* schema's fields rewrite `{ref.f}` too.
- `SchemaService.update` validates a template against the schema's own and inherited fields. `_template_holders`/`_rewrite_templates` keep both `display_template` and every `filename_template` restriction in step when a field is renamed or deleted, resolving by field identity so a shadowed inherited field is left alone.
- `POST /schemas/{name}/preview-name` renders a template against sample values (errors come back in the body). Frontend: `components/templates/TemplateBuilder.tsx` (chips insert at the cursor, per-variable format picker by dtype from `utils/templates.ts`, server-rendered preview) is used by the schema page's Naming tab and the file field's download-name rule.

### Field restrictions

Which restriction keys exist for a type, and how the UI should present them, is declared once in `domain/field_descriptors.py` (`FIELD_TYPES`, `FIELD_KINDS`). `schema_service.VALID_RESTRICTION_KEYS` is derived from it and `GET /schemas/field-types` serves it, so the field editor (`components/schemas/FieldForm.tsx`, rendering `RestrictionControls.tsx` through `controlRegistry.ts`) and the record form's guidance build from data. Adding a restriction means: a descriptor entry, its check in `_check_restrictions()`, and — only if no existing `control` fits — a new control in `RestrictionControls.tsx` registered in `controlRegistry.ts`. Descriptors only describe; validation stays in `_check_restrictions()` (stored values) and `SchemaService` (restriction values, `_check_control_value` + `_validate_restriction_values`). Rules (validation) are kept apart from views (how a value is displayed, e.g. a spectrogram for audio): a field's views are meant to become another section of the field inspector (`InspectorSection` in `SchemaFieldsSection.tsx`) with their own settings, not more keys in `restrictions`.

Each field carries a `restrictions: dict[str, Any]` validated at write time by `_check_restrictions()` in `record_service.py` — the single source of truth. Restriction keys by type:

| Type | Keys |
|---|---|
| `integer`, `float` | `min`, `max` |
| `float` | also `unit` (symbol; canonicalised, e.g. `degC` → `°C`) |
| `string` | `choices` (list), `max_length` |
| `longtext` | `max_length` (multi-line text box; plain string, newlines kept; not nameable in name templates) |
| `date`, `datetime` | `min`, `max` (ISO strings; compared as parsed objects, not strings; `date` bounds may be partial) |
| `date` | also `precision` (`year` / `month` / `day`) |
| `geo` | `geometry_types` (list), `bbox` (`[west, south, east, north]`) |
| `datetime` | also `timezone` (IANA name; overrides the collection's `timezone` when reading and showing this field) |
| `file`, `file_list` | `accept` (comma-separated MIME/ext), `max_size` (bytes), `filename_template` (see below) |
| `reference` | `schema` (target schema name) |

`filename_template` is a name template (see "Name templates" below; `{ext}` is the original file extension) resolved server-side by `resolve_filename()` in `record_service.py`, a thin wrapper over `templating.render` that adds sanitising — rejected at field-save time if it names a field not on the schema (`SchemaService._validate_filename_template()`). `RecordService._with_names()` resolves it against each record's own field values and stamps the result onto every `file`/`file_list` value in API responses as `resolved_filename`, alongside the unchanged original `filename`; a blank/missing referenced field falls back to the original filename rather than emitting a partial name. The record-UI download link (`DynamicField.tsx`) uses `resolved_filename` for its `download=` attribute. `GET /files/{sha256}` stays content-addressed and record-agnostic — it doesn't accept record/field context to resolve a template itself; it takes an explicit `?filename=` override, so scripted consumers that want the resolved name read it off the record API and pass it through.

### Workflow execution

`executor.run()` topologically sorts steps (Kahn's algorithm), resolves `step_id.output_name` input references, and calls each plugin's `run()` in order. `ctx.commit()` is called once at the end. Custom plugins are discovered from `_civex/plugins/*.py` and must define a class named `Plugin` subclassing `BasePlugin`.

Workflow triggers fire via `trigger_for_record()` in `WorkflowJobService`. When a record is **created**, both `record_created` and `record_updated` are fired — but `record_updated` only includes fields with non-null values in `changed_fields`, so field-restricted triggers (`fields: [some_field]`) do not fire unless that field was actually set to a non-null value on creation.

Manual workflow runs supply inputs via `initial_outputs` in the executor (key `"__input__"`). Steps reference them as `__input__.field_name`.

**Deleting runs.** `WorkflowJobService.delete_runs(ids)` (`POST /jobs/delete` with `ids` or `filter`, `DELETE /jobs/{id}`, `civex automation delete [--pending]`, the runs table's **Delete N…**/**Delete all N…**) removes runs whatever their state: a waiting one never starts (the claim is a conditional UPDATE on a row that is gone), a running one stops before its next step (`should_stop` finds no row) and its final `mark_*` is a no-op. What it changed in records stays.

**Stopping and provenance.** `AutomationConfig.paused` (`[automation]` in config.toml, read cheaply by `read_automation_paused(civex_dir)`) is the kill switch, and `WorkflowJobService` is its one decision point: `trigger_for_record` enqueues nothing, `enqueue_manual` raises, and `claim_pending` returns None while paused, so the server's `run_pending_jobs` and the CLI's `drain_jobs` both stop at once. `stop_all()` pauses *first* (so a run can't spawn more), then cancels every pending/running job (`status = "cancelled"`); `cancel_job` does one. A running job learns it was cancelled because `executor.run(should_stop=…)` asks `job_svc.should_stop(job_id)` (a fresh status read, or paused) before every step and raises `JobCancelled` (carrying the steps done); both drains then call `mark_cancelled`, and `mark_completed`/`mark_failed` never overwrite a `cancelled` row. A step already running is not interrupted. `claim_pending` is an atomic conditional UPDATE. `WorkflowJob.trigger_detail` (`{changes: [{field, before, after, watched}], caused_by: {job_id, workflow} | null}`) says what started a run; `RecordService.update` computes `changed` from the stored values on both sides (never from the response form with its derived `resolved_filename`, which once made a workflow watching a file field re-trigger itself on every save), and `WorkflowContext.job_id`/`workflow_name` become the `_cause` passed to `record_svc.update/add` so a chained run can name its parent. `WorkflowContext.job_depth` must be passed by every drain (the CLI's once forgot, so chains never hit `MAX_JOB_DEPTH`). Frontend: `StopAutomationDialog` is the one confirmation; workflow runs and the pause show in the shared status bar (below); `RunSummary` shows what changed and the chain; `JobsTable` has a per-run cancel.

### Built-in plugins

| Plugin ID | Purpose |
|---|---|
| `civex.get_field` | Read a field from the trigger record |
| `civex.save_field` | Write a value to a field on the trigger record |
| `civex.save_fields` | Write multiple fields at once |
| `civex.load_file` | Load bytes + filename from a file field |
| `civex.load_file_list` | Load a list of file refs from a file_list field |
| `civex.extract_from_filename` | Apply a regex to a filename; optionally convert to date/datetime using token format (`YYYY MM DD HH mm SS`); non-token chars are raw regex so `[-_]` works as a separator alternative |
| `civex.create_records_from_files` | Create one record per file in a file list (no key matching — pure insert) |
| `civex.match_files_to_records` | Match files to existing child records by key extracted from filename; creates if not found |
| `civex.upsert_records` | Upsert records from a pandas DataFrame |
| `civex.rows_to_records` | Convert rows to records |
| `civex.parse_table` | Parse delimited bytes (CSV, TSV, ...) into a DataFrame; `delimiters` lets one step read several kinds |

**Writing records from a plugin.** `RecordService.update` (and so `WorkflowContext.update_record`) **replaces** a record's whole data with what it is given, so a plugin passing only the fields it knows erases the rest: `civex.upsert_records` once reduced records with 58 fields (a file, 49 computed values) to its table's 9 columns. Use `WorkflowContext.patch_record(id, fields)`: it reads the record fresh, merges only `fields`, and writes nothing when they already hold those values (no history, no triggers, not listed as touched). An absent value is left out of `fields`; it never clears anything. `upsert_records`, `save_field` and `save_fields` use it; `match_files_to_records` merges by hand.

### CLI pattern

Each CLI module (e.g. `cli/schema.py`) creates a `typer.Typer()` sub-app. Commands call `get_ctx()`, delegate to a service, print with `console` (Rich), call `ctx.commit()`, then `ctx.close()`. Error handling raises `typer.Exit(1)` after printing; `CivexError` subclasses (`NotFoundError`, `AlreadyExistsError`, `ValidationError`) are the canonical error types.

### Frontend

React + TypeScript (Vite). Entry: `frontend/src/main.tsx`. Routing via React Router; data fetching via TanStack Query v5.

```
frontend/src/
  api/          # Typed fetch wrappers (schemas.ts, records.ts, workflows.ts, …)
  hooks/        # TanStack Query hooks (useSchemas, useRecords, useWorkflows, …)
  pages/        # One file per route (SchemaDetailPage, RecordDetailPage, JobsPage, …)
  components/   # Shared UI (records/DynamicField.tsx, jobs/JobsTable.tsx, …)
  utils/dates.ts  # timezone-aware datetime helpers (utcToZonedLocal / zonedLocalToUTC / formatDateTime / effectiveTimeZone)
```

The schema page (`pages/SchemaDetailPage.tsx`) is a compact header over tabs held in the address (`?tab=`): Fields (`SchemaFieldsSection`), Naming (`NamingSection`), Automations, History (delete is in the page's actions menu). Records are browsed from Collections, not from here.

Settings is a set of sub-pages, not one scroll: `pages/settings/SettingsLayout.tsx` is a section list plus an `<Outlet/>`, with routes `/settings/<appearance|database|storage|recently-deleted|map|advanced>` and `/settings` redirecting to Appearance. Settings > Storage (`components/settings/storage/StorageSettings.tsx`) has Volumes / Collections / Tasks tabs (Tasks = `TasksTab`: two cards, **Move files** (`NewTransferModal`) and **Clean up unused files** (`CleanUpDialog`), above the list of moves (`TransfersTab`); the old `?tab=transfers|maintenance` addresses still open it). `CleanUpDialog` looks (a dry GC run) as soon as it opens, says what it found in plain words, and one button deletes exactly that; it is the one clean-up UI, opened from Tasks (every volume) and from a volume page's *Unused* row (`volume` set, so `POST /store/gc` / `GCService.run(volume=)` / `civex store gc --volume` only touch that volume, and leave abandoned-upload scratch files to a store-wide pass), with the tab and a volume filter held in the address (`?tab=collections&volume=archive`). A volume's own page is `VolumePage` (`/settings/storage/volumes/:name`, a routed page outside the Settings layout; the volume row is a link to it): it pivots the same collection-by-volume data (`useAllCollectionStorage`) to show which collections are on the drive, plus the volume's `unused_*`/`history_*` bytes (from `FileReferenceRepository.surplus_by_volume`, merged into `GET /store/volumes`) and the moves involving it (`TransferCard`, shared with the Tasks tab). The list and the page share `VolumeSpace` and `useVolumeActions` (edit/remove/adopt/queue and their dialogs), so neither has its own copy. Above the tabs `StorageAttention` lists what needs a look, built by `hooks/useStorageAttention.ts`, the single place that decides what counts (unreachable volume holding files, low space, a move running/paused/interrupted). Where a collection's files are comes from one rule: `FileInfoService.all_collection_storage` (`FileReferenceRepository.volume_breakdowns`, catalog only) behind `GET /store/collections[/{id}]` and `civex store collections`; the single-collection answer is the bulk one for one id. `SpreadBar` and `utils/collectionStorage.gatherPlan` are the shared bar and "gather onto where?" rule used by the collection page and the Collections tab. The Collections tab is the one place homes are assigned (per row, or in bulk; `?focus=<collection id>` opens it filtered to one); a collection page's own Storage tab (`CollectionStorage`, `CollectionFileLocations`) is a read-only report (where the files are, which drive to plug in, where new files go) whose "Change"/"Gather" actions are links into Settings, so there is one copy of that logic. There is deliberately no Storage item in the sidebar; instead a running move shows live in the bottom status bar (see **Status bar** below).

Pins, recents and the Ctrl+K palette are per-browser (localStorage, `utils/pins.ts` + `hooks/usePins.ts`; there are no user accounts). A pin's `NavTarget` is built in `utils/navTargets.ts`; a pinned saved filter's live count is `hooks/useViewCount.ts` (keyed under `records`, so any record edit refreshes it).

On the record page, `RecordFieldGrid`'s `FileControl` attaches at once: `FileDropZone` (`components/ui`, the one file chooser, shared with `DynamicField` and the workflow run dialog) hands the files over, `utils/fileChecks.ts` refuses a wrong type or oversize file *before* upload, `useFileUploads` uploads, and the record is saved straight away (so workflow triggers on the field fire on upload). The only confirmations are for a file going: removing one, or replacing a single-file field's current one. A removed file's bytes are left to `gc_service`. Running a workflow is a visible button in the record page header (`components/workflows/RunWorkflowButton`: one workflow is one button, several are a menu); one that takes no files starts at once with a toast offering **View run**, and `WorkflowRunModal` opens only for `files` inputs and never shows the record ID when opened for a record.

**Creating records.** A record's explorer (`RecordsExplorer`) builds one **New** menu: the listed schema, then, inside a record, every child schema of that record's own the collection allows (`childStarters`, so a record with none yet can still get its first), else the top-level starters; each goes to `NewRecordPage`, whose **Add and add another** saves and stays on a blank form (`round` remounts the fields; a parent fixed by the list is kept).

**Lists held in the address.** `useListParams` keeps search, filters, sort, page and size in the query string. `Pagination`'s `onPageSize` must change the size *and* return to page one in ONE call (the list setters already do): React Router's functional `setSearchParams` is not queued, so a second call in the same event starts from the old address and undoes the first (a `onPage(0)` after `onPageSize` is what once made the Rows menu do nothing). `DataTable` takes `dense` for scan-heavy lists; the runs table uses it with `selection` for bulk re-run (`POST /jobs/rerun`, one request) and a `workflow` filter (`GET /jobs?workflow=`, exact name).

**Status bar.** The bar at the bottom of every page is generic: `components/status/TaskStatusBar` draws any list of `BackgroundTask`s (`utils/backgroundTasks`: title, optional progress bar, detail, note, actions that are buttons or links, an optional `overlay` for a dialog) and knows nothing of what they are. Each kind of work is a *source* hook in `hooks/tasks/` that turns its own state into tasks (`useMoveTasks`: the running move with progress, speed, ETA and Pause, one waiting for a drive, or how many wait; `useAutomationTasks`: the pause, with Resume, or runs busy for `SHOW_AFTER_MS` with how many wait, a batch progress bar once there is more than one run, and Stop), and `hooks/useBackgroundTasks` lists them. To show another kind of work, write a source and add one line there. Runs go one at a time, so the bar never says how many are "running".

**Filtering runs** reuses the records' filter, not a copy. The wire format and `parse_filter_tree` are `domain/filters.py`'s; the run fields are declared once in `domain/run_filters.py` (`RUN_FIELDS`, served by `GET /jobs/filter-fields`; `parse_run_filter` checks fields and operators, no `schema`). `job_repo._tree`/`_condition` compile a tree onto `workflow_jobs` columns (error kind/step via `error_details` JSON), and list, count, `ids_matching` (bulk re-run by `filter`), `failure_groups` and the UI all take the same `filter`. Frontend: `JobsTable` renders `FilterControls`/`FilterBuilder` over `utils/runFilter.runFilterFields` (a `FilterableField` with `ownerless` and per-field `operators`, so no schema heading and no `schema` on conditions); the old `status`/`trigger`/`workflow` params are read as a filter (`legacyRunFilter`). `FailureGroups` is the triage panel. No migration was needed.

**The batch tracker** (`useAutomationTasks`) reads `batch` from `GET /automation`, counted by `job_repo.batch_stats` from existing timestamps: every run queued while the queue was non-empty since it last emptied (a run finished after the batch's earliest member was queued belongs to it). Failures count as done. It shows a bulk start at once (a single run only after `SHOW_AFTER_MS`), and when a batch ends with failures leaves a notice (counted by `jobs/count`) until dismissed. Mutations that start runs refresh `['automation']` straight away (`refreshRuns`), because idle polling is 15 s.

**Runs that finished with problems.** `utils/runNarrative.runProblems` is the one rule: skipped rows plus `unmatched` and `ambiguous` step outputs. `JobStatusBadge` takes `problems` and shows an `attention` badge instead of a green one (list and run page); `RunSummary` opens with the problems and the files named. A new plugin output that means "left something undone" belongs in `runProblems`.

**Bulk run.** `POST /workflows/{name}/run-many` (`RunManyRequest`; one run per record, `skipped` with reasons like `/jobs/rerun`; 422 for a workflow with `files` inputs). `RecordsExplorer`'s `SelectionBar` takes an `actions` slot holding `BulkRunWorkflow` (`bulkRunnable` filters by `record_schema` and no files input); not offered for "all matching".

**A run's page** (`pages/JobDetailPage`) has `?tab=` tabs, Summary / Steps / Records touched (`components/jobs/RecordsTouched`, names live from `RecordName`). A link from a record page carries `?from=<record id>` (`JobsTable` with `recordId`, `RecordProvenance`): the page then builds its breadcrumb from that record's ancestors (`recordTrail`) ending on `/records/<id>?tab=runs`; without it the trail is `Runs ›`. Keep `from` when switching tabs or re-running. `civex.match_files_to_records` refuses to guess: files whose normalised keys clash within a run are all skipped and listed in its `ambiguous` output (a pattern like `sel_([0-9]{2})` once made 64 files into 47 keys and silently overwrote 17 contour files).

**Shift-click ranges.** Every list of checkboxes picks a range the same way: click one, shift-click another, and everything between them in the order shown takes the second box's new state. The logic is one hook, `hooks/useRangeSelect` (`onClick` on each box records shift, since a change event doesn't carry it; `rangeFor(id)` in the change handler returns the ids or null), used by `DataTable` (so every table with `selection`; an optional `onSetMany` makes a range one update, else it toggles each row that needs it), the column picker, the collection schema list (each box in the range goes through the parent/child rule) and the geometry-type boxes. A new multi-select should use it.

**Tab titles.** `Page` sets the browser tab (`hooks/useDocumentTitle`, `utils/documentTitle`): the current thing first, then what it sits inside, nearest first, then `civex` ("Sample 12 · Patient 3 · study · civex"). It is made from the page's text title, or else the last item of its breadcrumb trail, plus the earlier trail items; a page made of several areas passes `documentTitle` instead (Settings does, adding the Storage tab: "Tasks · Storage · Settings · civex"). The title goes back to `civex` when the page goes away.

**UI components and content rules** live in `frontend/UI-AUDIT.md` ("Component and content rules"): one component per concept in `components/ui/` (`Button`/`IconButton`, `Chip`, `SegmentedControl`, `ListButton`, `Card`, `DataTable`, `SortableList`, `TabNav`/`TabPanel` + `useTabParam`, `Disclosure`, `InfoTip`/`Tooltip`, `Subheading`). Don't write a raw `<button>`, `<table>` or `<details>` outside `ui/` (lint warns). Explanations are tooltips (`Page info=`, `Field info=`), not paragraphs; `Page meta=` is for facts only; big pages are tabs held in the address, never stacked collapsibles. Rows and cards are clickable as a whole (`DataTable rowHref`/`onRowClick`, `Card to`), and controls are at least 32 px.

**Navigation state.** Anything that is a place lives in the address: tabs (`useTabParam`, pushes history), the explorer (`schema`/`within`/`q`/`filter`/`sort`), and a simple list's search, dropdown choices, sort and page (`useListParams`, with `ListToolbar` above a `DataTable`; used by Runs and every History tab, namespaced by `ns`, replaces history). A record's Contains tab is the record explorer itself (`RecordsExplorer root=`), so descending the hierarchy never leaves the record page. Cancel and "done" actions use `useBack(fallback)` (a step back in history, else the fallback) instead of hard-coded list links, and a finished form replaces its own history entry. Runs filter by status, trigger and search and sort by column on the server (`GET /jobs`); every audit endpoint takes `action` and `sort` through one `AuditView` dependency.

`DynamicField` is the single component that renders an editable input for any field type, including restriction-aware behaviour (choices→select, min/max, accept/max_size on files). `JobsTable` owns its own pagination state and accepts `recordId?` + `statusFilter?` props — do not duplicate pagination in parent pages.

## Documentation

The docs site lives under `docs/` (MkDocs Material, see `mkdocs.yml`). Some pages are generated at build time — editing a generated page directly loses the change on the next build, so know which is which before touching a file under `docs/`:

| Path | Source of truth |
|---|---|
| `docs/reference/cli/*` | Generated from `civex.main:app` by `docs/_gen/_cli.py` |
| `docs/reference/http-api.md` + `openapi.json` | Generated from `create_app().openapi()` |
| `docs/reference/plugins/*` | Generated from the plugin registry + `docs/_prose/plugins/*.md` |
| everything else under `docs/` | Hand-written |

Keep-in-sync rules:

- New CLI command → write prose help only; no indented line art, and never `\b` escapes — it renders in the generated reference.
- New HTTP endpoint → add a docstring, and `Field(description=)` on any new request/response model — both feed the generated `http-api.md`.
- New built-in plugin → add `docs/_prose/plugins/<slug>.md` with the `<!-- civex:tables -->` marker, or CI fails.

`make docs` serves the site with live reload; `make docs-build` runs the strict build CI uses.
